# Quick Task 260915-v51: Fix the Kernel Copy-Per-Commit Quadratic — Summary

`World::Transaction` replaces the whole-World copy that `Kernel::submit`,
`Kernel::fromJournal` and `Kernel::replayUpTo` each made once per commit, so
reopening a world now costs time proportional to the ops in its journal rather
than to commits squared — 32,000 commits went from 23.0 s to 0.19 s with the
atomicity guarantee and every byte of the `.tree` format unchanged.

## What Changed

`World::Transaction` is a scoped scratch over a world that now changes in
place. Before each op is applied it saves that op's footprint, and its
destructor puts the saved values back unless `commit()` ran — so every early
return from `submit` (a `Rejection`, a record that would not decode, a failed
`Journal::append`) restores the world without the return site having to
remember to.

`World::prepare` and `World::apply` were not modified at all: `World.cpp` and
`World.hpp` have **zero removed lines** in the diff, purely additive. Validation
order, id assignment, the delete cascade and tick arithmetic run through the
identical code, so replay determinism cannot have drifted by construction.

The footprint, one `std::visit` branch per op alternative with no default
branch (an eighth verb is a compile error here too):

| Op | saved before it is applied |
|---|---|
| CreateNode | the node id it carries (absent → rollback erases it) |
| SetProperty | the one property the target and key name |
| UnsetProperty | the one property the target and key name |
| CreateEdge | the edge id it carries |
| DeleteNode | the whole node, plus every live edge whose `from` or `to` is that node — the cascade `apply` performs and no file line records |
| DeleteEdge | the whole edge |
| Advance | nothing; the tick was saved when the transaction opened |

Per-id saving is first-touch-wins and tri-state (live value / tombstoned /
absent), which is what makes a create-then-delete inside one rejected commit
leave no tombstone behind.

## Measured Before and After

Same machine, same shape as spike 006 (one node, one commit per new property
key), `Kernel::openBytes` best of three after a discarded warm-up:

| commits | before | after | speedup |
|---|---|---|---|
| 1,000 | 24.90 ms | 6.19 ms | 4.0x |
| 4,000 | 325.70 ms | 24.48 ms | 13.3x |
| 8,000 | 1352.13 ms | 47.90 ms | 28.2x |
| 32,000 | 23002.26 ms | 190.46 ms | 120.8x |

Growth shape — the cost of 4x the commits (linear predicts ~4, quadratic ~16):

| measurement | before | after |
|---|---|---|
| 1,000 → 4,000 | **13.08x** | **3.96x** |
| 8,000 → 32,000 | **17.01x** | **3.98x** |

The 32,000-commit figure reproduces spike 006's worst case (26,814 commits →
22,668 ms) and now returns in under a fifth of a second.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's entity-level footprint did not remove the quadratic**

- **Found during:** Task 2, at the first post-fix run of Case C.
- **Issue:** Implemented exactly as the plan's footprint table specified
  (`SetProperty` saves "the node or edge the target names"), the change left
  reopen at **14.38x** for 4x the commits — still quadratic. A probe isolating
  the phases showed `Journal::scan` linear (6.1 → 10.3 → 20.5 → 40.3 ms as
  commits doubled) and replay still doubling-squared (21.5 → 75.6 → 311.6 →
  1269.4 ms). The cause: saving "the node" a `set` addresses copies the node
  *including its whole property map*, so a node accumulating one property per
  commit still costs O(properties) per commit. This is precisely the shape the
  plan's own objective calls out — "2.3's writing threads make a single node
  accumulate tens of thousands of properties" — so the entity-level footprint
  could not satisfy the plan's first must-have truth.
- **Fix:** `SetProperty` and `UnsetProperty` now save **one property**
  (`(id, key) → previous value or absent`) rather than the entity. The
  mechanism is unchanged — still a narrow scratch saving values, never inverse
  ops; still no change to `prepare`/`apply` — it is the same narrowing taken
  one step further, from "the whole world" to "the touched entities" to "the
  touched entities and, for a property write, the touched property".
- **Consequence for correctness:** rollback became two passes, entities then
  properties, because a commit may set a property on a node and *then* delete
  that node — the saved entity is the node as it stood after the set, the saved
  property is what it held before, so the property must be restored second. A
  property whose entity is not live after pass one is skipped: its entity save
  already put that id back the way it was. Case A's A3 (create-then-delete in
  one rejected commit) covers the interaction.
- **Files modified:** `tapestry/kernel/World.hpp`, `tapestry/kernel/World.cpp`
- **Commit:** 7fed53f

**2. [Rule 3 - Blocking] A peer session's staged deletion leaked into the first commit attempt**

- **Found during:** Task 3, at the post-commit path gate.
- **Issue:** This run shares one working tree — and therefore one git index —
  with the Phase 2.2 session. That session had staged a deletion of
  `app/src/renderer/components/SaveIndicator.tsx`. `git commit` commits the
  index, not just what this run staged, so the first commit (6be32b3) contained
  six paths, one of them under `app/`. The plan's own staged-path gate caught
  it; it is exactly threat T-v51-05 arriving from the opposite direction than
  anticipated.
- **Fix:** `git reset --soft HEAD~1`, then `git restore --source=HEAD --staged`
  on the non-`tapestry/` path only — which un-stages it while leaving the
  deletion in the working tree, so the peer session lost no content. Recommitted
  as 7fed53f with five paths. **Confirmed preserved:** their next commit
  (fe33d69, `feat(02.2-05): frame headers…`) carries the
  `SaveIndicator.tsx` deletion, so nothing of theirs was destroyed.
- **Lesson for future shared-tree runs:** staging by explicit path is not
  sufficient. The staged list must be inspected with `git diff --cached
  --name-only` immediately before `git commit`, and any foreign path un-staged
  with `git restore --source=HEAD --staged` (never `git reset --hard`, never
  `git checkout --`, which would destroy the peer's working-tree content).
- **Files modified:** none — git history only.
- **Commits:** 6be32b3 (rolled back, never pushed), 7fed53f (final)
