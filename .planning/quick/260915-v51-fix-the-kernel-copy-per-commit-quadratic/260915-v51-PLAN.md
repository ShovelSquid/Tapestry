<objective>
Kernel::submit, Kernel::fromJournal and Kernel::replayUpTo each copy the entire World once per
commit to buy all-or-nothing atomicity. The world grows as commits accumulate, so opening a world
is O(commits²): spike 006 measured 2,268 commits -> 176 ms and 26,814 commits -> 22,668 ms,
exponent ~2.0.

Copy only the nodes and edges a commit touches instead of the whole world. Keep the scratch and
restore shape, keep the atomicity guarantee word for word, narrow only what gets copied.

Purpose: reopening a world must stay usable as history accumulates — 2.3's writing threads make a
single node accumulate tens of thousands of properties, and every world eventually accumulates
commits.
Output: `World::Transaction` (a narrow scratch with a restore), the three kernel call sites rewired
onto it, the comments in Kernel.hpp/Kernel.cpp made true again, and three new kernel tests.
</objective>

<mechanism>
Decided by the user; the executor implements it rather than re-choosing it.

**Chosen:** a narrow scratch. Before each op is applied, copy the entities that op will change
(and only those) into the scratch; if the commit does not complete, put those copies back. Scratch
and restore, exactly as now — what shrinks is what gets copied, from "the whole world" to "the
touched set". The guarantee is unchanged.

**Rejected, do not implement:** an undo log of inverse ops. It needs a correct inverse per op kind,
which is more surface and more ways to be subtly wrong. `Transaction::record` saves *values*, never
inverses: rollback puts a saved entity back without knowing which op removed it.

**Not an option either:** making `World` copy cheaply via shared entity pointers. That still copies
the map spine once per commit, so a world where each commit creates a node stays quadratic.

Why it is safe: `World::prepare` and `World::apply` are not modified at all. Validation order,
id assignment, the delete cascade and tick arithmetic run through the same code as today, so the
deterministic core's semantics cannot drift by construction.
</mechanism>

  <action>
    Add a nested `World::Transaction` declared in World.hpp and defined in World.cpp, and a
    `World::Transaction begin();` factory on World. Transaction holds a `World&`, is neither
    copyable nor movable, and offers: `prepare(Op&)` forwarding unchanged to World::prepare;
    `apply(const Op&)` which first saves that op's footprint and then calls World::apply
    unchanged; `commit()`, which keeps the change and drops the saved copies; and `rollback()`,
    which puts the saved copies back. The destructor rolls back unless commit() ran, so every
    early return from submit — a Rejection, a record that would not decode, an append failure —
    restores the world without the return site having to remember to.

    Do not modify World::prepare or World::apply. Their semantics are the contract; the whole
    point of this shape is that the deterministic core keeps running the identical code.

    At begin(), save the three scalars: the next node id, the next edge id, and the tick. They are
    O(1) and cover every op that moves a counter, so `advance` needs no per-op record at all.

    Per-entity saving is a first-touch-wins tri-state, so restoring is uniform and needs no
    knowledge of which op did what. For an id being saved for the first time, record either the
    live entity's value, or that it was tombstoned, or that it was absent. Rollback then: value
    saved -> put the entity back and clear any tombstone for that id; tombstoned -> erase the
    entity and re-add the tombstone; absent -> erase the entity and erase any tombstone. The third
    case is what makes a create-then-delete inside one rejected commit leave no tombstone behind.

    Footprint per op kind, saved before World::apply runs. Write it as a std::visit with one
    branch per alternative and no default branch, the way every other Op visitor in this kernel is
    written, so an eighth verb is a compile error here too:

    | Op | saved before it is applied |
    |---|---|
    | CreateNode | the node id it carries. prepare() has already assigned it, so record must run after prepare and before apply |
    | SetProperty | the node or edge the target names |
    | UnsetProperty | the node or edge the target names |
    | CreateEdge | the edge id it carries |
    | DeleteNode | the node id, plus every live edge whose from or to is that node — the cascade apply performs. Missing these is how a rejected delete would restore a world with edges gone |
    | DeleteEdge | the edge id |
    | Advance | nothing; the tick was saved at begin() |

    The delete-node branch scans the edge map, which is the same scan World::apply already does
    for that op — this adds no new order of growth, and it is the only op with a footprint larger
    than the ids it names.

    Rewire the three kernel sites onto Transaction, preserving each one's existing outcome exactly:
    - fromJournal: one transaction per commit; on a refused op, markCorrupt and return as now — the
      destructor restores the world to the previous commit, which is where the discarded copy left
      it today.
    - replayUpTo: still rebuilds from an empty World; one transaction per commit; a commit whose op
      is refused is skipped and the loop continues, exactly as now.
    - submit: one transaction across the op loop; commit() only after Journal::append has
      succeeded, so the world still moves last.

    CRITICAL, and the one place this refactor can silently change the file format: submit builds
    the record's tick from the world, and today that read happens while the world has not yet
    moved, so it is the tick *before* this commit's advance ops. Applying in place makes a naive
    read return the tick *after* them, which would write a different tick line, and a journal
    written that way fails to decode on reopen with TickMismatch. Capture the tick into a local
    before the op loop and build the record from that local. The existing case "kernel: tick lines
    follow advance" (kernel_test.cpp ~line 759) is the gate on this.

    Then make the prose true again, in this same task:
    - Kernel.hpp submit doc (~lines 56-62): describe the narrow scratch. Leave the sentence "A
      Rejection or an I/O error at any point leaves both the file and world() exactly as before."
      byte for byte — it is the contract and it is still true.
    - Kernel.hpp replayUpTo doc (~lines 70-74): confirm it still reads true and adjust only if not.
    - Kernel.cpp file-header comment (lines 1-3) and the fromJournal comment (~lines 92-95): both
      describe copying the world per commit. Rewrite them to describe what the code now does.
    - World.hpp: document Transaction next to the class comment, and put a line above the private
      member list saying that every member listed there must be covered by the rollback, so the
      next person to add a field is told what they owe it.

    Do not commit. Task 3 commits.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| journal file -> world | Verified but possibly hostile `.tree` bytes are replayed into memory on open |
| caller (plugin, agent, renderer) -> submit | Untrusted ops reach World::prepare; a rejection must leave no trace |
| this session -> the 2.2 session's working tree | Two writers share one checkout; a stray edit or a broad `git add` is a real corruption path |

|-----------|----------|-----------|----------|-------------|-----------------|
| T-v51-01 | Tampering | World::Transaction::rollback | high | mitigate | An incomplete restore would silently persist half of a rejected commit into the next accepted one. Rollback covers all seven World members, the footprint map is a std::visit with no default branch (an eighth verb becomes a compile error), and Case A asserts full observable-state identity after four different rejection shapes, including the cascade and create-then-delete |

The tick is captured into a local before the op loop; "kernel: tick lines follow advance" and Case B's byte-identity check are the gates |
