# Phase 02.8 Plan 04: Status, main and shared half Summary

**A chat's Claude can now call `set_status({ text, needs?, level? })`. It reaches only its own session as a service-level `status` event and never enters the tree. One pure reducer (`src/shared/chat/session-status.ts`) derives Idle, Working, Needs you, Done and Failed, the status line and the level from observed events. Main keeps each session's last status text in chats.json so a relaunch opens as Idle with it.**

## Accomplishments

- **The tool.** `SetStatusArgs` is a strict zod object: `text` is 1 to 120 chars on one line ("text must be one line"), `needs` is optional boolean, and `level` is an optional integer from 0 to 100. The `set_status` definition uses the plan's title and description and `readOnlyHint: true`. The shim registers it from `TOOL_DEFINITIONS` like every other tool, and shim.test now asserts 21 names.
- **Dispatch.** `case 'set_status'` refuses with `SET_STATUS_REFUSAL` ("set_status is only available to Tapestry's in-app chats") when `commands.chat` is absent. Otherwise it calls `commands.chat.setStatus(actor, args)`, with the actor taken from the socket token. index.ts sets `agentCommands.chat` right after the ChatService is built.
- **ChatService.setStatus.** It finds the loaded session whose `agentActor(session.agent).id` is the caller's (and that is not being deleted), else refuses. It records `{ type: 'status', text, needs, level: clampLevel(level ?? (needs ? 3 : 1)) }` into the open turn (or ahead of the next one) and emits it tagged with that turn. It never calls SessionNotes. `turnItemsFromEvents` ignores `status` events and already left out `set_status` calls, so the passage never holds either.
- **The reducer** (`reduceStatus(status, { kind: 'event', event } | { kind: 'ack' }, now)`) is exhaustive and has no side effects. It takes the transcript's events plus `status`:
  - `user` gives Working with "Reading your message", clears Needs you and resets the turn's set_status memory.
  - The status text comes from `status` first. After that, tool calls (`toolLabel`, which drops the MCP prefix and any payload) and a reply's first line no longer change it that turn.
  - `status` with `needs` or level 3 gives Needs you at level 3. It persists through done, ack, Stop, errors and later statuses, until a `user` event.
  - `done ok` gives Done at the turn's last set_status level, else 2.
  - `error` gives Failed with the short phrase. `done ok:false` with no error gives "The turn didn't finish". Once Failed, a later ok `done` stays Failed.
  - A `done` with `reason: 'stopped'` gives Idle with "Stopped".
  - `ack` turns Done or Failed into Idle and keeps the text. On any other state it returns the same object.
  - `arrivedAt` changes only when the state changes.
  - A level-0 status changes `text` but not `cardText`.
- **Helpers.** `statusLine(status, forCard?)` gives `<State word> · <text>`, or the text alone for Idle. `statusTextAfterTurn(events)` folds a turn from Idle. `shouldAnimate(level, threshold)` is true when `level >= 1 && level >= threshold`. `failedPhrase(kind)` and `FAILED_PHRASES` cover the eleven phrases.
- **The last status text.** `ChatService` computes `statusTextAfterTurn` over the open turn's events at each `set_status` and at each turn commit (including the commit on quit). It keeps the result in memory and in chats.json v2 `sessions[key].lastStatus`, capped at 200 chars and read back defensively. `open()` returns `lastStatus` (string or null) next to `busy`. `deleteSession` drops it with the entry.
- **The prompt.** `chatSystemPrompt` gained: "Use the tapestry set_status tool to show a few words about what you are doing when you start something new, and call it with needs: true whenever you ask the person a question or wait for their answer."
- **The fake.** fake-claude has a `status` scenario: it calls `set_status` through the real shim, emits the tool_use and tool_result, then "Which file should I read?". Its MCP start-up and tool call are now shared helpers (`ensureMcp`, `callTool`, `reply`), and the `edit` scenario uses them unchanged in behaviour.

## Decisions Made

- **Needs you outranks every later event** in its session until a `user` event: `done`, `ack`, a stopped `done`, an `error` and a later non-needs status all leave the state, the "!" and the question's text standing. This follows D-11 and UI-SPEC § Leaving a state.
- **A level above 3 is clamped, so a level of 9 (and level 3 without `needs`) raises Needs you**, as A-04 says for level 3.
- **Working carries a level:** 1 by default, or the level of the latest status this turn. Done takes the turn's last set_status level (0 is allowed) or 2. Failed is 2 (A-07). Idle is 0.
- **What is stored as lastStatus** is the full `text`, not `cardText`, as the plan says ("the reducer's text"). A level-0 text can therefore show on the card after a relaunch. That is minor and easy to change in 02.8-05 if it looks wrong.
- **A quit mid-turn stores "Stopped".** The close path commits the turn with a stopped `done`, so the stored text matches the passage. The UI-SPEC § Relaunch wording ("shows its last status text followed by nothing else") fits either way.
- **`initialStatus` takes an optional `turns`.** A session with turns but no stored status (every session made before this plan) opens Idle with an empty text rather than "New chat". The renderer in 02.8-05 can pass `committedTurns(node)`.

## Known limitation (by design)

**Sessions started before this plan do not know `set_status`.** `--system-prompt-snapshot` reuses a session's first system prompt on every resume, so a session begun under the 02.7, 02.8-01, 02.8-02 or 02.8-03 prompt never hears of the tool. Its status falls back to the tool label and the first line of the reply (D-13), and it never raises Needs you. A new chat has the tool.
