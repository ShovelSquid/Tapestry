# Phase 2.8: Agent Note Windows - Research

**Researched:** 2026-09-25
**Domain:** Electron main-process chat service re-keying, `.tree` transcript encoding, MCP tool addition, React canvas chrome (status, edge arrows, forks)
**Confidence:** HIGH for the codebase facts (every claim below was read this session); MEDIUM for the recommended encodings and signatures (they are designs, marked as such)

## Summary

Everything this phase needs already exists in shape: `ChatService` (one chat per workspace tree, keyed by tree id), the `ChatEngine` seam, a CLI engine that resumes by `--resume <id>`, a zod-validated MCP tool table re-checked in main, an agent bridge that stamps the actor from a per-agent token, the 2.5 `resolveWhere` placement resolver (already imported by main), pure window/camera geometry, and a node-environment vitest harness with a token-free fake `claude`. No new npm package is needed. The work is re-keying and composition, plus four genuinely new pieces: a plain-text transcript grammar, a pure status/level reducer, pure edge-arrow geometry, and the fork path.

Four findings change how the phase must be planned. (1) **Workspace trees refuse renderer node creation and deletion** (`workspaceSubmitRefusal`) and refuse undo, and `NoteCommands` refuses every note tool in a workspace tree. So session notes can only be created, appended to, forked and deleted by new **main-process** paths that write through `tree.bridge.submitAs` directly, and the UI-SPEC's "one undo restores a deleted chat" cannot hold in a workspace tree. (2) **2.1 passage anchors were never wired to edges** (review CR-03): the `passage` mark exists in the ProseMirror schema, but no code writes an edge that points at an anchor. Session bodies should be plain text, not ProseMirror JSON, so a turn's anchor is its turn number, carried as an edge property (`set e<k> turn int <k>`). This is new convention, not reuse. (3) **The "D-05 per-agent edit gate" premise is stale.** 02.4 replaced it with locks, and `AGENT_NOTES_OPEN_TO_AGENTS = true` plus the workspace lock policy mean any agent may edit any agent note and any workspace file. Per-session identity gives attribution and colour, not isolation. (4) **UI-SPEC A-01 cannot work as written.** Note ids are `n<k>`, not hex. Derive the agent name from the tree id and the note id instead.

**Primary recommendation:** Add a new node type `tapestry.chat/session@1` whose `body` is a plain-text transcript in a small line grammar (`src/shared/chat/transcript.ts`) and whose `chat.turns` int counts committed turns. Write every session commit (create, turn, fork, delete) from a new main module, `main/chat/session-notes.ts`. Key `ChatService` by `(treeId, noteId)`, with agent `claude-chat-<first 8 hex of tree id>-<note id>`. Add `set_status` as the 21st bridge tool, routed to `ChatService` and never to the tree. Keep all status, level, arrow and view state in one renderer store with pure, vitest-covered reducers.

### Locked Decisions

#### Sessions are notes
- **D-01:** Only in-app chat sessions appear. MCP agents and terminal sessions come later.
- **D-02:** A session is a note (a node) in its workspace tree, with a real placement, so `place` and `lock.layout` apply. Any number per workspace. `ChatService` is keyed by session note id instead of tree id, with an MCP config per chat.
- **D-03:** Every session is its own agent, and a fork gets a new one. Under D-05, sessions can't edit each other's notes. The spec writes the name as `agent.claude-chat.<session>`, but `ACTOR_NAME_RE` (`main/commands/actor.ts:53`) allows `[a-z0-9_-]` up to 32 characters, so use something like `claude-chat-<short id>`. Exact form is Claude's discretion.
- **D-04:** The docked `ChatPanel` is the enlarged view of a session note, not a second UI or a second store.
- **D-05:** The card keeps its note size and the conversation scrolls inside it. Scroll position, card size and open or closed state are view state.
- **D-06:** The dialogue box is in the window: you reply to a "needs you" right there on the card.

#### Transcript: one document (Kaelen, 2026-09-25)
- **D-07:** A session's turns are stored as one document, not as child notes. Each turn (your message, then the agent's reply) is a passage appended to the session note's text, one commit per turn, so it reads without Tapestry. Turns never use notes-inside-notes (`inside ref`).
- **D-08:** Tool calls go into the transcript as one-line summaries, never full payloads.
- **D-09:** Replay uses the recorded replies, never a new model call.

#### Status and states
- **D-10:** Status is chrome, never history. Working blur, flash, "!" and the live status line are renderer state. Nothing about status enters `.tree`.
- **D-11:** States: Idle (no turn running, nothing unread: sharp, quiet); Working (`engine.busy`: blurred and desaturated, not the gray author-unknown token); Needs you (the agent called `set_status` with `needs: true`: a "!" that persists until you reply, not colour alone and not motion alone); Done (`done { ok: true }`: jiggles and flashes in the agent's author colour, then settles and decays); Failed (`error` or `done { ok: false }`: must not look like Done, uses the `ChatErrorKind` plain-words message).
- **D-12:** After a relaunch every session shows Idle with its last status text, never a stale Working. The engine resumes by `resumeSessionId` on the next send.
- **D-13:** New workspace tool `set_status({ text, needs?, level? })`. `text` is a few words, `needs: true` raises Needs you, `level` 0-3 is clamped to the ceiling. The bridge stamps the actor. It writes nothing to the tree. Without it, the status line falls back to the last tool call or the first line of the last reply, and the level falls back to 2 on done. Never guess "needs you" from text.

#### Levels and attention
- **D-14:** Levels: 0 silent; 1 status text updates, no motion; 2 jiggle and flash (default on done); 3 persistent "!" (default on needs you). Fixed ceiling 3 until rank exists (2.4 deferred `lock.rank`).
- **D-15:** A visibility threshold in settings sets the lowest level that animates; lower levels only update text.
- **D-16:** Agents never move the camera. A window that changes state rises in its local stack order (`surface-windows.ts`). An off-screen session at level 2 or above gets an edge arrow in its author colour, with "!" for needs you. Clicking the arrow pans to it; that is the person's action.

#### Reply at any turn: forks
- **D-17:** Replying at the last turn continues the note. Replying at an earlier completed turn k leaves the original note untouched and creates a new session note beside it with turns 1..k, your reply, and the conversation from there. It is placed with 2.5's resolver (`beyond` the original, from its parent).
- **D-18:** The fork is one commit: the new note plus a `forked-from` edge from it to the passage anchor (2.1) of turn k in the original. The line is drawn from that turn inside the original card and clamps to the card's top or bottom edge when turn k is scrolled out of view. Forks of forks work the same way.
- **D-19:** The original never knows: its engine session, file and ability to keep messaging are untouched. You can fork at any completed turn even while the original is mid-reply; the in-progress turn is not a fork point.
- **D-20:** The fork gets its own engine session, started by replaying turns 1..k from the recorded transcript (tool calls as their one-line summaries) as its first context. No CLI session-file internals, no `--fork-session`. `ChatEngine` gains `fork(atTurn)` so the panel doesn't care which engine runs.
- **D-21:** A fork is an event; the world is not rewound. The fork works against the tree and workspace as they are when it's made.

### Claude's Discretion

- The exact text encoding of a turn passage in the note (speaker marker, separators), as long as it reads plainly in `.tree` and each turn is one addressable passage.
- Plan split and wave order. A sensible order: session notes and per-session ChatService first, transcript passages next, then status and levels, edge arrows, and forks last.

Rank property and levels 4+, take focus, `placement.near`, MCP and terminal sessions as notes, world rewind with a fork (Phase 3), API-key engine (02.7-07).

- Hold the token per session in memory (re-issued each launch, as today). Write one config file per session: `<userData>/chat/<16 hex of tree id>-<nK>.mcp.json` (0600, directory 0700). Replace `configTreeIds: Set<string>` with a set of session keys. `closeWorkspace(treeId)` must drop **every** session in that tree.

### Pattern 2: Session commits are written in main, never through `kernel:submit` (SC1, SC6)

**Facts:**
- `workspaceSubmitRefusal` refuses `createNode` and `deleteNode` in a workspace tree, and `setProperty`/`unsetProperty` only for `file.*` keys [VERIFIED: app/src/main/workspace/guards.ts:31-47]. Refusal text: `'Workspace windows hold files; Tapestry changes a file only through its window or the file tools.'` [guards.ts:17-18]. Undo and redo: `"Undo isn't available in a workspace window; the files are the record. Use git to undo a file change."` [guards.ts:20-21]. Wired at `index.ts:309-313`.
- `NoteCommands.createFrom` and `writeToNote` refuse any workspace tree: `` `${tree.name} is a workspace; its notes are files. Use write_file or edit_file` `` [VERIFIED: notes.ts:228-231, 264-265, 667-668]. The renderer's `createNote` refuses the same way (`App.tsx:575-581`), and delete refuses `tapestry.workspace/*` types (`App.tsx:885-892`).
- The mirror planner only indexes shape nodes (`isShapeNode`, `mirror/plan.ts:378-381`), so a non-workspace node in a workspace tree is never deleted by reconcile. The canvas already draws such nodes at top level and counts them in frame bounds (`Canvas.tsx:446-460`).
- `createEdge` accepts `props` in the native addon [VERIFIED: app/native/addon.cpp:279-300].
- `bridge.getNextIds()` predicts ids so one commit can hold a node and an edge that names it (`notes.ts:236-239, 316-340`).

**Pattern:** a new `SessionNotes` class in `main/chat/session-notes.ts` owns these four writes. Each resolves the workspace's `OpenTree`, calls `prepareWriteFor`, validates, calls `bridge.submitAs(actor, message, ops)`, then `hooks.onCommitted` (which sends `'tree-changed'`, `index.ts:387-390`).

| Write | Actor | Ops |
|------|-------|-----|
| create | `human user.<name>` (`getHumanActor`, `index.ts:297-303`) | `createNode tapestry.chat/session@1` with `title "New chat"`, `body ""`, `chat.turns 0`, `position.x/y` from the resolver, `width`/`height` (see Pitfall 6) |
| appendTurn | `plugin agent.<session agent>` [ASSUMED, see A2] | `setProperty body <whole transcript>`, `setProperty chat.turns <k>` |
| fork | human | `createNode` (body = turns 1..k, `chat.turns k`, title `<orig>, from turn k`) + `createEdge {from: next.node, to: original, label: 'forked-from', props: { turn: {type:'int', value:k} }}` |
| delete | human | `deleteNode` (edges cascade: `delete-node` "Removes a live node and every edge touching it", FORMAT.md:348) |

Add IPC channels `chat:create`, `chat:fork` and `chat:delete`. Route the renderer's delete path (`App.tsx:885-910`) to `chat:delete` for session-typed nodes. Otherwise it hits `WORKSPACE_SUBMIT_REFUSAL`. Title rename, move and resize still go through `kernel:submit`, which the guard allows.

### Pattern 3: Transcript grammar in the note body (SC2, D-07, D-08)

**Facts:**
- Native notes store the body as ProseMirror doc JSON (`plainTextToDocJson`, `notes.ts:97-104`). `docJsonToPlainText` returns non-JSON bodies unchanged (`notes.ts:132-142`), so `read_note` and `search_notes` read a plain-text body as-is.
- `.tree` writes text longer than 80 bytes, or text containing a newline, as a `<<TEXT` block, verbatim [VERIFIED: tapestry/docs/tree/FORMAT.md:464-471]. Limits: "A record body is at most 64 MiB … a line is at most 1 MiB" [FORMAT.md:653-655]. Property key: `[A-Za-z_][A-Za-z0-9_.:-]*` [FORMAT.md:437-440].
- The thread precedent (FORMAT.md:366-424): a plugin's own grammar lives inside one `text` value, and `body` stays a plain readable text.
- 2.1 passage anchors are a ProseMirror mark `passage` with attr `anchorId` [VERIFIED: renderer/editor/schema.ts:29-48]. The flow that would connect an anchor to an edge was never wired: "the passage-connection flow that would call them is not wired yet (see CR-03 in the review)" [VERIFIED: NoteCard.tsx:206-207; 02.1-REVIEW.md:92-103]. No code reads an anchor from an edge today.

**Recommendation (discretion: encoding).** Use a plain-text body (not ProseMirror JSON) in a line grammar where column 0 is structure and content is indented. Every line then classifies on its own, with no ambiguity, and the body still reads like a chat log in `.tree`:

```text
Turn 1
You: How do I add a test for the parser?
Tool: read_file src/parser.ts — done
Claude: Add it next to the feature. Here is the shape:
  describe('parser', () => { … })
Tool: write_file src/parser.test.ts — done
Claude: Done. Run npm test.

Turn 2
Note: Shell access is on for this chat — not sandboxed. …
You: Now run it
Error: Claude Code stopped unexpectedly (exit code 3)
```

Rules for `src/shared/chat/transcript.ts`:
- Column-0 structural lines: `Turn <k>`, `You: …`, `Claude: …`, `Tool: <summary>`, `Note: …`, `Error: …`, `Stopped`. A continuation line of the preceding You/Claude/Note/Error item is written with a two-space indent. A blank line inside content is written empty. The encoder trims each item's trailing blank lines and emits exactly one blank line before `Turn k` (k > 1), so the parser drops a block's trailing blank lines.
- **The turn header is the passage anchor.** Turn k is addressable as the k-th `Turn` block. It stays stable because the body is append-only and only main writes it (A-09, and Pitfall 8 for the guard).
- `Tool:` lines reuse `ChatPanel.tsx`'s `ToolRow` string (`shortToolName` + path argument + `— done` / `— refused: <first line>`, `ChatPanel.tsx:42-80`). Move that function into the shared module. Payloads are never written (D-08). **Exclude `set_status` calls** from the transcript (D-10: status is not history).
- Store `chat.turns int <k>` next to `body` in every turn commit. The renderer knows how many turns are committed without parsing, and the fork validates k against it.
- Round-trip test: `parse(encode(turns)) === turns` for adversarial content (lines beginning `Turn 3`, `You: `, `Tool: `, two spaces, `\r\n`, emoji, 100k-character messages, empty reply).

Why not per-turn property keys (`chat.turn.3`)? They would avoid rewriting the whole body each turn (Pitfall 7), but `body` would then not hold the conversation, which contradicts D-07's "appended to the session note's text". `read_note` and `search_notes` would also see an empty note. This is recorded as an open question, not adopted.

### Pattern 4: One commit per completed turn, ordered so nothing jumps (SC2)

**Facts:**
- `ChatService.onEngineEvent` delays a shell-on turn's `done` until the workspace catch-up finishes (`chat-service.ts:390-398`).
- The renderer's `busyAfter` treats `user` as busy and `done` as idle (`state/chat.ts:200-204`). The service keeps at most `MAX_TRANSCRIPT_EVENTS = 2000` events in memory (`chat-service.ts:53`), and a relaunch loses them.

**Pattern:** ChatService accumulates the current turn's events (from its `user` event through `done`). On `done`: (1) run the shell catch-up, if the turn had the shell on; (2) `SessionNotes.appendTurn` with the passage built from those events; (3) record and emit `done`. Keep only the **live turn** in memory: `open()` returns `{ committedTurns, liveTurn: { turn, events } | null, busy, lastStatus, allowShell }`. The renderer draws the body's parsed turns plus the overlay, and drops the overlay once the refreshed node's `chat.turns ≥ liveTurn.turn`. Keying on the turn count, not on `done`, avoids a double or missing turn while `refreshTree` (async IPC) is still in flight.

For failed or stopped turns, write the passage with an `Error: <message>` or `Stopped` line (UI-SPEC A-13), so the document stays honest. Record the person's own text as `You:`. Never record a fork replay preamble (Pattern 9) or a session-lost resend twice. Notices that arrive between turns (shell on/off) attach as `Note:` lines at the top of the next turn. Drop the resumed and session-lost notices: the note now shows the history, so `RESUMED_NOTICE`'s "earlier messages aren't shown here" is false.

### Pattern 5: `set_status` as the 21st bridge tool (SC4, D-13)

**Facts:**
- `TOOL_DEFINITIONS` is the table the shim advertises and main re-validates. Every schema is `.strict()` and has no actor field [VERIFIED: mcp/schemas.ts:9-13, 243-363].
- `runAgentTool(commands, actor, tool, args)` looks the tool up, runs `safeParse`, then switches on the name [VERIFIED: commands/agent-tools.ts:63-190]. The socket server calls it with `agentActor(name)`, where the name comes from the verified token (`index.ts:437-441`).
- `shim.test.ts:180-214` asserts **exactly** the sorted tool list ("so a tool added later has to be a deliberate decision"). It must gain `set_status`.

**Pattern:**
```typescript
// mcp/schemas.ts. Values below are recommendations, not existing code.
export const SetStatusArgs = z
  .object({
    text: z.string().min(1).max(120),      // "a few words"; one line enforced in main (reject \n)
    needs: z.boolean().optional(),
    level: z.number().int().min(0).max(100).optional(), // accepted, then clamped to STATUS_LEVEL_CEILING
  })
  .strict()
// definition: name 'set_status', annotations { readOnlyHint: true }  (it writes nothing to any tree)
```
- `AgentCommands` gains `chat?: { setStatus(actor: Actor, args): CommandResult<{ shown: true }> }`. `ChatService.setStatus(agentName, args)` finds the session whose derived agent name matches. For any other agent it refuses: `set_status is only available to Tapestry's in-app chats`. External MCP agents can see the tool but cannot raise the attention UI.
- It emits a **service-level** event `{ type: 'status'; text: string; needs: boolean; level: 0|1|2|3 }` on `'chat-event'` and never calls `submitAs` (D-10). Store the text as the session's `lastStatus` (in memory and in chats.json v2) for D-12.
- `ChatEvent` is duplicated by hand in `renderer/global.d.ts:356-390` (`TapestryChatEvent`) and in `preload/index.ts:11-20`. Update all three (Pitfall 10).
- Add a line to `chatSystemPrompt` (`claude-cli.ts:408-414`) telling the model to call `set_status` with a few words, and with `needs: true` when it asks the person something. The prompt is fixed per session: "It stays constant, since `--system-prompt-snapshot` reuses the first one on every resume" (`claude-cli.ts:403-407`). Sessions resumed from the 02.7 prompt will not know the tool.

### Pattern 6: One renderer store for card and panel (SC3, D-04)

**Facts:** `useChat(treeId)` holds events in component state and subscribes to `onChatEvent` per hook instance (`state/chat.ts:225-307`). The card and the panel would each keep their own copy of that state, which is the "second store" D-04 forbids.

**Pattern:** a module-level store (`state/chat-sessions.ts`) keyed `` `${treeId}:${noteId}` ``, read through `useSyncExternalStore`, with **one** `window.tapestry.onChatEvent` subscription installed from `App`. It holds the live-turn events, the status reducer's state, the shared draft (UI-SPEC: "One draft per session, shared by both"), and fork mode. Keep `foldChatEvents` (`state/chat.ts:135-197`) as the live-turn folder. `ChatPanelState` changes from `{ treeId }` to `{ treeId, noteId }`. "Back to card" no longer calls `chat.stop` (today `closeChat` stops the turn, `App.tsx:177-180`; UI-SPEC A-12 changes that).

### Pattern 7: Status reducer (SC4, D-11..D-15), pure and in `src/shared/chat/session-status.ts`

Inputs: `user`, engine events, `status` events, and person actions (`ack`, `replied`, `stopped`). Output: `{ state: 'idle'|'working'|'needs'|'done'|'failed', text, level, arrivedAt }`, plus `shouldAnimate(level, threshold)`. Rules, straight from D-11..D-15 and the UI-SPEC tables:
- `user` → working ("Reading your message"). `tool-call` → text = tool summary. `text` → text = first line, unless a `set_status` text arrived this turn (set_status wins).
- `status{needs:true}` or level 3 → needs (level 3). It persists through `done`, hover and open. Only `replied` (a send at the last turn) clears it. A fork does **not** clear it on the original (D-19).
- `done{ok:true}` → done at the turn's last set_status level, else 2. `error` or `done{ok:false}` → failed, never animated. A `done` whose `reason` is `'stopped'` → idle with text "Stopped" (`stopWith('stopped')` emits `{ type: 'done', ok: false, reason }`, `claude-cli-engine.ts:249-256`).
- `ack` (pointer rests 1000 ms, focus, enlarge, send) turns done/failed into idle and keeps the text.
- Initial state after load = idle with `lastStatus` from main, or working if main says `busy`. That gives D-12 and no stale Working.

### Pattern 8: Edge arrows (SC5, D-16)

**Facts:**
- `worldToScreen(cam, wx, wy)` handles roll [VERIFIED: camera.ts:108-111]. `centerOn(cam, wx, wy, viewportW, viewportH)` [camera.ts:219-229].
- The Canvas holds the drawn camera in `const [view, setView] = useState<Camera>(IDENTITY_CAMERA)` [Canvas.tsx:296], per-tree `frameRects` [Canvas.tsx:423-480], measured card dims in `nodeDimsRef`, and `viewportRef` [Canvas.tsx:294].
- `panToFrame` eases through `rig.easeTo((c) => centerOn(...), FLY_TAU_MS)` [Canvas.tsx:496-511]. `panToNote` uses `setView` with `panX = clientWidth / 2 - cx * prev.zoom`, which **ignores roll** [Canvas.tsx:516-538].
- `flyTo` in `threads/navigation.ts:49-94` animates **thread time** (centerSeconds/spanSeconds), not the 2D camera. The UI-SPEC motion table names it for the arrow pan. Use the CameraRig instead.

**Pattern:** a pure `edge-arrows.ts`: `cardOffscreen(corners: Point[], viewport)` checks all four `worldToScreen` corners of `(tree.frame.x + local.x, tree.frame.y + local.y, w, h)` (the same world convention as `panToNote`). `arrowSpot(centre, viewport, insets)` is the ray from the viewport centre to the card centre, clipped to the inset rectangle: 16 px sides and bottom, 64 px top, right inset 452 px when the ChatPanel is open. `spreadOnEdge(spots, 40)` keeps centres at least 40 px apart. Render `EdgeArrowLayer` as a screen-space sibling of the transformed canvas layer, inside Canvas where `view` lives. The click pans with `rig.easeTo(c => centerOn(c, cx, cy, w, h), FLY_TAU_MS)`, or `rig.direct` under reduced motion.

Stack raise: TreeFrame draws cards in DOM order sorted by `depthOrder` [TreeFrame.tsx:505-506, 748-751]. Add a per-tree renderer list `raised: string[]` (the `raiseWindow` rule, `surface-windows.ts:159-167`) as a secondary sort key.

### Pattern 9: Fork (SC6, D-17..D-21)

**Facts:**
- `ChatStartOptions { cwd: string; resumeSessionId?: string }` [VERIFIED: engine.ts:47-52]. `ChatEngine` has `start`, `send`, `onEvent`, `busy`, `stop`, `setAllowShell?`, `dispose`, `killNow?` [engine.ts:54-91].
- The CLI engine spawns lazily. `send` writes `userMessageLine(text)` to stdin [claude-cli-engine.ts:150-174]. `buildClaudeArgs` uses `--resume <id>` when continuing and `--session-id <uuid>` for a new session [claude-cli.ts:119].
- `resolveWhere(world, subject, where)` with `WherePlacement = { near: string } | { beyond: string; from: string }` [VERIFIED: placement.ts:522, 565]. `beyond` is fixed. `near` follows only when the anchor is the subject's own grew-from parent [placement.ts:618-647].
- In a workspace tree, `place` resolves in frame coordinates through `inFrameCoordinates` and writes back through `toLocalPosition` [spatial.ts:108-122, 420-437].

**Engine seam (recommended signature, discretion):**
```typescript
// engine.ts: RecordedTurn comes from src/shared/chat/transcript.ts
export interface ChatEngine {
  // …existing members…
  /**
   * Make this new, not-yet-sent engine begin where turn `atTurn` of `recorded`
   * ended (D-20). The CLI engine replays turns 1..atTurn as text in its first
   * message; an API engine would build its message list from them.
   */
  fork(atTurn: number, recorded: readonly RecordedTurn[]): void
}
```
The method takes the recorded turns because after a relaunch the original has no live engine and its in-memory events are gone. The recorded `.tree` transcript is the only source that always exists, which is also what D-20 names. `ClaudeCliEngine.fork` stores a preamble. The first `send(text)` writes `userMessageLine(preamble + text)`, with `--session-id <new uuid>`. `ChatService` records `{type:'user', text}` with the person's text only.

**Service flow (`chat:fork(treeId, noteId, k, text)`):**
1. Validate `1 ≤ k ≤ committedTurns(original)`. The in-progress turn is never committed, so it can never be chosen (D-19). The original's `busy` doesn't matter.
2. Placement: if the original has a `forked-from` edge, use `{ beyond: original, from: <its forked-from target> }` so forks fan outward. Otherwise use `{ near: original }` (a root session has no parent; see Open Question 2). Resolve on `inFrameCoordinates` nodes with the fork's stored size in the subject props.
3. One commit as the human: `createNode` + `createEdge forked-from {turn: int k}` (`getNextIds` for the edge's `from`). Verify `result.nodeIds[0] === next.node`, as `createFrom` does (`notes.ts:343-351`).
4. `issueToken(fork agent)`, a new engine through the factory, `engine.fork(k, parseTranscript(original.body).slice(0, k))`, then send `text`. The original's engine, chats.json entry and note are never touched.

Readable result in `.tree` (grammar per FORMAT.md:347):
```text
create-node n57 tapestry.chat/session@1
set n57 body text <<TEXT
Turn 1
You: …
TEXT
set n57 chat.turns int 2
…
create-edge e31 n57 n42 forked-from
set e31 turn int 2
```

### Anti-Patterns to Avoid
- **Creating sessions through `kernel:submit`:** the workspace guard refuses it (Pattern 2).
- **Using `NoteCommands.createFrom`/`updateNote` for sessions:** both refuse workspace trees. Session notes also have no grew-from parent.
- **Storing the transcript as ProseMirror JSON with passage marks:** it is unreadable in `.tree`, depends on a 2.1 flow that was never wired, and the card renders read-only anyway (A-09).
- **Child notes or `inside` refs for turns:** forbidden by D-07.
- **Persisting `state` (working/done) anywhere:** only the status *text* may be remembered (D-12).
- **Writing card size to `width`/`height` on resize:** view state only (D-05, UI-SPEC § Session card anatomy).
- **A second `useChat` store for the panel:** breaks D-04.

## Common Pitfalls

### Pitfall 1: Workspace guard and missing undo
**What goes wrong:** creating or deleting a session from the renderer fails with `WORKSPACE_SUBMIT_REFUSAL`. The UI-SPEC's "Delete chat … in one commit that one undo restores" cannot happen, because replay is refused in workspace trees (`guards.ts:20-21`, `App.tsx:1124-1130`).
**How to avoid:** use the main-side `chat:create`/`chat:delete`/`chat:fork` channels. Change the delete dialog copy to not promise undo. It already says "The conversation stays in history", which remains true.
**Warning signs:** a notice "Workspace windows hold files…" after clicking New chat.

### Pitfall 2: The "D-05 per-agent edit gate" is not in force
**What goes wrong:** the plan tries to guarantee "sessions can't edit each other's notes" and either finds no mechanism or re-adds the removed 02.2 gate. That would contradict 02.4.
**Why it happens:** `export const AGENT_NOTES_OPEN_TO_AGENTS = true` [VERIFIED: locks.ts:74] ("a note an agent created starts open to every agent", locks.ts:67-74). Workspace files are open to every agent unless explicitly locked (locks.ts:114-133). 02.7-CONTEXT's D-05 is about file-versus-edit conflicts, not identity. STATE.md records "02.4-01: … 02.2 D-05 authorship gate removed".
**How to avoid:** per-session identity delivers attribution, colour and lock *ownership* only. Session transcripts are still protected, because no agent note tool writes to a workspace tree (`notes.ts:228-231`) and `set_status` writes nothing. Record this in the plan's must-haves instead of adding a gate.

### Pitfall 3: The turn passage is recorded from the wrong text
**What goes wrong:** the fork preamble, the attachment context or the session-lost resend appears as "You:" or appears twice. Or `set_status` calls show up as `Tool:` lines, which puts status into history.
**How to avoid:** build the passage from the service's per-turn event list, using the person's text from `send`. Filter `set_status` tool calls. The attachment line is part of what the person sent (`composeFirstMessage`, `state/chat.ts:83-85`), so keeping it is honest.

### Pitfall 4: Stale Working
**What goes wrong:** a persisted `state` or a missed `done` leaves a card blurred after relaunch or renderer reload.
**How to avoid:** never persist state. On mount, read `busy` from `chat:open` (main is the truth: `(chat.engine?.busy ?? false) || chat.settling !== null`, `chat-service.ts:169`). A relaunch has no engines, so everything starts Idle with `lastStatus`. `killNow` emits no `done` (`claude-cli-engine.ts:203-212`), but it only runs at quit.

### Pitfall 5: Many live `claude` processes
**What goes wrong:** each session's CLI process stays alive after its turn (one long-lived process per chat, `claude-cli-engine.ts:5-8`), so ten sessions leave ten `claude` processes and ten MCP shims running.
**How to avoid:** cap live idle processes (for example, end the least-recently-used idle engine's process quietly when a fifth would start; the next send resumes by `--resume`). The number is Claude's discretion; see Open Question 3. `stopAll` and `killAllNow` must iterate over sessions.

### Pitfall 6: Placement uses stored sizes, and the card size is view state
**What goes wrong:** `noteSize` falls back to `DEFAULT_NOTE_WIDTH = 280` and `DEFAULT_NOTE_HEIGHT = 120` [VERIFIED: placement.ts:35, 42, 159-166], but the session card draws at 360 × 440 (UI-SPEC A-02). Forks and `look` then overlap the original on screen.
**How to avoid:** write `width 360` and `height 440` as real properties once at creation (the "note size" D-05 says the card keeps). Resizing still changes only view state. See Assumption A3.

### Pitfall 7: Quadratic `.tree` growth
**What goes wrong:** every turn rewrites the whole `body`, so an n-turn session adds about n²/2 turn-sizes to the journal. With 4 KB turns, 50 turns add about 5 MB and 200 turns about 80 MB, all replayed on open.
**How to avoid (this phase):** accept it under D-07, measure it in a test (bytes added per turn), and write it into the phase summary. A later option is per-turn keys (Open Question 1). Session trees live in `<userData>/workspaces`, not in the person's folder.

### Pitfall 8: The renderer can still overwrite `body`
**What goes wrong:** the guard only refuses `file.*` keys, so any renderer code that saves a body through `kernel:submit` (for example if NoteCard ever renders a session) could rewrite a transcript and break fork anchors.
**How to avoid:** render sessions only with the session card (read-only, A-09). As hardening, extend `beforeSubmit` for workspace trees to refuse `body`/`chat.*` on nodes of type `tapestry.chat/session@1`. This needs a node lookup. `beforeSubmit` has `treeId`, so resolve through the registry.

### Pitfall 9: Input leaking to the canvas
**What goes wrong:** Delete or Backspace typed in the card composer deletes the note, and wheel scrolling in the transcript pans the canvas.
**How to avoid:** copy `PanelShell`'s handlers (`ChatPanel.tsx:91-125`): `stopPropagation` on keydown, pointerdown, dblclick and contextmenu, and a passive wheel listener that stops propagation unless `ctrlKey` is held.

### Pitfall 10: The duplicated event types drift
**What goes wrong:** `ChatEvent` gains `status` in `engine.ts`, but `TapestryChatEvent` in `renderer/global.d.ts:369-379` and `ChatOpenState` in `preload/index.ts:17-20` do not. Typecheck passes in one project and the renderer silently ignores status.
**How to avoid:** update all three in the same task, and run `npm --prefix app run typecheck` (it checks both tsconfigs).

### Pitfall 11: Off-screen test under roll, and `flyTo`
**What goes wrong:** testing only the card's top-left corner, or using `panToNote` (roll-blind) or `threads/navigation.ts` `flyTo` (thread time, not the 2D camera).
**How to avoid:** test all four corners through `worldToScreen`, and pan with `rig.easeTo(centerOn)`.

### Pitfall 12: Fork placement in a workspace tree
**What goes wrong:** calling `resolveWhere` on raw `bridge.getNodes()` treats folder-local file-card positions as frame positions, so obstacles land in the wrong place.
**How to avoid:** run nodes through `inFrameCoordinates` first (export it from `spatial.ts`), and convert back with `toLocalPosition`. For a top-level session the local spot equals the frame spot.

### Pitfall 13: The fork replay is too large for the context window
**What goes wrong:** forking a very long session sends a preamble bigger than the model's context, and the first turn fails with `crashed`.
**How to avoid:** cap the replay (for example, keep the last N characters of turns 1..k with an "earlier turns omitted" line). Test the cap as a pure function. The spec says very long sessions fall to CLI auto-compaction, but a single oversized first message is not compacted [ASSUMED].

### Pitfall 14: Existing tests assume one chat per workspace
**What goes wrong:** all 28 `chat-engine.test.ts` cases call `chat.send(treeId, …)` and `chat.open(treeId)`. The re-key breaks them wholesale.
**How to avoid:** in the re-key plan, migrate the harness first (`startHarness` creates one session note), then the cases. Keep every behaviour assertion.

## Open Questions

1. **Quadratic journal growth (Pitfall 7).**
   - What we know: D-07 puts the whole transcript in the note's text, and each turn rewrites it.
   - What's unclear: whether Kaelen would accept per-turn keys (`chat.turn.<k>`, with `body` as a periodic checkpoint as threads do), which keep one commit per turn at O(n).
   - Recommendation: ship the body rewrite, measure the growth in a test, and put the question in `autonomy/REVIEW.md`.
2. **What "beyond the original, from its parent" means for a root session.**
   - Recommendation: A7. Also record it for review.
3. **How many live `claude` processes to allow.**
   - Recommendation: start with a small cap and end idle processes least-recently-used first. It is invisible to the person except for a resume on the next send.
4. **Quitting mid-turn loses the person's message**, because no `done` arrives, so there is no turn commit.
   - Recommendation: accept it this phase (D-12 only promises Idle). Optionally commit a `Stopped` passage from `disposeAll` when it can be awaited.
5. **The legacy 02.7 conversation per workspace.**
   - Recommendation: A5, leave it. A "Continue earlier chat" affordance is out of scope.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (agent tokens) | `AgentRegistry.issueToken`/`verify` (sha256 + `timingSafeEqual`); one token per session, rotated each launch |
| V3 Session Management | yes (CLI session ids, MCP config files) | 0600 files under a 0700 dir, deleted on session delete, workspace close and quit; tokens never in argv, env, logs or the renderer (`chat-service.ts:8-12`) |
| V4 Access Control | yes | The actor comes from the token only; `set_status` is refused for non-chat agents; renderer IPC validates `treeId` (`TREE_ID_PATTERN`) and `noteId` (`NODE_ID_RE` + node type check in that tree); session writes are main-only |
| V5 Input Validation | yes | zod `.strict()` `SetStatusArgs`; message ≤ `MAX_MESSAGE_CHARS = 100_000` (`chat-service.ts:52`); fork `k` checked against `chat.turns`; title length ≤ 200 |
| V6 Cryptography | no new use | Reuse `randomBytes` in the registry; never hand-roll |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| One session's agent claims another's status | Spoofing | The name comes from the socket token; `set_status` has no session argument |
| An external MCP agent raises "Needs you" or edge arrows | Spoofing / Elevation | `setStatus` refuses names not matching a live session |
| The renderer overwrites a transcript `body` through `kernel:submit` | Tampering | Session card is read-only; guard hardening in Pitfall 8 |
| A crafted `noteId` spawns an engine or agent for a file note | Elevation | Validate type `tapestry.chat/session@1` in that tree before `ensureEngine` |
| Prompt injection through a replayed transcript | Tampering | The replay holds only the recorded conversation and one-line tool summaries, framed as history in the preamble; tool results are never replayed |
| `set_status` spam or many sessions exhausting processes | DoS | Text length cap; coalesce in the renderer; live-process cap (Pitfall 5) |
| Token leakage through many config files | Information disclosure | Files are 0600 and deleted on every exit path; covered by the existing test pattern "keeps the token in a 0600 config file that is deleted when the workspace closes" |
