<objective>
Status, main and shared half: the `set_status` tool end to end, and the one pure reducer that turns observed events into a session's state, status text and level, with the last status text kept across a relaunch. Nothing here enters the tree.

Purpose: SC4 and D-10..D-14. 02.8-05 draws these states on the card and in the panel; 02.8-06 decides what animates. The split keeps each plan inside its context budget (plan checker, iteration 1).

Output:
- the `set_status` tool end to end (schema, dispatch, ChatService, the event, the fake's `status` scenario, the shim's 21-tool list);
- the pure reducer in `src/shared/chat/session-status.ts`, with its tests;
- `lastStatus` kept in chats.json v2 and returned by chat:open;
- the system prompt line.

Recorded choices:
- **`set_status` is a bridge tool** in `TOOL_DEFINITIONS` (annotations `readOnlyHint: true`, since it writes no tree). External agents see it in tools/list but are refused. Rated **costly**: it is a published MCP contract that models learn from the system prompt.
- **The `status` event is service-level.** It joins `ChatEvent` in engine.ts, documented as never emitted by an engine, and main records it into the open turn's live events so the renderer's reducer sees it in order. `turnItemsFromEvents` ignores it, and set_status tool calls are already left out (D-10).
- **Needs you clears on the `user` event** of that session. Only a person's send in that session produces one; a fork sends in the fork's own session, so the original keeps its "!" (D-19).
- **The last status text** is the reducer's text after the turn's events (`statusTextAfterTurn`), computed in main at each turn commit and at `set_status`, and stored in chats.json v2 `sessions[key].lastStatus`. That is chrome outside the tree (D-10, D-12).
- **Sessions resumed from a 02.7-era or 02.8-01-era prompt will not know the tool**, because `--system-prompt-snapshot` reuses the first prompt. The status falls back to tool and reply text (D-13).
</objective>
