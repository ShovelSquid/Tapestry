# Phase 2.6 Plan 07: An unreadable settings.json is never written over Summary

**settings.json is now read in three states (missing, unreadable, ok). Every writer throws `SettingsUnreadableError` on an unreadable file and leaves its bytes alone. Launch cases A, B and C return `setup-failed` before creating or opening anything, so a hand edit with one trailing comma no longer costs the `trees` backup or the user name.**

## Accomplishments
- Closed CR-01 / verification gap 1. The pointer write, `setUserName` and the agents switch cannot replace a settings.json that exists but does not parse as a JSON object. All four `missing` items in gap 1 are implemented and tested.
- First launch (case A) over a broken file writes nothing, creates no space files, and says why in the window. The approved `setup-failed` sentence now carries the file path and the parse error, and ends "Nothing in settings.json was changed." Fixing the file lets the next launch import as usual.
- Cases B and C stop before `TapestryHome.open`, `ForestStore.open` or `TapestryHome.createReferencing` runs, and every existing file keeps its bytes.
- A missing, empty or whitespace-only file still takes the pointer write as before.
- Review IN-03 is fixed: the `AppSettings.version` doc now says "Raised only to 2, by the pointer write; never lowered."

## Decisions Made
- **Empty or whitespace-only counts as missing** (Claude's discretion, as the plan allowed). Nothing is in such a file to lose, and first launch keeps working.
- **How a refusal reaches the person (index.ts unchanged):**
  - `settings:setUserName` already wraps the call in try/catch and returns `{ ok: false, error }`. The name prompt shows the `SettingsUnreadableError` message, which names the file and says it was left untouched.
  - `agents:setEnabled` calls `settings.update` without a try/catch, so its IPC call now rejects and the toggle keeps its old value. Before this plan it overwrote the file.
- **Spies prove the B/C early stop.** Opening a tree takes an OS journal lock and leaves no file behind, so "nothing was opened" can't be seen on disk. The tests spy on the static `open` and `createReferencing` methods instead. The byte-identity and existence checks still come from the files themselves.
