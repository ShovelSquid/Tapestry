# Phase 2.6 Plan 04: Membership and Identity by Header Digest Summary

**Which trees are in the space is now recorded in the forest. Opening, creating or adding a vault tree writes its stand-in and placement in one commit signed by the person, and the system then records the tree's digest once. Closing a tree deletes its stand-in in one commit signed by the person, so its last frame stays in history. A member is its digest. A moved file keeps its frame when the person opens it from its new path. A copy is refused. A different world at a member's path is listed as unavailable and never adopted. Duplicate stand-ins are folded in one system commit that names both, and Tapestry's own files cannot be added. No open, create, close or vault handler writes the settings `trees` list any more.**

## Accomplishments

- **`ForestStore`**
  - `addMember` writes one commit holding the stand-in (kind, path hint, and for a vault the vault root hint; no digest) and its `placement` edge, typed `real`. The stand-in id is predicted and then checked.
  - `removeMember` is one `delete-node`, and the kernel removes the placement edge with it.
  - `writeMemberFacts` sets text facts and deletes stand-ins in one commit. It throws when there is nothing to write.
- **`SpaceService`**
  - `memberFor` is the single join rule used by `list`, `moveFrames` and membership: by digest, then by path for a stand-in without a digest, and by path for an unavailable entry.
  - `requireReady` throws the approved 4.9 wording.
  - `addMember` works through these cases:
    - A tree already recorded at the same path keeps its frame. Only a missing digest is filled in.
    - A stand-in with the same digest at a stale path is reused. Its hint is updated in the person's commit, and the stale `path:` record is dropped.
    - Otherwise a new stand-in goes at the rightmost x + 480 + 64, at that frame's y. The two numbers are named constants with the renderer-bundle comment.
  - `recordIdentity` and the private `settleIdentity` write the digest once, signed `system tapestry`. When another stand-in already carries that digest, they fold into it instead (Pitfall 10, case 2).
  - `removeMember` resolves through the registry entry, so it runs before `registry.close`.
  - Restore:
    - It is fold-safe: each stand-in's facts are read again just before it opens, deleted stand-ins are skipped, and so are worlds already open.
    - Stand-ins with a digest open with `expect { id, reason: 4.11 }`.
    - A `TreeIdentityClash` on a stand-in without a digest folds it away in one system commit (Pitfall 10, case 1).
  - `setReserved` is called with both files' paths and digests and the 4.10 wording. `close()` clears it.
  - `reopenMember` records identity on success. On a clash it folds the duplicate and rethrows.
  - `relocateMember` makes one human commit that updates the path hint and vault root hint. It writes nothing if neither changed.
- **`index.ts`**
  - `openIntoSpace` does the following, in order:
    1. It resolves `getHumanActor()` first.
    2. It returns 4.9 when the space is not ready.
    3. It opens the tree, then calls `space.addMember`.
    4. If recording fails, it closes a tree that this call opened.
  - `trees:open`, `trees:create` and `vault:add` use it.
  - `trees:close` calls `space.removeMember` before `registry.close`.
  - `trees:reopen` calls `space.reopenMember`.
  - `placeNewFrameFromSettings`, `rememberTree`, every `settings.addTree`/`removeTree` call and the `TreeFrameSetting` import are gone. Only `trees:setFrame` still writes settings, until Plan 05.

## vault:locate and vault restore

- **`vault:locate` did not exist on this branch after the merge,** because 2.2 Plan 08 has not landed. So no handler was converted. `SpaceService.relocateMember(treeId, treePath, vaultRoot, actor)` is built and tested so that it is ready for it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Case A's commit count in `space-service.test.ts`**
- **Found during:** Task 1
- **Issue:** The Plan 02 test asserted that a first launch leaves exactly 1 forest commit. Recording the digest on first open (this plan's D-03 behaviour) adds one system commit per opened member.
- **Fix:** The test now expects 3: the import, then `record identity of "alpha"` and `record identity of "beta"`, in that order.
- **Files modified:** `app/src/main/space/space-service.test.ts`
- **Commit:** `8b85ae5`

**2. [Rule 2 - Missing critical] Reserve before restoring, not only at the end of `start()`**
- **Found during:** Task 2
- **Issue:** The plan says to call `setReserved` "at the end of a successful start()". A hand-edited forest whose stand-in names `Forest.tree` would then be tried during restore. It would be reported as `locked` against our own lock, which is the untrue message Pitfall 4 exists to prevent.
- **Fix:** `setReserved` runs once the forest and Tapestry tree are open, before restore. The restore loop catches and logs the refusal.
- **Files modified:** `app/src/main/space/space-service.ts`
- **Commit:** `b73ec11`

**3. [Rule 2 - Missing critical] `restoreVault` requests carry `expect`**
- **Found during:** Task 2
- **Issue:** Native members open with the recorded digest, but the vault hook's request had no way to pass it on. When 2.2 Plan 08 wires the hook, it could adopt a different world at a vault member's path (T-2.6-13).
- **Fix:** Added an optional `expect` to the request. After the hook runs, the service records identity only when the opened digest matches. The membership vault test asserts that the hook receives it.
- **Files modified:** `app/src/main/space/space-service.ts`, `app/src/main/space/membership.test.ts`
- **Commit:** `b73ec11`

**4. [Scope note] `addMember` on a recorded open tree records a missing digest**
- The plan says to return `{ committed: false }`. The service still returns that when the digest is already present, which is the tested case. When the stand-in has no digest yet (the tree failed to open at launch and was then opened with Open tree), it writes the one system identity commit. Otherwise the identity would stay unrecorded until the next launch.

**5. [Scope note] Relocate and a moved file share the add message.** See Decisions.
