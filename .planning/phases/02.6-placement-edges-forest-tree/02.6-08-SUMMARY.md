# Phase 02.6 Plan 08: One-to-one Registry/Forest Join Summary

**Every successful open now clears the unavailable records for its path and its own id. Unavailable records for known members are keyed by their header digest instead of by path, and `removeMember` refuses to delete a stand-in that another live entry still joins. This closes CR-02 (a stale "missing" frame deleting a live world's stand-in) and WR-01 (a different world at a member's path hiding that member for good).**

## Accomplishments

- **Gap 2 (CR-02, SC-4):** `TreeRegistry.adopt()` now deletes `path:<target>` and the adopted id from the unavailable map before emitting. Create New World at a missing member's path leaves exactly one frame on one stand-in, and the move commits. The world is restored at its moved frame after a relaunch.
- **Defence in depth:** `SpaceService.removeMember` writes nothing when another `registry.summary()` entry joins the same stand-in.
- **Gap 3 (WR-01, SC-5):** `recordUnavailable` uses `opts.expect.id` when a digest is expected. `tryOpen` honours `expect` when the path is already open, and throws `TreeIdentityClash` when the expected id is open elsewhere. After Open tree on a path that holds a different world, both members are listed. They are still both listed on every later launch, and each live stand-in is listed exactly once.
- `memberFor` now uses three explicit one-to-one rules. `dropStaleRecord`, a path-only lookup that could close another member's record, is removed.
- 02.6-04-SUMMARY claimed that member D "reappears as unavailable after relaunch". That claim is now true and tested, including after the person opens the new world at D's path.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Correctness] tryOpen checks for a clash before recording the open-path mismatch**
- **Found during:** Task 2
- **Issue:** The plan listed step 1 (a different world open at the path: record the expected member as unavailable) before step 2 (the expected id is open elsewhere: throw). In that order, if both are true, the id would be recorded as unavailable while it is open, which breaks T-2.6-35.
- **Fix:** Return the existing tree when it matches or when there is no `expect`. Next, throw the clash if the expected id is open. Only then record the mismatch. Both behaviours the plan describes are unchanged and tested.
- **Files modified:** app/src/main/trees/registry.ts
- **Commit:** a3fc55d

**2. [Cosmetic] The Task 1 commit uses the `fix(02.6-08)` type**
- It closes a review bug, so the executor's commit-type table gives `fix`. The orchestrator's note listed `feat/test/docs`. History was not rewritten.
