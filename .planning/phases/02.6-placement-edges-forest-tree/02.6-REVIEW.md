## Summary

This is an incremental re-review of `280d4e9..HEAD`: gap-closure plans 02.6-07 (unreadable settings.json), 02.6-08 (one-to-one registry/forest join), 02.6-09 (renderer close, growth push and fit) and 02.6-10 (add rollback). I read each diff and the code around it, and traced the calls into `VaultService.addVault`/`catchUp`, `KernelBridge.close`/`ensureLoaded`, `AgentsPanel` and the NoteCard resize path. The 176 tests in the eight listed test files pass.

To check one scenario I wrote a throwaway vitest script in `/tmp`. It used the real registry, the real addon and `openWithRollback`, and I deleted it afterwards. No source file was touched. The script reproduces WR-01 below.

Both prior critical findings are fixed, and so are WR-01, WR-03 and WR-05. The fixes are well tested. The remaining problems:

1. **WR-01 (new).** The WR-02 rollback closes every new registry entry that is not a member yet. That includes an entry another add has opened and not yet recorded. So one failed add can close a second vault add while its catch-up is still running.
2. **WR-02 (new).** The CR-01 guard makes `settings.update()` throw on an unreadable file, and `agents:setEnabled` does not catch it.
3. **WR-03 (new).** The CR-01 guard also makes case B a hard stop. On an ordinary relaunch, one typo in settings.json now leaves the whole space closed, even though nothing needs to be written to open it.
4. **WR-04 (still partly open from WR-04).** The renderer no longer arms frame undo for a growth push. Main still signs that push as the person's "move frame" and puts it on the frame-undo stack.

## Warnings

### WR-01: A failed add closes another add that is still in flight, so that add fails or returns ok with no registry entry

**File:** `app/src/main/space/open-into-space.ts:45-78`, `app/src/main/index.ts:525-546` (with `app/src/main/obsidian/vault-service.ts:94-113`)
**Issue:** `rollBack` closes every registry id that is not in this call's `before` snapshot and for which `isMember` is false. An add that another call started is exactly that kind of entry during the gap between the other call's `open()` and its `record`. For `vault:add`, that gap is the whole `catchUp` (`walkVault`, `buildVaultModel` and the commits), which can take seconds on a large vault. The file comment only considers "a concurrent add that succeeded". It does not cover one that has not reached `record` yet.

A realistic sequence: the person adds a large vault V2, and while it is reading they add vault V1, whose tree is locked or damaged. The sequence then runs as follows:
1. V2's `open()` has adopted V2 and is awaiting `catchUp`. V2 is not a member yet.
2. V1's `tryOpen` records `path:…/V1.tree`, and `requireOpen` throws.
3. V1's rollback sees both `path:…V1` and V2's id as new (neither is in V1's `before`) and not members. It closes both, which releases V2's bridge.
4. V2's `catchUp` continues on a bridge whose `instance` is null. The next bridge call throws `No kernel loaded — call create() or open() first` (`kernel-bridge.ts:444-447`), and V2's add fails with that message. If the close lands after catch-up's last bridge call, V2's `record` still runs. `addMember` then writes a stand-in for a tree the registry no longer holds, and the handler returns `{ ok: true, treeId }` for an id that `trees:list` does not contain. The mismatch is T-2.6-24 in the other direction.

I reproduced the second outcome with the real registry and addon. Add 1's `open` adopts and then fails, while add 2's `open` adopts and waits. Result: `add2 resolved ok; in registry? false recorded as member? true`. The new tests (`open-into-space.test.ts`) only cover an overlapping add that has already been recorded.
**Fix:** Scope the rollback to what this call introduced. The simplest option is to serialize the adds:
```ts
// index.ts
let addQueue: Promise<unknown> = Promise.resolve()
function openIntoSpace(open: () => TreeEntry | Promise<TreeEntry>) {
  const run = addQueue.then(() => openIntoSpaceNow(open))
  addQueue = run.catch(() => undefined)
  return run
}
```
Alternatively, have the registry report which entries each `open()` created. For example, `TreeRegistry` could expose an `onEntryAdded` listener that `openWithRollback` subscribes to only during its own synchronous `open()` segments. Or `VaultService.addVault` could attach the id it adopted to the error it throws. Then close only those ids. Add a test in which the overlapping add is still pending when the first add fails.

### WR-02: `agents:setEnabled` throws uncaught when settings.json is unreadable; the switch silently does nothing

**File:** `app/src/main/index.ts:437-454` (via `app/src/main/settings.ts:368-372, 389-391`)
**Issue:** Before 02.6-07, `settings.update()` wrote over an unparseable file and never threw for a parse error. It now throws `SettingsUnreadableError` from `writableBase()`. `agents:setEnabled` calls `settings.update(...)` with no `try`, so the `ipcMain.handle` promise rejects. The only caller, `AgentsPanel.handleToggleEnabled` (`AgentsPanel.tsx:98-101`), awaits it with no `catch`. The result is an unhandled rejection in the renderer, and `onRefresh()` never runs. The person clicks the switch and nothing happens, and nothing says that settings.json is the cause. `settings:setUserName` does catch this error (`index.ts:466-473`). This handler was missed when the throw was introduced.
**Fix:**
```ts
ipcMain.handle('agents:setEnabled', async (_event, enabled: unknown) => {
  if (typeof enabled !== 'boolean') return { ok: false, error: 'enabled must be true or false' }
  try {
    settings.update((current) => ({ ...current, agentsEnabled: enabled }))
  } catch (err) {
    return { ok: false, error: errorMessage(err) }
  }
  ...
})
```
Then have `AgentsPanel` show `result.error`.

### WR-03: A hand-edit typo in settings.json now leaves the whole space closed on an ordinary relaunch (case B)

**File:** `app/src/main/space/migrate.ts:339-361`, `app/src/main/settings.ts:28-33, 319-325`
**Issue:** When settings.json is unreadable, `getTapestryPointer()` returns null (`readObject()` → null). An existing install therefore classifies as `recover-home`, and `recoverHome` now returns `setup-failed` before it opens anything. So one trailing comma, added to a file the module header calls "user-editable plain JSON", means every tree in the space is gone from the window until the person finds and fixes the file. `Tapestry.tree` and `Forest.tree` are both intact, and opening them needs no write: `reopenFromPointer` is read-only. Only the pointer write (`:353`) needs the guard. The settings header still promises that such a file "never stops the app from starting". The app does start, but with an empty space. In practice this makes a harmless typo stop the space from opening. The case A and case C stops are justified, because they would create files or a second identity. Case B is not.
**Fix:** In `recoverHome`, when `assertReadable()` fails, still call `reopenFromPointer(paths.home)` and return the opened space without writing the pointer. Carry the unreadable-settings message as a non-fatal notice, so the banner says why settings changes cannot be saved. Keep the hard stop only for `importFromSettings` and `recoverForest`.

### WR-04: A neighbour pushed aside by a note change is still committed as the person's "move frame" and pushed onto main's frame-undo stack

**File:** `app/src/main/space/space-service.ts:452-465`, `app/src/renderer/components/Canvas.tsx:455-480`
**Issue:** 02.6-09 fixed only the renderer's run arming. `recordFrameGrowth` still sends `[grownFrame(unchanged), ...pushed]` through the same `trees:moveFrames` IPC. Main drops the unchanged first entry, so `changes[0]` is the pushed neighbour. The forest then records `move frame "B" and push N-1 aside`, signed `actor human user.<name>`, although the person only resized a note in A. It also pushes a frame-undo step and clears `redoSteps`. Tapestry's core value is readable provenance (CLAUDE.md, Readability and Control), and this commit tells a false story about who moved what. The stack is also polluted. The renderer's reset on `tree-edited` hides that today, but it only works as long as every growth source goes through `submitChange`.
**Fix:** Pass `frameMoved` (or a separate `trees:pushFrames` IPC) to main. For a growth batch, name the grown frame (for example `push N frames aside for "A"`), do not push an undo step, and do not clear redo. Alternatively, sign growth pushes as the system in the same way as fits, since the person did not choose them.

## Info

### IN-01: A fit that main commits is applied when the reply arrives and can overwrite a move made in the meantime

**File:** `app/src/renderer/components/Canvas.tsx:528-534`
**Issue:** `onFrameMove(treeId, origin.x, origin.y)` runs asynchronously. If the person grabs the new frame before the `fitFrame` reply arrives, the reply snaps the frame to the fitted spot. It does that during the drag, or after the drop, when main has already recorded the drag origin. The window is one IPC round-trip, so the risk is low.
**Fix:** Skip applying the fit when the frame's local position no longer equals `tree.frame` at request time, or when a drag of `treeId` is in progress.
