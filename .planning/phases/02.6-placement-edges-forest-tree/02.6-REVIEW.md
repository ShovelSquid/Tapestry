# Phase 02.6: Code Review Report

**Reviewed:** 2026-09-24T23:29:27Z
**Depth:** standard
**Files Reviewed:** 24
**Status:** issues_found

## Summary

I reviewed the phase 02.6 commits (`feat/test(02.6-01..06)`): the forest and Tapestry tree stores, launch classification and import, SpaceService membership, frame moves, fit and undo, the registry seams, the IPC wiring and the renderer's drop batch and undo routing. The 169 tests in the listed test files pass. I ran three of the scenarios below as throwaway vitest scripts in `/tmp` (removed afterwards; no source was touched). They reproduce CR-01, CR-02 and WR-01 against the real addon.

The main problems:

1. **settings.json.** The pointer write treats an unparseable settings.json as empty and replaces the whole file. This now runs automatically at launch, not only when the person changes a setting. It destroys the `trees` backup that D-10 promises to keep, and it also destroys `userName`. A first launch with such a file imports zero trees, permanently.
2. **The join between registry entries and stand-ins.** The join assumes each registry entry maps to its own stand-in, and each path to one entry. Two registry behaviours break that assumption. `create` does not clear an unavailable `path:` record. `tryOpen` keys unavailable records by path alone. So a visible frame can share a stand-in with another tree, and closing it removes the other tree from the forest. A stand-in can also become invisible and impossible to remove from the UI.
3. **Failures inside `open()`.** A vault add that fails inside `open()` leaves a registry entry with no stand-in. That breaks the T-2.6-24 promise that the registry and the forest never disagree.

## Critical Issues

### CR-01: An unparseable settings.json is silently replaced at launch, destroying the `trees` backup and the user name

**File:** `app/src/main/settings.ts:199-209, 257-268` (callers `app/src/main/space/migrate.ts:167, 214, 334`)
**Issue:** `readRaw()` returns `null` for a file that exists but does not parse, the same as for a missing file. `setTapestryPointer()` then does `const raw = this.readRaw() ?? {}` and writes `{ version: 2, tapestry: {...} }` over the file. The header says settings.json is "user-editable plain JSON", so a hand edit with a trailing comma is a realistic way to get there.
- **Case A (first launch):** `readLegacyTrees()` reads nothing, so the forest is created with **0 members** and the commit says `import 0 trees...`. The pointer write then removes the original `trees` list, `userName`, `agentsEnabled` and every unknown key. From then on the pointer exists, so the import never runs again and the arrangement is gone for good. I reproduced this: the file with `userName` and one tree became exactly `{"version":2,"tapestry":{...}}`.
- **Case B (`recover-home`):** a corrupt file also makes `getTapestryPointer()` return null. If `Tapestry.tree` exists, launch goes to `recoverHome` and the same write clobbers the file on an ordinary relaunch.

This breaks D-10 ("the old list stays an untouched backup") and the module's own promise that a corrupted preferences file "is an inconvenience, never a failure". Before 2.6, the file was only rewritten when the person changed a setting; now launch rewrites it.
**Fix:** Tell "missing" apart from "present but unreadable", and refuse to write over the second:
```ts
private readRaw(): { state: 'missing' } | { state: 'unreadable'; error: string } | { state: 'ok'; value: Record<string, unknown> } { ... }

setTapestryPointer(path: string): void {
  const raw = this.readRawState()
  if (raw.state === 'unreadable') {
    throw new Error(`settings.json could not be read, so it was left untouched: ${raw.error}`)
  }
  const base = raw.state === 'ok' ? raw.value : {}
  ...
}
```
In `importFromSettings`, return `setup-failed` (before creating any file) when settings.json exists but cannot be parsed, so the next launch can import once the file is fixed. Apply the same guard to `write()`.

### CR-02: Creating a world at a missing member's path makes two frames share one stand-in; closing the stale frame removes the new tree from the forest

**File:** `app/src/main/trees/registry.ts:295-304` (`create` never clears `unavailable`), `app/src/main/space/space-service.ts:584-591, 642-650, 776-787`
**Issue:** Take a digest-less stand-in S at `/a.tree` whose file is missing, so the registry holds `path:/a.tree` as unavailable. The person then uses Create New World to save a new world at `/a.tree`.
1. `registry.create` adopts world E but leaves the `path:/a.tree` record in place. Only `tryOpen` deletes it.
2. `addMember(E)` finds S through the digest-less path fallback and `settleIdentity` writes E's digest onto S.
3. Now **both** registry entries join to S: E by digest and `path:/a.tree` by path. The space shows two frames at the same origin.
4. A drop that pushes both fails with "Frame moves must be a list of 1 to 1 moves" or "moved twice in one drop".
5. Clicking **Close tree** on the stale "missing" frame runs `removeMember` on S and deletes the stand-in of the live world E. E stays open with no stand-in. Any move of it throws `Unknown tree`, and it disappears from the space at the next launch.

I reproduced this: after closing the stale frame the forest had 0 members while E was still listed as open.
**Fix:** When a tree is adopted at a path, drop any unavailable record for that path, as `tryOpen` already does:
```ts
// registry.adopt(), after this.trees.set(id, tree):
this.unavailable.delete(unavailableId(target))
```
As defence in depth, `SpaceService.removeMember` should refuse to delete a stand-in that another live registry entry also joins to. It should close only the stale registry record instead.

## Warnings

### WR-01: Re-opening a path that now holds a different world leaves an invisible stand-in that cannot be removed

**File:** `app/src/main/space/space-service.ts:584-623`, `app/src/main/trees/registry.ts:327-384` (unavailable records keyed by path only)
**Issue:** Member D at `/a.tree` has a recorded digest. The file is replaced by world E, and at launch the frame shows the 4.11 "A different world is now at..." message. The natural next step is Open tree... on `/a.tree`. `trees:open` calls `tryOpen` without `expect`, which opens E and deletes the `path:/a.tree` record. `addMember(E)` finds no stand-in, because D's digest differs and it is not digest-less, so it adds a **second** stand-in at the same path.

D's stand-in is still in the forest but no registry entry joins to it, so it never appears on screen. At every later launch, D records `path:/a.tree` as unavailable, then E's restore at the same path deletes that record (`registry.ts:381`). The ghost stays hidden for good. I reproduced this: after the reopen, `list()` had 1 tree and the forest had 2 members. After closing the visible tree the forest still held 1 member, with no way to remove it from the UI. The ghost's placement also counts in `nextFrameOrigin` and in the `moveFrames` length bound.
**Fix:** In `addMember`, when a stand-in with a *different* digest has the same path hint as the newly opened entry, treat it as replaced: either rewrite it (the person chose this path) or delete it in the same person-signed commit and name both in the message. Keying unavailable records by stand-in rather than by path would also stop one path from hiding another member.

### WR-02: A vault add that fails inside `open()` leaves a registry entry with no stand-in (breaks T-2.6-24)

**File:** `app/src/main/index.ts:522-544` with `app/src/main/obsidian/vault-service.ts:98-111`
**Issue:** `openIntoSpace` only rolls back the registry when `space.addMember` throws. `vaultService.addVault` can throw *after* it has changed the registry, in two ways:
- **Unavailable vault tree:** `tryOpen` records the `path:` entry, then `requireOpen` throws. This happens for a vault tree that is locked by another window or damaged.
- **Failed catch-up:** the tree opens and is adopted, then `catchUp` rejects.

In both cases the outer `catch` returns the failure and leaves the entry in the registry. `trees:list` shows it at (0,0) with no stand-in (the service's own comment says "which the membership handlers never leave behind"). Dragging it, or any drop whose push-apart touches it, fails the whole batch with `Unknown tree`. It also vanishes at the next launch.
**Fix:** Compute `before` first and wrap the whole `open()` + `addMember` in the rollback:
```ts
const before = new Set(registry.summary().map((t) => t.id))
const beforeUnavailable = new Set(registry.unavailableList().map((t) => t.id))
try {
  const tree = await open()
  space.addMember(tree, actor)
} catch (err) {
  for (const t of registry.summary()) if (!before.has(t.id)) registry.close(t.id)
  throw err
}
```

### WR-03: Closing a tree now needs a name and a ready space, but the renderer drops the result, so refusals are silent

**File:** `app/src/main/index.ts:660-677` (renderer callers `app/src/renderer/components/FrameHeader.tsx:94`, `app/src/renderer/components/TreeFrame.tsx:98`)
**Issue:** Before 2.6, `trees:close` needed no actor. It now calls `getHumanActor()` and throws `SpaceRefusal` when the space is not open, and it returns a 4.9 `notice` ("notice on ... close" in the 02.6-06 commit). Both renderer callers still do `void window.tapestry.trees.close(id)`. A refused close (no name yet, space not open, forest write failure) therefore does nothing visible, and the approved 4.9 sentence is never shown.
**Fix:** Route close through an App-level handler that awaits the result and shows `result.notice ?? result.error`, the same way `addTreeToSpace` does.

### WR-04: A pushed-aside neighbour from a note move or resize is recorded as a person's frame drop and arms frame undo

**File:** `app/src/renderer/components/Canvas.tsx:442-462`, `app/src/renderer/App.tsx` (`handleFramesMoved`), `app/src/main/space/space-service.ts:449-461`
**Issue:** `recordFrameGrowth` sends `[grownFrame(unchanged), ...pushed]`. In main, `changes[0]` is the first *changed* entry, which is a pushed neighbour. So the history reads `move frame "B" and push N aside`, signed by the person, although they moved a note in A and never touched B. It also pushes an undo step. In the renderer the result arrives after `submitChange` has already sent `'tree-edited'`, so `'frames-moved'` restarts the run. The next Ctrl+Z then undoes the neighbour push instead of the note move the person just made. This contradicts the stated rule that a tree edit ends the frame run.
**Fix:** Give growth pushes their own path. Either use a separate IPC and message (e.g. `push N frames aside for "A"`) that neither arms the renderer run nor clears redo, or pass `frameMoved` through to main and name the grown frame in the message. At minimum, do not call `noteFrameEvent('frames-moved')` for growth results.

### WR-05: The renderer keeps a fitted position that main refused, so screen and forest silently disagree

**File:** `app/src/renderer/components/Canvas.tsx:480-508`, `app/src/main/space/space-service.ts:488-505`
**Issue:** The fit effect calls `onFrameMove` locally and then `void window.tapestry.trees.fitFrame(...)` without checking the result. Main allows one fit per member per *main* session, while `placedRef` is per *renderer* session. A new renderer session re-runs the fit for every tree, and main returns `committed:false` for spent or person-moved members. This happens when the window is re-created on macOS `activate` (`index.ts:863-867`) or after a renderer reload. The frame then sits at a position the forest never recorded. The next `trees-changed` refresh jumps it back, and the fit will not run again because `placedRef` already holds the id.
**Fix:** Apply the fitted origin only when main reports `ok && committed`, or call `refreshTreeList()` when it does not.

## Info

### IN-01: `relocateMember` and `recordIdentity` are unused in production; `relocateMember` does not validate its path

**File:** `app/src/main/space/space-service.ts:630-635, 680-705`
**Issue:** Only tests call these methods. `relocateMember` writes `resolve(treePath)` as a path hint without `isSafeTreePath`, and it labels the commit `add tree "..."`.
**Fix:** Remove them until `vault:locate` lands, or validate with `isSafeTreePath` and use a dedicated message such as `record new location of "..."`.

### IN-02: Dead guards in index.ts

**File:** `app/src/main/index.ts:533, 569-570, 886`
**Issue:** `space` is never set back to null (`will-quit` calls `space?.close()` only), so `if (!space) throw new SpaceRefusal()` after the `await` is dead. The real guard is `requireReady()`. The `trees:list` fallback for `space === null` is also unreachable, because `space` is assigned before any handler runs.
**Fix:** Check `space.ready` after the await, or set `space = null` in `will-quit`, and remove the unreachable fallback.

### IN-03: `AppSettings.version` doc contradicts `setTapestryPointer`

**File:** `app/src/main/settings.ts:56-60` vs `257-268`
**Issue:** The doc says "this build never raises it", but `setTapestryPointer` raises it to 2.
**Fix:** Change the doc to "raised only to 2, by the pointer write; never lowered".

### IN-04: The name-required refusal in `openIntoSpace` is shown as "The file may be damaged"

**File:** `app/src/main/index.ts:526`, `app/src/renderer/App.tsx` (`addTreeToSpace`)
**Issue:** `getHumanActor()` throws "Set your name before making changes". There is no `notice`, so the renderer replaces it with the generic damaged-file sentence.
**Fix:** Return that refusal as a `notice`, or reopen the name prompt.

### IN-05: The frame-undo step is popped before the forest write, so a failed write loses it

**File:** `app/src/main/space/space-service.ts:537-559`
**Issue:** `from.pop()` runs before `forest.setOrigins`. If the write throws, the step is lost, and the renderer resets its run.
**Fix:** Peek, write, then pop, or push the step back in a `catch`.

### IN-06: Vault stand-ins are never restored but still take part in layout

**File:** `app/src/main/index.ts:498-511`, `app/src/main/space/space-service.ts:279-283, 840-849`
**Issue:** This is a known gap: there is no `restoreVault` hook. Imported or added vault members are hidden after a relaunch, yet they still shift `nextFrameOrigin` and count towards the `moveFrames` bound. The person cannot remove them from the UI.
**Fix:** Track this with the 2.2 Plan 08 merge. Until then, consider leaving unrestorable members out of `nextFrameOrigin`.
