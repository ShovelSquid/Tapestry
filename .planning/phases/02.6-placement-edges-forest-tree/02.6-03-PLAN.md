**As** Kaelen, **I want to** arrange my trees and have that arrangement kept in a readable forest tree referenced from one always-open Tapestry tree, **so that** arranging trees gets an actor, undo, history and branches like any other edit.

*(User story derived from the ROADMAP Phase 2.6 Goal line; its "so that" clause is quoted verbatim.)*

Plan 02 proved the space against the real addon at the `SpaceService` boundary. This plan puts it under the app:

1. **Tracer.** App launch starts the space. The window draws frames from the forest. A drop sends one batch and records one signed commit. 2. **Launches that must write nothing (D-14 cases E, G, H).** Plan 02 implemented them in `reopenFromPointer` and `start()`. They are tested here, beside the startup code that relies on them.

This plan was split out of Plan 02 so each stays within the context budget. It runs after Plan 02's blocking checkpoint and adds no record name or migration behaviour. Values in brackets are the Plan 02 checkpoint's Recommended values; use `02.6-02-SUMMARY.md` § Checkpoint decisions wherever it differs.

**Interim state until Plans 04-05.** `trees:open`, `trees:create`, `trees:close`, `vault:add` and `trees:setFrame` still write the old settings list until Plan 04 (membership) and Plan 05 (fit) convert them. Do not run the app against real user data before Plan 06's human check.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → `trees:moveFrames` | An untrusted batch of ids and numbers |
| process env → main (dev builds) | `TAPESTRY_USER_DATA_DIR` and `TAPESTRY_SPACE_DIR` redirect where data is read and written |
| another Tapestry window → journals | A second process may hold the Tapestry tree or forest lock |
| settings pointer / forest file → launch | A missing file, or a different file at the referenced path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-2.6-05 | Denial of Service | `trees:moveFrames` flood | medium | mitigate | The handler passes the payload untouched to `SpaceService.moveFrames`, which validates length, uniqueness, membership and finite numbers (Plan 02) and writes nothing for an unchanged batch |
| T-2.6-11 | Repudiation / Spoofing | actor on a drop | high | mitigate | The handler resolves `getHumanActor()` in main; the IPC payload has no actor field |
| T-2.6-22 | Elevation of privilege | dev path overrides | medium | mitigate | Honoured only when `!app.isPackaged` and the value is an absolute path without `..`; a packaged build ignores them |
| T-2.6-03 | Tampering | pointer to a missing or foreign file | high | mitigate | Cases E and H write nothing and open nothing; tested with byte comparison |
| T-2.6-28 | Denial of Service / Tampering | two windows on one space | medium | mitigate | Case G returns `*-locked`, opens no member, and writes nothing; `space.close()` at quit releases locks for the next launch |
| T-2.6-DATA | Tampering | human check against live data | high | mitigate | The human check uses copies through the dev-only variables; tests inject every path under `makeTempDir` |
</threat_model>
