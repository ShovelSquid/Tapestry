<objective>
**As** Kaelen, **I want to** arrange my trees and have that arrangement kept in a readable forest tree referenced from one always-open Tapestry tree, **so that** arranging trees gets an actor, undo, history and branches like any other edit.

*(User story derived from the ROADMAP Phase 2.6 Goal line; its "so that" clause is quoted verbatim.)*

Plans 02-03 made the forest the arrangement. This plan makes it the **membership** too, and makes a member's identity its header digest (D-03):

1. **Tracer:** open, create or add a vault tree, and it lands in the forest; close it and it leaves, with its last position kept in history; relaunch and exactly those members come back. The first successful open records the digest once, signed by the system.
2. **Identity:** a moved file keeps its frame when you open it from its new place; a copy is refused; a different world at a member's path is shown as unavailable and never adopted; a duplicate stand-in is folded away; Tapestry's own files cannot be added.

After this plan, no open, create, close or vault handler writes the settings `trees` list. Only `trees:setFrame` still does, until Plan 05.

The one-way doors this plan writes through (D-13 record names, D-10/D-14 migration) were confirmed at Plan 02 Task 1; this plan introduces no new name and no new migration behaviour, so it carries no checkpoint of its own. Every value in brackets below is the Plan 02 checkpoint's Recommended value; use the resolved value from `02.6-02-SUMMARY.md` § Checkpoint decisions wherever it differs. All names come from `app/src/main/space/shapes.ts`; never spell a type, key or label inline.

**Shared-machine rules:** never `npm install`; stage by name; `git show --stat HEAD` after each commit; tests inject every path and use `makeTempDir`.

Requirements: the phase owns none (ROADMAP). This plan exercises TREE-02 (stable identifiers) and PROV-03 (who changed membership) through integration only, so `requirements` is empty.
