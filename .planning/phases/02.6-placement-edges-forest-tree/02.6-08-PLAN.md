<objective>
Close verification gaps 2 and 3 (review findings CR-02 and WR-01). Both come from one root cause. The join between registry entries and forest stand-ins assumes one-to-one, but unavailable records are keyed by path alone.

- **Gap 2 (CR-02, SC-4).** `registry.create` does not clear the `path:` record at its path. So after Create New World at a missing member's path, two list entries share one stand-in. Closing the stale "missing" frame then deletes the live world's stand-in, a later move throws, and the world disappears at the next launch.
- **Gap 3 (WR-01, SC-5).** Suppose member D has a digest, and a different world E now sits at D's path. When the person uses Open tree on that path, E's adopt deletes D's `path:` record. E then gets a second stand-in, and D's stand-in stays in the forest but is never shown again and cannot be removed.

This plan:

1. **Tracer (Task 1, CR-02):** `adopt()`, which open, create and tryOpen all go through, clears the unavailable record at the adopted path. `removeMember` refuses to delete a stand-in another live entry still joins. The regression test drives the reproduced flow end to end against the real addon.
2. **Task 2 (WR-01):** unavailable records for a member whose digest is known are keyed by that digest, not by path. One path therefore cannot hide another member. The join and the `tryOpen` shortcuts are then made one-to-one, and a three-launch regression shows every forest member stays listed.

**Choice for gap 3, recorded as asked by the orchestrator.** The verification offered two fixes: (a) `addMember` treats a same-path stand-in with a different digest as replaced, either rewriting it or deleting it, or (b) unavailable records are keyed by stand-in. This plan takes **(b)**, keying by the member's recorded digest, which is the stand-in's identity on disk. The reasons:

- It is the only choice that removes nothing the person did not close. D stays visible with the approved 4.11 reason, and the person can Close it themselves. That is T-02.2-32 and SC-5.
- It needs no new commit wording. Option (a) needs an unapproved sentence to name both trees in one commit, and shapes.ts must not change.
- It never gives an old member's frame to a new identity (Pitfall 5). Option (a)'s "rewrite" does.
- It is fully reversible, because it changes in-memory keys only.
- It matches D-03: a tree is named by its digest, and `path:` is only for a tree never read.

Purpose: SC-4 and SC-5 hold on the reproduced paths, and the same fix keeps SC-2 and SC-3 intact (one placement edge per frame).

Requirements: the phase owns none. This plan exercises TREE and PROV through integration only, so `requirements` is empty.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| files at member paths → registry | A path may now hold a different world, a new world, or nothing; the path is only a hint (D-03) |
| renderer → `trees:close` / `trees:moveFrames` | The renderer names ids from `trees:list`; main resolves them to stand-ins |
| registry (in memory) → forest (on disk) | The join decides which stand-in a close deletes and which placement a move writes |
