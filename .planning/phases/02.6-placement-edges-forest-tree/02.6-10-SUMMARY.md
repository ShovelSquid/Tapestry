# Phase 02.6 Plan 10: Add Rollback (WR-02) Summary

**When adding a tree fails anywhere, the new `openWithRollback` helper closes every registry entry the call introduced that joins no stand-in, then rethrows the original error. That covers a vault tree that will not open, a failed catch-up, and a forest write failure. The registry and the forest therefore agree after every add. `SpaceService.isMember` keeps the rollback from closing a tree that a concurrent add has already put in the forest.**

## Accomplishments

- **WR-02 / T-2.6-24 is closed.** Before this plan, `openIntoSpace` rolled back only when `addMember` threw. Now `open()` (`registry.tryOpen`, `registry.create` or `vaultService.addVault`) and the forest record both run inside `openWithRollback`. A vault tree recorded unavailable and then refused by `requireOpen` leaves nothing behind in the registry. Neither does a tree adopted before its catch-up rejects.
- **T-2.6-40:** the rollback skips any new entry that `isMember` reports, so a concurrent add that succeeded during a slow vault catch-up survives.
- **T-2.6-41:** a rolled-back adoption releases its journal lock. The tests prove this by reopening the file with a fresh `KernelBridge`.
- **IN-02, the `openIntoSpace` half:** the check after the await now tests `space.ready`, not only whether `space` is non-null.
- Errors are rethrown as the same object, so `spaceFailure` still produces the approved 4.9 and 4.10 notices unchanged.

## Decisions Made

- If `isMember` throws for an id, the rollback keeps that entry. Wrongly closing a tree the forest holds is the more harmful mistake. `SpaceService.isMember` never throws in any case.
- The rollback needs no restore step for unavailable records that `adopt()` retired. If the adopted world matches such a record's stand-in, `memberFor` joins it, `isMember` is true, and the entry is kept.
