# Phase 02.6 Plan 09: Renderer reflects main's answers (WR-03, WR-04, WR-05) Summary

**Frame undo is armed only by a committed frame drag (not a note-growth push), a system fit is drawn only once the forest holds it, and Close tree now shows main's 4.9 notice or a `Close tree failed:` banner instead of failing silently.**

## Accomplishments

- **WR-04 (undo half):** `frameRunEventForDrop(result, frameMoved)` in `undo-target.ts` returns `'frames-moved'` only for `ok && committed === true && frameMoved`. Canvas passes `frameMoved` with every `moveFrames` result, rejected calls included, and `App.handleFramesMoved` routes through the rule. Ctrl+Z after a note change that pushed a neighbour now goes to the note change. Ctrl+Z after a frame drag still puts the frames back.
- **WR-05:** `originAfterFit(result, fitted)` in `frame-moves.ts`. The fit effect no longer calls `onFrameMove` before main answers. It awaits `trees.fitFrame` and moves the frame only on a committed fit. A rejected call is logged and the frame stays put. `placedRef` still allows one fit per tree per renderer session.
- **WR-03:** `App.handleCloseTree` awaits `trees.close`. If main returns a `notice`, it is shown word for word with `setNotice`, as `addTreeToSpace` does. Any other failure, including a rejected call, shows `Close tree failed: <error>` in the app banner. `onCloseTree` is passed from App to Canvas (as a prop and in the handlers bag), then to TreeFrame (in its handlers and the unavailable-frame actions), then to FrameHeader (as `onClose`). The "Close tree" label and tooltip are unchanged.
- The pan and zoom code from quick task 260924-dwq is untouched. The plan's Canvas diff has no line that mentions zoom, wheel or pan.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The result parameter type includes `error?: string`**
- **Found during:** Task 1 (typecheck after GREEN)
- **Issue:** The plan's signature was `result: { ok: boolean; committed?: boolean }`. The plan's own test literal `{ ok: false, error: 'x' }` then fails TypeScript's excess-property check (`TS2353`) under `tsconfig.web.json`.
- **Fix:** Both `frameRunEventForDrop` and `originAfterFit` take `{ ok: boolean; committed?: boolean; error?: string }`, the same shape the IPC results have. Behaviour is unchanged.
- **Files modified:** `undo-target.ts`, `frame-moves.ts`

## Open questions for Kaelen

These are user-visible wording, which needs Kaelen's approval. An unattended run must not invent approved copy, so nothing below was changed. Items 1 and 2 have to be decided. Item 3 was shipped as a banner and needs a yes or no.

1. **The growth-push forest commit message (WR-04, second half; answer 1.12). Unchanged.** When a note landing or resizing grows its frame into a neighbour, the forest records:
   - `move frame "<name>" and push <N> aside`, built by `moveFrameMessage` in `app/src/main/space/shapes.ts:143-146`
   - Here `<name>` is the **first pushed neighbour**, not the frame that grew, because main names `changes[0]`, the first entry that changed. The grown frame's own entry is unchanged. The commit is **signed by the person**, which is correct because their edit caused it, but it reads as though they moved B.
   - The candidate wording in the review, not implemented: `push <N> frames aside for "<grown frame>"`. Another option is to keep `move frame "<grown frame>" and push <N> aside` and name the grown frame. Either one is a new sentence in the 1.12 set and changes `space-service.test.ts:279`'s expectation for growth batches only.
   - Related question: should a growth push go on main's frame-undo stack and clear its redo stack at all? Today it does. The renderer just no longer lets Ctrl+Z reach it.
2. **New banner text for a Close tree failure (WR-03).** When main returns no `notice`, or the call rejects, the banner shows:
   - `Close tree failed: <error>` (for example, `Close tree failed: Unknown tree <id>`)
   - `Close tree failed: unknown error` (when main gives no error string)
   - The pattern copies the existing `Undo failed: <error>` / `Redo failed: <error>` banners. The plan treats it as not new approved copy, but it is a new user-visible string, so please approve it or reword it. Refusals that main marks with a notice (4.9 no name / no open space, 4.10) are shown exactly as main words them.
3. The console-only log `Frame fit failed:` is not user-visible and needs no approval.
