# Phase 2.6 Plan 03: Launch Into the Forest Summary

**The app now opens the space at launch through `SpaceService.start()`, which replaces the settings.json restore loop. `trees:list` reads frames from forest placement edges. A drop, with every frame it pushed aside, is one `trees:moveFrames` call that main signs with the person's name and records as one forest commit. Quitting closes the forest and Tapestry tree before the registry. Dev builds can point userData and the space folder at scratch copies. Tests show that launch cases E, G and H write nothing and open nothing.**

## Accomplishments

- **`index.ts`**
  - A module-level `space: SpaceService | null`. It is built after `registry` and `settings` with paths `{ forest: <spaceDir>/Forest.tree, home: <spaceDir>/Tapestry.tree, lastOpenedFile: getLastOpenedPath() }`. `HOME_LOCATION` is `'space-dir'` (answer 1.10), so the home sits in the space folder.
  - The only hook is `approvePath`, which adds `resolve(path)` to `approvedPaths`.
  - `await space.start()` replaces `settings.migrateLastOpened(...)` and the `settings.read().trees` loop. It runs after `createWindow()` and before `loadPluginsSafely()`. A problem is logged with `problemMessage`, and an unexpected throw is caught and logged, so plugins and the window still load.
  - `trees:list` returns `space.list()`. When `space` is null it falls back to `registry.summary()` with `{ x: 0, y: 0 }`.
  - `trees:moveFrames` works in this order:
    1. It calls `getHumanActor()` first.
    2. It returns `SPACE_NOT_OPEN` (4.9) when the space is not ready.
    3. It returns `{ ok: true, committed }` on success.
    4. It catches any error as `{ ok: false, error }`.
    5. It emits no `trees-changed`.
  - `will-quit` calls `space?.close()` before `registry.closeAll()`.
  - `devPathOverride()` reads `TAPESTRY_USER_DATA_DIR` and `TAPESTRY_SPACE_DIR` only when `!app.isPackaged`, and only accepts an absolute path with no `..`. The userData redirect runs at module load, before `app.whenReady()`.
  - The `getLastOpenedPath` comment and the Trees IPC banner were rewritten (2.6 D-01 supersedes 2.2 D-18). The banner names the handlers that still write settings until Plans 04 and 05.
- **Preload and `global.d.ts`.** Both declare `trees.moveFrames(moves)` and `TapestryFrameMove`. The `trees` doc comment now says the arrangement lives in the forest tree. The `frame` doc comment says it is read from the tree's placement edge (D-04).
- **`Canvas.tsx`**
  - `settleFrames` is gone.
  - `recordFrameMoves(movedId, movedOrigin, frameMoved)` builds one `buildFrameMoveBatch`, applies the pushed frames locally with `onFrameMove`, and makes one `moveFrames(batch)` call. When the result is not ok, it logs `[Canvas] frame move not recorded:`.
  - `handlePointerUp` uses it for a moved drop. Note landing and resize handlers use it through `recordFrameGrowth`, which makes no call when nothing was pushed.
  - The placement-correction effect is unchanged until Plan 05.
- **Launch-problem tests (4 new, in `space-service.test.ts`).**
  - Case E: `home-missing`, the space folder stays empty, and settings bytes are unchanged.
  - Case G, home held: `home-locked`.
  - Case G, forest held: `forest-locked`. The Tapestry tree that launch opened is released again.
  - Case H: `forest-mismatch`. The replacement forest's bytes are unchanged, and both files are released.
  - In every case, `ready` is false, the registry and `list()` are empty, `moveFrames` throws 4.9, and each involved file keeps its bytes and `@commit` count.

## Decisions Made

- `trees:moveFrames` returns the `SPACE_NOT_OPEN` constant from `migrate.ts` rather than retyping the 4.9 sentence, so the wording stays spelled in one place.
- `space.start()` is wrapped in try/catch in `index.ts`. `start()` returns problems rather than throwing, but a bug there must not stop the window or plugins from loading (D-33 spirit).
- For note-driven pushes the batch's first entry is the grown frame at its unchanged origin. The service skips unchanged entries, so the commit records only the pushed frames. Its message names the first pushed frame, as in `move frame "x" [and push k aside]`, and it is signed by the person.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Note-driven push-apart would have lost its persistence**
- **Found during:** Task 1
- **Issue:** The plan says to delete `settleFrames`. Since 02.5-03 (`aa8dfe5`), four note handlers call it (`onPositionChange`, `onTakeOverPosition`, `onWidthChange`, `onHeightChange`), so that a note that grows its frame pushes neighbours aside. The plan covered only `handlePointerUp`. Deleting the function, or keeping those callers on `trees:setFrame`, would write to settings.json, and `trees:list` no longer reads it. The pushed frames would jump back on relaunch.
- **Fix:** The same `recordFrameMoves` batch serves both paths. A note growth calls it with `frameMoved = false`, so it sends nothing when no frame was pushed, and one `moveFrames` call otherwise.
- **Files modified:** `app/src/renderer/components/Canvas.tsx`
- **Verification:** typecheck, build, full suite; `! grep settleFrames` is clean, and there is exactly one `moveFrames(` call site.
- **Committed in:** `82df051`

**2. [Rule 3 - Blocking, test fixture] Case H needed a forest from a different second**
- **Found during:** Task 2
- **Issue:** The first run of case H returned no problem. A header digest covers `world Forest` and `created <second>`, so two temp forests created in the same second had identical digests. To the kernel they were the same world.
- **Fix:** The test waits for the next wall-clock second before building the other space. It also asserts that the two headers differ, so the premise is stated. No production code changed.
- **Files modified:** `app/src/main/space/space-service.test.ts`
- **Committed in:** `719ba90`

## Issues Encountered

- **Finding for Kaelen and Plan 06 (not fixed; the kernel is out of scope):** a forest's identity is its header, meaning the world name `Forest` plus the creation time to the second. Case H's digest check therefore cannot tell apart two forests created in the same second, for example on two machines. In practice this is very unlikely. It is noted because the approved world name (1.9) is the same for every forest, so only the timestamp separates them.
