<domain>
## Phase Boundary

The arrangement of open trees stops being an unrecorded preference in `settings.json`. It moves into a **forest file**: an ordinary `.tree` whose content is one stand-in node per member tree and one `placement` edge per frame. The forest file is referenced from an always-open **Tapestry tree**, and `settings.json` keeps only a pointer to that tree. Arranging trees then gets an actor, undo, history and branches like any other edit.

**In scope:** the Tapestry tree (created, opened at launch, holding the reference to the forest); the forest file; members named by header digest with a path hint; frames as placement edges; non-destructive migration of today's open trees and frame positions; frame undo; recording of frame moves.

**Out of scope:** moving note positions (`position.x/y`) onto placement edges. That is a later phase after 2.3, provisionally 2.7, because it moves D-27's thread frame. Also out of scope: lock-ceiling properties on the Tapestry tree (2.4's later slice), several forests and switching between them, and any 3D or drawing work (Phase 4).

</domain>

<decisions>
## Implementation Decisions

### Decided before this discussion (Decision Register, 2026-09-16)
- **D-01:** **There is a forest file.** Kaelen: *"yeah lets do a forest file"* (Pending #21 → #5 A). **This supersedes 2.2 D-18** ("there is no forest file"). The main-branch copy of D-18 is left unedited; this line records the supersession.
- **D-02:** **One Tapestry tree holds the widest scope and references forests; forests are ordinary trees** (#2 shape C, under the grant). In 2.6 the Tapestry tree's only job is to reference the current forest. 2.4's later slice adds the lock-ceiling properties. Until then `agentsEnabled` stays in `settings.json` as the de facto top rung.
- **D-03:** **A tree is named by its header digest; the path is only a hint** (#13 B, under the grant). The forest always stores `path.hint` and stores `digest` once it is known. A tree that has never been read keeps an in-memory `path:` id (2.2 T-02.2-32's `unavailableId`) until its first successful open. **A `path:` id is never written to disk as an identity.** Two paths with one digest are one member, consistent with `registry.ts` `adopt()` refusing a copied world.
- **D-04:** **Each frame is a `placement` edge** from the forest's space to a member stand-in, carrying `origin.*`. A placement may also carry `size.*` (#6), but frames leave it unset in 2.6 because frame size is computed from content (`frames.ts` `computeFrameBounds`). No kernel verb or value type is added. Nothing in the space model refuses a kind of thing from being placed (#7).
- **D-05:** **Note positions are untouched.** `position.x/y` stay node properties and D-27's thread frame does not move (#4). A forest placement is a *new* record, so nothing is migrated off notes.

### Where the forest file lives (Kaelen: 1a)
- **D-06:** **One forest, stored as a normal visible file** (for example `~/Documents/Tapestry/Forest.tree`), opened automatically at launch. Kaelen never has to pick it. It can be read without the app, which is the project's readability constraint. — **Reversibility:** costly — once users have a forest at a path, moving the default means migrating the pointer, but the pointer in `settings.json` already carries that.
- **D-07:** **Switching between several forests is deferred.** The forest is an ordinary tree that the Tapestry tree references, so plural forests need no reshaping later.

### Undoing a frame move (Kaelen: 2a)
- **D-08:** **Ctrl+Z right after dragging a frame puts it back.** Otherwise Ctrl+Z keeps undoing the selected tree's last edit, as today (`use-forest.ts` `selectedTreeId`).
- **D-09:** **A frame undo is a compensating commit, not a rewind.** It writes the previous `origin` back as a new commit. Reason: `KernelBridge.submit` refuses to commit while a tree is rewound ("Cannot commit while history is rewound"), so rewinding the forest would make the next drag or automatic fit fail until redo. A compensating commit keeps the forest always writable, and history still shows the move and its reversal.

### Current layout on first launch (Kaelen: 3a; substance of #18)
- **D-10:** **On first launch after upgrade, today's open trees and their frame positions are copied into a new forest.** The old `trees` list in `settings.json` stays untouched as a backup and is no longer written. `SettingsStore.migrateLastOpened` already set this precedent: the old file is read once, and nothing writes it afterwards. The settings `version` is bumped and the pointer is added. — **Reversibility:** one-way — the new settings shape and the migrated forest are what every later launch reads. The exact behaviour (triggers, the missing-pointer and missing-file cases, the commit's actor and message) goes to Kaelen at a blocking checkpoint (#18).

### What history records (Kaelen: 4a)
- **D-11:** **A drag, together with the frames it pushes aside (`frames.ts` `pushApart`), is one commit under the user's actor,** so one undo restores all of them.
- **D-12:** **A frame that shifts on its own to fit its notes is recorded as `actor system`, and only when its position actually changes.** This covers the renderer's content-bounds correction after open, which `index.ts` describes at `trees:setFrame`. Opening a space must not add history entries when nothing moved. Following 2.2 D-21, an author is never guessed.

### One-way doors held for Kaelen
- **D-13:** **The on-disk record shape is a one-way door (#17).** This means the Tapestry-tree and forest node type strings, the property keys (`digest`, `path.hint`, `origin.*`, `size.*`, and whatever the Tapestry tree uses to reference its forest) and the `placement` edge label. History is append-only and replay keeps old names forever. **The plan must propose the exact shape in a `checkpoint:decision` task with `gate="blocking-human"`, before any task that writes it.** — **Reversibility:** one-way — replay of every forest ever written depends on these names.
- **D-14:** **The `settings.json` migration's exact behaviour is a one-way door (#18).** It goes behind the same blocking-human checkpoint (or a second one), before any code that migrates. D-10 is Kaelen's answer on substance; the checkpoint confirms the specifics. — **Reversibility:** one-way — see D-10.

### Claude's Discretion
- **The forest is not drawn as a frame inside itself**, and the Tapestry tree is not drawn at all in 2.6. A forest placed in a forest would draw as one "you are here" mark, since the recursion cap is 1 (`Concept - The World Contains Its Controls`). Nothing in 2.6 needs that case.
- **Opening a tree** creates its stand-in and placement in one commit under the user's actor. **Closing a tree** deletes its stand-in, and with it its placement, in one commit under the user's actor, so a closed tree's last position is restorable from history. **When a tree first opens**, its `digest` is written as `actor system`.
- **A moved file is re-identified only when the user opens it from its new path.** If the digest matches an existing member, that member's frame is reused and `path.hint` is updated in the same commit. There is no automatic filesystem search.
- **An unavailable member's frame can be moved.** The position belongs to the forest, not to the member tree. Today `trees:setFrame` requires an open tree; that restriction goes.
- The default location may be under `~/Documents/Tapestry/`, provided `validateTreePath` accepts it (paths under home are accepted).
- Plan structure, file layout, and whether forest logic lives in a new main-process module or in `registry.ts`.

<code_context>
## Existing Code Insights

### Reusable Assets
- `TreeRegistry` already opens many journals and keeps unopenable ones as `UnavailableTree`. The forest and Tapestry trees are two more journals, but they are **not** space members and must not appear in `summary()`.
- `frames.ts` `pushApart` and `placeNewFrame` are pure functions. D-11 needs their output as one batch of placement writes.
- `SettingsStore.migrateLastOpened` is the pattern for a non-destructive, read-once migration (D-10).
- `KernelBridge.submit(actorKind, actorId, message, ops)` already takes an explicit actor, which D-11 and D-12 need.

### Established Patterns
- Main stamps actors; the renderer never sends one.
- Every tree operation names its tree first (D-15 preload API).
- Main and renderer are separate bundles. Main has so far copied renderer constants rather than importing them (`placeNewFrameFromSettings` repeats 480 and 64). The 2.5 planner found that importing from `app/src/renderer/layout/` works with no config change; that choice is under orchestrator review.
- Undo is a per-tree rewind, and commits are refused while a tree is rewound. That is why D-09 uses a compensating commit.

### Integration Points
- `trees:list` today joins `registry.summary()` with frames from settings, keyed by path. It will join with forest placements keyed by member identity instead.
- `trees:setFrame` today writes `settings.setTreeFrame(path)`. It becomes a forest commit carrying the pushed-aside frames too (D-11), or an `actor system` commit for an automatic fit (D-12).
- `trees:open`, `create`, `close` and `reopen` add or remove a member, and record the digest when first known.
- App startup reads the pointer from `settings.json`, or runs the D-10 migration, then opens the Tapestry tree and the forest before restoring members.

</code_context>
