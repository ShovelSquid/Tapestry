## Summary

Everything this phase needs already exists in the kernel. A forest is an ordinary `.tree`: a space node, one stand-in node per member tree, and one `placement` edge per frame carrying `origin.x`/`origin.y` as `real`. The kernel accepts properties on edges (`SetProperty` takes `Target = std::variant<NodeId, EdgeId>`), keys like `path.hint` and `origin.x` pass `isValidKey`, and `delete-node` cascades to the node's edges. Closing a tree is therefore one `deleteNode` op. The Tapestry tree is a second ordinary journal holding a root node (which 2.4 will later decorate) and a reference to the forest. Cross-file references cannot be `ref` values, because `ref` must name a live id *in the same world* (`World.cpp` `checkValue`). The forest's digest is therefore stored as `text`, the same way 2.2 Plan 15 stores `remote.tree`.

The work is in the Electron main process, plus a small renderer change. (1) A new main-side module holds the Tapestry and forest `KernelBridge`s **outside** `TreeRegistry`, so they never appear in `summary()`, never become `primary()`, and are never reachable by plugins or agents. (2) Every `trees:*` handler in `index.ts` that today calls `settings.addTree/setTreeFrame/removeTree` instead writes a forest commit. `trees:list` joins `registry.summary()` with forest placements by member identity (digest first, then `path.hint`). (3) The renderer's two per-frame `trees.setFrame` loops (`Canvas.tsx` `settleFrames` and the placement-correction effect) become one batched `moveFrames` call under the human actor and one `fitFrame` call under `system`. (4) Ctrl+Z immediately after a frame drag is routed to a main-side frame-undo that writes a compensating commit. (5) `SettingsStore` gains `version: 2` and a pointer, and it must stop dropping unknown keys and normalising `trees` on write. Today `update()` rewrites the file from `read()`, which drops every key it does not know and drops malformed `trees` entries. That breaks D-10's "untouched backup" promise unless it is fixed first.

The largest risks are not technical. They are sequencing and naming. This branch must merge main first (Pending #15). 2.2 still has Plans 08-16 to execute on main, and they touch `index.ts`, `settings.ts` (Plan 14), `registry.ts` and `Canvas.tsx` (Plan 15). **2.2 Plan 15 creates `app/src/main/commands/forest.ts` / `ForestCommands` and claims the `tapestry.forest/` type namespace**, so 2.6 must not use that path or class name, and its type strings must be chosen knowing that namespace exists. Several builds of the app (one per worktree) share one `userData/settings.json`, so an older build can rewrite settings and delete the pointer. The migration must handle "pointer missing, but the files exist" without importing twice.

**Primary recommendation:** Build a `SpaceService` in `app/src/main/space/` that owns the Tapestry and forest bridges and every forest commit. Keep `TreeRegistry` unaware of the forest, apart from one "reserved path" refusal. Gate all writing code behind one `checkpoint:decision` (`gate="blocking-human"`) that presents the record shape (§Q7) and the migration behaviour (§Q8) together. Fix `SettingsStore` passthrough in Wave 1 before anything writes version 2.

## Answers to the planner's questions

### Q1. `KernelBridge`: create/open, digest, submit, next ids, undo/redo, op shapes

All from `app/src/main/kernel-bridge.ts @8c4e219` [VERIFIED: read this session]:

- `create(path, worldName)` (:141-147) calls `TapestryAddon.create`, then closes any previous kernel, then sets `openPath`. The kernel refuses an existing file: the sink opens with `O_CREAT | O_EXCL` [VERIFIED: tapestry/kernel/journal/Sink.cpp:119 @8c4e219, `flags |= O_CREAT | O_EXCL;`]. **The kernel does not create parent directories**, so main must `mkdirSync(dir, { recursive: true })` first. `worldName` must be one token (`Kernel.cpp` `checkWorldName`: "world name is not one token"), so `Forest` and `Tapestry` are valid and `My Forest` is not.
- `open(path)` (:155-165) replays the whole journal. It **does not throw on a damaged journal**. `Kernel::fromJournal` marks it corrupt and returns (`Kernel.cpp` :94-112). Callers must check `status().kind === 'Ok'`, as `TreeRegistry.tryOpen` does (:230-247). A second open of a locked file throws `"another process holds the journal lock"` [VERIFIED: Journal.cpp:57 @8c4e219]. flock is per open file description, so **a second `KernelBridge` in the same process also gets `locked`** [VERIFIED: registry.test.ts:324-340 comment and test @8c4e219].
- `close()` (:173-185) releases the flock deterministically. It must be called for the forest and Tapestry bridges at `will-quit` (today only `registry.closeAll()` runs there, `index.ts` :721-727).
- `submit(actorKind, actorId, message, ops)` (:190-207) **throws** `'Cannot commit while history is rewound; redo to the latest change or discard the undo first'` when `currentSeq !== getLastSeq()`. It returns `CommitResult { seq, digest, nodeIds, edgeIds }` (:57-62). `submitAs(actor, message, ops)` (:216-218) is the preferred form. The kernel also refuses an actor kind outside `human|plugin|system`, a non-token id, and a message over the line limit (`Kernel.cpp` :123-133).
- `getHeaderDigest()` (:268-271) returns `sha256:<hex>`, the registry's tree id.
- `getNextIds()` (:280-286) returns `{ node: string; edge: string }` and **throws while rewound**. Within one submit the kernel assigns ids sequentially (`World::prepare` sets `create.id = m_nextNode` and `apply` advances it; ops are prepared and applied one at a time in `Kernel::submit`). A commit creating k nodes gets `n<N>..n<N+k-1>`. Verify with `result.nodeIds` as `notes.ts createFrom` does (:312-319).
- `undo()` / `redo()` / `discardRedo()` (:314-358) are the replay-position stack. `kernel:undo`/`kernel:redo` IPC resolve the tree through `resolveTree`, so **a bridge that is not in the registry can never be undone from the renderer**. That is what D-09 needs.
- `getNodes()`/`getEdges()` return `NodeData { id, type, props }` / `EdgeData { id, from, to, label, props }`, with `props: Record<string, { type: string; value: string | number | boolean }>` (:64-76).

**Op object shapes** (parsed in `app/native/addon.cpp` `jsToOp` :245-331 @8c4e219) [VERIFIED: read this session]. The verbs, quoted verbatim from the source: `"createNode"`, `"setProperty"`, `"unsetProperty"`, `"createEdge"`, `"deleteNode"`, `"deleteEdge"`, `"advance"`. Field names quoted from `requireString(env, jsOp, "<name>", …)`: `type`, `props`, `target`, `key`, `value`, `from`, `to`, `label`, `id`, `ticks`.

```ts
// Source: app/native/addon.cpp jsToOp @8c4e219
{ op: 'createNode', type: 'tapestry.spaces/space@1', props: { title: { type: 'text', value: 'Forest' } } }
{ op: 'createEdge', from: 'n1', to: 'n2', label: 'placement',
  props: { 'origin.x': { type: 'real', value: -245.01 }, 'origin.y': { type: 'real', value: -65.5 } } }
{ op: 'setProperty', target: 'e1', key: 'origin.x', type: 'real', value: 40 }   // target 'n<k>' or 'e<k>'

```
(The type string, keys and label above are illustrations of shape only. Their final names are the #17 checkpoint's decision.)

Value types accepted by `jsToValue` (:139-173), quoted: `"text"`, `"ref"`, `"time"`, `"int"`, `"real"`, `"bool"`. **An untyped JS number is inferred as `int` when it is integral** (`jsToValueInferred` :179-196). **Always pass `{ type: 'real', value }` for `origin.*`**, or a drag that lands on a whole pixel writes `int` and the file mixes types (Pitfall 3). `setProperty` has no inferred form: `type` is required (:266).

Kernel rules that matter here [VERIFIED: tapestry/kernel/Ops.hpp, World.cpp @8c4e219]:
- `isValidKey`: *"A property key: [A-Za-z_][A-Za-z0-9_.:-]*"* (Ops.hpp :124-143).
- Node type and edge label: `isToken` (non-empty, no byte < 0x20, no 0x7F, no space), valid UTF-8, ≤ 1 MiB (World.cpp :179-185, :226-231).
- `delete-node`: *"removes a live node and every edge that touches it"* (Ops.hpp :73-80, World.cpp `apply` :295-307).
- `ref` values must name a **live node or edge in the same world** (World.cpp `checkValue`: *"refs must name a node or edge that is live right now"*). A cross-file reference must be `text`.
- `unsetProperty` of an absent key is refused (`UnknownTarget … has no property`).
- Inline text ≤ 80 bytes, otherwise a `<<TEXT` block (FORMAT.md "Value types"). A `sha256:` digest is 71 bytes and stays inline. Long paths become blocks, which is still readable.

### Q2. `TreeRegistry`: how trees open, and how to keep the forest out of it

From `app/src/main/trees/registry.ts @8c4e219` [VERIFIED: read this session]:

- `TreeKind`, quoted: `export type TreeKind = 'native' | 'vault'` (:44). `UnavailableStatus`, quoted: `export type UnavailableStatus = 'damaged' | 'locked' | 'missing'` (:61).
- `open(path, opts)` (:174-182) and `create(path, worldName, opts)` (:185-193) return the existing entry for an already-open path, otherwise open a new `KernelBridge` and call `adopt`.
- `tryOpen(path, opts)` (:210-253): `existsSync` check → `missing`; open throws → `classifyOpenFailure` (`/journal lock|\blocked\b/i` → `locked`, else `damaged`); `status().kind !== 'Ok'` → closes the bridge and records `damaged`. On success it calls `adopt` and **deletes the stale `path:` record**. It returns `OpenTree | UnavailableTree`. **An identity clash still throws** (:206-208).
- `unavailableId(resolvedPath)` returns `` `path:${resolvedPath}` `` (:112-114). It is in memory only (`unavailable: Map`).
- `adopt(bridge, target, opts)` (:303-331) sets `id = bridge.getHeaderDigest()` and throws `` `${clash.name} is already open from ${clash.path}` `` when the digest is already open. It sets `primaryId` for native trees and emits.
- `reopen(treeId)` (:262-272) drops the unavailable record and calls `tryOpen` again with the same kind, name and vaultRoot.
- `close(treeId)` (:343-361) handles both kinds. `closeAll()` (:363-376).
- `summary()` (:443-466) lists open trees (status `'ok'`) followed by unavailable ones (status + reason). The doc comment says frames live in settings. That comment must change.
- `primaryBridgeProxy()` (:477-500) forwards to `primary()`, the last native tree. `resolveRef()` (:509-520) matches id, then case-insensitive name. **These two are the only doors plugins and agents have** (`index.ts` `loadPluginsSafely`, `NoteCommands(registry, …)`).

**Recommendation: hold the Tapestry and forest bridges outside the registry.** A `SpaceService` constructs its own `KernelBridge`s, so `list()`, `summary()`, `primary()`, `resolveRef()` and `lastNativeId()` cannot see them. Add one guard to the registry, or to the `trees:open`/`trees:create` handlers: **refuse a path, or a digest after opening, equal to the forest's or the Tapestry tree's.** Without it, "Open tree…" on `Forest.tree` fails as `locked` with the copy "This tree is open in another Tapestry window", which is wrong. Suggested refusal copy: "Forest.tree is Tapestry's own arrangement file and can't be added as a tree." This copy is new user-visible text, so check it against the UI-SPEC copy tone.

```ts
const result = forest.submitAs(actor, `add tree "${name}"`, ops)
if (result.nodeIds[0] !== next.node) throw new Error(`expected ${next.node}, kernel issued ${result.nodeIds[0]}`)
```
For k nodes in one commit (migration), compute `n<N+i>` from `next.node` with a single helper, and verify all of `result.nodeIds`. Phase 3's branch-tagged ids (`b2.n12`, FORMAT.md "Identifiers") will break naive arithmetic, so keep it in one function.

### Pattern 2: Member identity resolution
- A registry entry with a digest id (open tree): find the stand-in whose `digest` equals it. If none, find the one whose `path.hint` equals the entry's path **and** has no `digest`. If none, the tree is not a member.
- A registry entry with a `path:` id (unavailable): find the stand-in whose `path.hint` equals the path.
- When opening path P yields digest D, and stand-in S has `digest == D` but `path.hint != P`: reuse S and `setProperty path.hint` in the **same** commit as the user action (Discretion). If S's tree is already open from another path, `adopt` throws "already open from", and nothing is written.
- When the stand-in has `digest == D1` but the file at `path.hint` opens with D2 ≠ D1: **a different world now sits at that path.** Do not adopt it as this member. Close the bridge, and report the member as `missing` with a reason naming the mismatch (Pitfall 5).
- The renderer keeps using registry ids (digest or `path:`). Nothing new crosses IPC as an identity, so no `path:` id is ever written (D-03).

### Pattern 3: Compensating frame undo (D-09)
Main keeps an in-memory stack `{ commitSeq, entries: [{ edgeId, before: {x,y}, after: {x,y} }] }`, where `before` is **read from the forest** before writing `moveFrames`, never taken from the renderer. `undoFrames()` pops one entry. For each edge that is still live and whose current origin equals `after`, it writes `before`. Edges moved since then (for example by a system fit) are skipped. Everything happens in one human commit. It returns what changed so the renderer can refresh. Redo, if wanted, uses the mirror stack (Open Question 2).

### Anti-Patterns to Avoid
- **Putting the forest in `TreeRegistry`:** it leaks to `primaryBridgeProxy`, so plugins could write into it, and to `resolveRef`, so agents could name it.
- **`kernel:undo` on the forest:** it rewinds, and the next drag then throws (D-09).
- **Untyped numbers in props:** `origin.x` written as `int` (Pitfall 3).
- **Writing a `path:` id or a guessed digest to disk** (D-03).
- **Committing on every launch:** the fit must compare before writing, and the digest write must happen only when absent (D-12).
- **Calling `settings.update()` with the v1 `read()`:** it drops the pointer (Pitfall 1).
- **Naming the module `commands/forest.ts` or the class `ForestCommands`:** that collides with 2.2 Plan 15.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Durable, attributed layout storage | A JSON layout file or a SQLite table | The `.tree` journal via `KernelBridge.submitAs` | Actor, history, replay and readability for free, and the core value requires it |
| Cascade on close | `deleteEdge` then `deleteNode` | A single `deleteNode` (the kernel cascades) | Fewer lines. The kernel's history index already records the cascaded edge |
| Tree identity | A new UUID property | `getHeaderDigest()` | Enforced by the digest chain (spec §5). Already the registry id |
| Frame geometry | New overlap math | `frames.ts` `pushApart` / `placeNewFrame` / `computeFrameBounds` | Deterministic, tested (`frames.test.ts`) |
| Atomic settings write | fs code | `SettingsStore.write` (tmp + rename) | Already crash-safe |
| Locked/damaged/missing detection | Custom probes | `TreeRegistry.tryOpen` | Its classifications are tested (registry.test.ts) |

**Key insight:** the kernel already expresses everything. Every new line of 2.6 code is either wiring or a policy decision, and the policies (identity, migration, undo) are where bugs will live, so they belong in small pure or testable units.

## Common Pitfalls

### Pitfall 1: `SettingsStore.update()` silently deletes the pointer and "cleans" the backup
**What goes wrong:** after the migration, `setUserName` or `agents:setEnabled` rewrites settings from `read()`. `read()` returns only `version: 1, userName, agentsEnabled, trees` (validated), so the pointer vanishes and malformed `trees` entries disappear.
**Why it happens:** `read()` is a whitelist (settings.ts :123-153), and `update()` is `write(mutator(read()))`.
**How to avoid:** passthrough of the raw `trees` value and unknown keys, and `version` read from the file. Test: write a v2 file with an extra key and a malformed tree entry, call `setUserName`, and assert the key and the raw `trees` bytes (as JSON) are unchanged.
**Warning signs:** a second launch re-runs the migration (case B).

### Pitfall 2: The forest leaks to plugins or agents
**What goes wrong:** a plugin's `context.kernel.submit` or an agent's `create_note` lands in `Forest.tree`.
**How to avoid:** keep the forest bridges outside `TreeRegistry`. Test: after `space.start`, `registry.list()`, `summary()`, `primary()` and `resolveRef('Forest')` do not include the forest.

### Pitfall 3: Integer origins
**What goes wrong:** a JS number with no explicit type is inferred as `int` when integral (`addon.cpp` `jsToValueInferred`), so `origin.x int 0` and `origin.x real 12.5` both appear in the file.
**How to avoid:** always `{ type: 'real', value }`. Test: add a member at (0,0) and assert `getEdges()[0].props['origin.x'].type === 'real'`.

### Pitfall 4: Adding `Forest.tree` or `Tapestry.tree` as a member
**What goes wrong:** `tryOpen` hits our own flock, so the frame says "open in another Tapestry window".
**How to avoid:** a reserved-path check (resolve and realpath) before `tryOpen`, and a digest check after it. Return a clear error.

### Pitfall 5: A different world at a member's path
**What goes wrong:** `bega.tree` was replaced by another world. Adopting it by path would give the old frame to a new identity (the copy problem 2.2 `adopt()` guards against).
**How to avoid:** compare the stored `digest` with the opened digest. On mismatch, report the member unavailable and keep the stand-in untouched.

### Pitfall 6: Several builds share one `userData`
**What goes wrong:** `~/Tapestry` (2.2) and this worktree build the same app name, so an older build rewrites `settings.json` without the pointer and keeps editing `trees`. Two running instances also fight over flocks.
**How to avoid:** case B (reuse the existing default `Tapestry.tree`, never re-import blindly) and case G (locked). Say this at the human-verify step. Consider a dev-only `userData` override if Kaelen wants the builds separate (not in scope).

### Pitfall 7: Launch writes history although nothing moved (D-12)
**What goes wrong:** the placement-correction effect fires with minimum-size rects before nodes load. If it moves a frame on every launch, history fills up.
**How to avoid:** main writes a fit only when the value differs, and the renderer's fit is deterministic from the stored origins. Test: running the fit twice commits once. Also consider allowing one fit per member per session in main (threat T-2.6-03).

### Pitfall 8: `getNextIds()` while the forest is rewound
**What goes wrong:** it throws.
**How to avoid:** never call `undo()` on the forest bridge. Assert `!forest.isRewound` in `SpaceService`.

### Pitfall 9: Vault members at launch
**What goes wrong:** main at `8c4e219` skips `kind !== 'native'` during restore, so a migrated vault member would show nothing. It would not even appear as unavailable, because it was never `tryOpen`ed.
**How to avoid:** keep that behaviour (skip) until 2.2 Plan 08's `vaultService.openVault` lands on main, then route vault members through it. Keep the vault member in the forest either way, and don't drop it from `trees:list` silently. Decide at planning whether a skipped vault member is listed. Recommended: follow whatever main does at merge time.

### Pitfall 10: Two stand-ins, one digest
**What goes wrong:** a file was added twice by path before its digest was known, so the forest has two members that turn out to be one world.
**How to avoid:** in the first-open digest commit, if another stand-in already has D, keep the older one and `deleteNode` the newer one in the same `system` commit. Otherwise the second `tryOpen` throws "already open from" and its frame disappears from `summary()`.
