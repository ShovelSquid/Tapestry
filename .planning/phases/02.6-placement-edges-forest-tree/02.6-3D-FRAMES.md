Nothing here changes the 2.6 plans: frames still write only `origin.x` and

**Builds on:** `~/Tree/Connections/Spec - Placement Edges.md` §1–§3 and §8,

## The gap this closes

The placement spec gives every placed thing seven readable reals:
`origin.x/y/z`, `direction.x/y/z` and `roll`. 2.3 already writes the same
seven reals on threads (as `thread.origin.*`, `thread.direction.*` and
`thread.roll`). **But nothing defines what the numbers mean.** Which way does
z point? What is `roll` measured from? What happens when a canvas faces
straight up or down? Today it doesn't matter, because every value is the
default. It will matter the first time anything is tilted, and by then
history is append-only. So the definition should be settled before 02.6-02
approves the key names. It is one paragraph of the reader's guide, and it
costs no code in 2.6.

## 1. One chart for every space

**Every space uses the same coordinates: x is east (screen right), y is
south (screen down), and z is up, toward a viewer looking down at the
ground.** Depth is −z.

- Every number already on disk keeps its meaning. Canvas positions are
  DOM-style y-down, and D-27's default direction `0 0 -1` travels "into
  depth", which is downward in this chart.
- **Today's canvas is the ground plane at z = 0, seen from above.** That is
  what `Concept - Surfaces` asks for ("keep a canonical ground plane where
  the 2D canvas is today"). It also makes `Concept - Spatial Z-Depth`
  literal: child notes sit lower in z, and you fly down to them.
- **There is no separate 2D chart.** A canvas is a space whose contents
  happen to sit at z = 0 and whose preferred view is square-on. Nothing
  converts between 2D and 3D. This follows the mathspace rule that
  dimension is data, not a type (No Special Cases). `kind` stays a renderer
  hint, as the spec says.
- This chart is left-handed. That does no harm because §2 defines every
  axis by an explicit formula, not by a handedness convention, and the
  resulting transform is always a proper rotation.

## 2. What a placement's seven reals mean

A placement maps a point `(u, v, w)` in the placed thing's own coordinates
into the parent space:

```
p = origin + u·R + v·D − w·F
```

- **`F` (forward) = `direction`**, normalized on read, with zero read as
  the default. It is the way you look when you are square-on to a surface,
  reading it, and the way a thread travels.
- **`D` (down)** is the reference direction projected perpendicular to F,
  then normalized:
  - the reference is **world down, `0 0 -1`**, so a painting hung on a
    wall keeps its top edge up;
  - **except** when F is exactly vertical as written (`direction.x` and
    `direction.y` are both 0: floors, ceilings and today's default). Then
    the reference is **south, `0 1 0`**, so the default placement is the
    identity.
- **`R` (right) = F × D**, as an ordinary component cross product.
- **`roll`**, in degrees, turns R toward D (clockwise as the viewer sees
  it): `R' = cos r·R + sin r·D`, `D' = cos r·D − sin r·R`.

Checks: the default (`0 0 -1`, roll 0) gives R = +x, D = +y and −F = +z,
which is exactly the identity, so every existing layout is unchanged. A
canvas hung on the north wall (`0 -1 0`) gives R = east and D = world down.

**Why forward plus roll, not a quaternion, a matrix or an up vector:** this
is D-27's reasoning, and it still holds. `0 -1 0, roll 10` reads as "faces
north, tilted ten degrees". Any direction-plus-roll scheme needs one
fallback case, and this definition puts it where a person would put it
(floors and ceilings), triggered only by exact zeros that the file shows.
The snapping UI writes exact zeros, so nearly vertical values stay under
the first rule and remain well defined.

**Units and scale:** one unit in a placed thing is one unit in its parent,
with no `scale` key. A canvas hung in a room is as large as its contents.
Mathspace makes the same call ("world units; a unit scale on the Space is
the user's choice"); the name `scale` stays free if it is ever needed.
`size.w` and `size.h` are in the placed thing's own units.

**Nesting:** a thing's position in the world is the placements along its
chain, composed at render time. The recursion cap stays at 1 (World
Contains Its Controls). A thing placed in several spaces is drawn once in
each.

## 3. Principles taken from the physics engine

The physics engine (mathspace) and Tapestry already share a kernel. Five of
its rules carry over directly:

1. **Geometry is data.** No code knows what a wall or a floor is. "Up"
   exists only as the roll reference in §2. Gravity or snap-to-wall
   behaviour, if it ever exists, is a rule note, not renderer code.
2. **View state never enters history.** The camera, the zoom, which surface
   you are "in", and the square-on snap are all view state and are never
   recorded. The one exception is a *saved viewpoint*, an ordinary node
   placed in a space with the same seven reals plus a span. It is written
   only when a person saves one, like mathspace's View note.
3. **Rendering reads and never writes.** World matrices are computed in
   floats at draw time. Only the seven readable reals are stored, never a
   derived matrix.
4. **One function turns a hit into coordinates, and the result is what gets
   recorded.** "Put this on that wall" means a ray-plane hit becomes local
   `(u, v)` through one main-process function, and those numbers are
   written. Replay reads the numbers and never re-derives them, which is
   the project's rule that replay uses recorded outcomes.
5. **Layout helpers are constraints.** `frames.ts` `pushApart` is a
   hard-coded non-overlap constraint. In mathspace terms it is a pair rule.
   Nothing changes now, but new arrangement behaviour (keep frames apart,
   hang on the nearest wall) should be built as rules the person can read
   and switch off, not as more special cases in the renderer.

## 4. Navigation

**One camera model, and it is a placement.** The camera is `origin`,
`direction`, `roll` and a field of view. "Square-on to a surface" means the
camera's F and roll equal the surface's. **In that state the surface is
drawn exactly as the app draws it today**, with the CSS `translate` and
`scale` and crisp DOM text. Zoom and distance are the same number:
`zoom = (viewportHeight / 2) / (distance · tan(fov / 2))`. The 3D camera is
a strict superset of today's view, and its resting state is today's app.

The recommended behaviour:

- **Zoom out of a surface into its parent.** Past a canvas's minimum zoom,
  the camera lifts out instead of clamping. You then see the canvas as a
  plane among others: trees in the forest, a painting in its room. Zooming
  into a plane flies square-on and lands in it. Depth in the placement tree
  becomes the zoom level, so no mode is needed. This is Surfaces' "there is
  only a frame you are in".
- **Square-on is an attractor.** A tilt gesture leaves it. Releasing near
  square snaps back. Spike 011's gravity rules apply: the pull is scaled by
  frame time and is suppressed while the hand is moving or during a fly.
- **Edit only square-on.** Clicking into a note on a tilted surface flies
  square-on first. That keeps ProseMirror, IME and selection on flat DOM,
  which is the only place they are proven. Tilted notes draw as DOM with a
  CSS `matrix3d` matched to the three.js camera: readable, not editable.
- **Zoom is a span, not a factor** (spike 011): the units across the
  window. It makes "text is readable here" (about 8 px per em) a threshold
  for level of detail: full note, card, then dot.
- **Getting around:** fly to anything by name (tree and note titles); a
  back and forward view history kept in memory like a browser's, not
  recorded; zoom to fit; and saved viewpoints as the durable addresses
  Surfaces calls for.
- **The camera rolls, and up is not forced** (Kaelen, 2026-09-24). The
  camera's `roll` is its own, separate from the surface's. Rolling while
  square-on turns the canvas on screen, the way you turn paper under a
  pen. In free flight the horizon is never levelled automatically. The
  gestures are a trackpad rotate, Shift+wheel, or `Q`/`E`. There is a
  light snap to the surface's own roll and to quarter turns (within about
  ±4°) under spike 011's rules. It is suppressed while the hand is
  turning, so any angle can be held. `0` resets. Camera roll is view state
  and is not recorded. A saved viewpoint keeps it, because a viewpoint is
  a placement.
- **The camera eases toward its target** (Kaelen, 2026-09-24). Input moves
  a *target* camera, and the drawn camera chases it with frame-rate
  independent exponential smoothing:
  `k = 1 − exp(−dt / τ)`, `current += (target − current) · k`.
  - Position is eased linearly. Zoom is eased in log space, so each
    doubling takes the same time. Orientation uses slerp internally (a
    quaternion in memory only; the file keeps direction and roll).
  - **Direct manipulation is never eased.** A drag or a two-finger pan
    stays 1:1 under the hand (τ = 0), because lag under the finger feels
    like the app fighting you (spike 011). Easing applies to wheel
    notches, pinch and zoom steps (τ ≈ 60–90 ms), fly-to and zoom-to-fit
    (τ ≈ 150–250 ms), and snaps and roll (τ ≈ 80 ms).
  - Zoom stays anchored at the cursor by computing the anchor against the
    *target* camera, so a burst of wheel notches doesn't drift.
  - Hit-testing uses the *drawn* camera, so a click lands where the
    content appears.
  - It settles when the error falls below half a pixel and 0.05°, and then
    the camera stops animating so the page can idle.
- **Rendering route:** 2.3's split. three.js (already a 2.3 dependency)
  draws spaces, frame planes and threads; DOM carries every note you can
  type into; and with no WebGL the app degrades to today's 2D canvas.
