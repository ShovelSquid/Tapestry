# Phase 2.2: Obsidian Bridge - Context

**Gathered:** 2026-09-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Outside writers reach a Tapestry world through one shared set of note and connection commands. Two writers use those commands in this phase, in this order:

1. **Agent bridge (first):** an MCP server that lets Claude, ChatGPT or any other agent read notes, create notes grown from existing notes, connect notes, and write to the source. Every agent is visibly and distinctly attributed.
2. **Obsidian bridge (second, on the same commands):** an Obsidian vault becomes its own tree. That tree faithfully records what the vault's files actually contain. Edits made in Tapestry go out to the files, and edits made in Obsidian come in with honest provenance. Tapestry shows several trees in one space, each in its own frame.

The roadmap entry for 2.2 still describes only the Obsidian half. Reword its goal (via `/gsd-phase edit`) to cover both halves (D-01).

Not in this phase: time threads, the z-axis live writing interface (Phase 2.3, D-02); branch merging and branch navigation (Phase 3); an AI that organizes notes for you (Phase 6 companion).

</domain>

<decisions>
## Implementation Decisions

### Scope and sequence
- **D-01:** Phase 2.2 covers both the agent bridge and the Obsidian bridge. Build one shared note/connection command set, expose it to agents over MCP first, then build Obsidian sync on the same commands.
- **D-02:** Time threads are out of 2.2 and become their own Phase 2.3, directly after 2.2. The 2.2 agent tools must not rule out writing into threads later. Time threads keep the name "thread". Phase 2.1's connection-with-a-centre-note (`thread-center` / `thread-arm`) gets renamed, and the new name is chosen in the 2.3 discussion. — **Reversibility:** costly — the rename touches 2.1's renderer components, node/edge type names and any worlds already written with them.

### Agent bridge
- **D-03:** An MCP server gives any agent (Claude, ChatGPT, others) a small, clear set of tools for reading, creating notes, connecting notes and writing to the source. The SDK's namespaced `CommandContribution` is the natural base for those tools.
- **D-04:** Every note an agent creates must name an existing note it grows from, written by a human or an agent, and is created already connected to it. Agents can never create loose notes. The bridge enforces this, not the agent.
- **D-05:** Agents may read any note and draw connections to any note, but may edit or delete only notes they wrote. Authorship comes from the actor on the commit that created the note.
- **D-06:** Agent commits read `actor plugin agent.<name>` (for example `agent.claude`, `agent.chatgpt`). Agents must be distinguishable from each other, because Kaelen says agents and avatars are a core part of the roadmap. There is no `.tree` format change. The bridge stamps the agent id itself: an agent cannot choose it and can never write as a human. — **Reversibility:** costly — actor ids are written into append-only history and cannot be rewritten later, so a different scheme would leave old commits in the old form.
- **D-07:** Human commits read `actor human user.<name>`, for Kaelen `actor human user.kaelen`. This replaces today's `actor human local` (all 390 commits in `~/Documents/we.tree`). Existing `local` lines remain valid history. — **Reversibility:** costly — same reason as D-06.
- **D-08:** Agents get tools that write to the source itself (the vault's `.md` files), and the vault tree records the result. D-04 and D-05 still apply.
- **D-09:** Agents may write to the source while Tapestry is closed. The bridge appends each write to a small, readable sign-in log (who changed what, when). When Tapestry catches up, it reads the log and attributes those edits to the right `agent.<name>`. Changes not in the log are treated as observed, author unknown (D-21).

### Source of truth and trees
- **D-10:** **Source-mirror model.** Each outside source is its own tree: the Obsidian vault now, and later other apps and devices through plugins. That tree is an append-only record of what the source actually contains, and Tapestry never keeps a diverging version. Both Tapestry and Obsidian are places to edit: a Tapestry edit is sent out to the source, and the tree then records what the source says. In Kaelen's words: "there should be immutable representations of that data. tapestry can output to change that data, but it should always only represent what that actual data is. this is because plugins will be used for all manner of different apps and devices, and needs to be able to reflect accurate informaion. These inputs should be displayed in different trees perhaps, which makes up the forest." — **Reversibility:** one-way — every later source plugin, the vault tree's record shapes, and D-11/D-14/D-16 all depend on this model.
- **D-11:** No merging. If a note changed in both Tapestry and the file before the bridge caught up, the file wins. The losing Tapestry edit stays in history and can be accessed later; no separate "attempt" object or re-send is needed.
- **D-12:** Notes written inside Tapestry keep today's editor JSON in `.tree`. A vault tree stores each `.md` file's text exactly as it is in the file. JSON is converted to Markdown only when a Tapestry-native note is written out to the vault (for example, by copying it into the vault frame, D-17). Kaelen chose this over storing Markdown everywhere, which Claude had recommended.
- **D-13:** The vault's tree file lives inside the vault folder, for example `~/House Party/House Party.tree`, so the vault and its history travel together.
- **D-14:** What Tapestry adds about vault notes (positions, Kaelen's own short connection labels, authorship) is stored in the vault tree, clearly marked as Tapestry's and kept apart from the mirrored file content. These additions never touch the `.md` files. Exception: connections drawn between vault notes are source data and go to the file (D-32).
- **D-15:** Tapestry shows several trees in one space. Each tree sits in its own named frame, like an island. A frame moves as a whole, notes stay inside their tree's frame, and trees never overlap.
- **D-16:** A connection between notes in different trees is recorded in both trees. Each tree records its own end, naming the other tree and note, so either tree opened alone shows that the link leads elsewhere. More generally, a change one tree makes to another is recorded within the trees it touches. — **Reversibility:** costly — the cross-tree reference shape is written into every affected journal.
- **D-17:** Dragging a note into another tree's frame creates a copy there, connected back to the original. Nothing disappears from its source tree.
- **D-18:** Tapestry remembers which trees were open in the space, and where their frames sat, and reopens them on the next launch. This lives in app settings; there is no forest file. Kaelen chose this over a readable forest file.

### Syncing
- **D-19:** The first vault to build and test against is House Party (`~/House Party/`): 13 character notes plus lore notes, plain `[[links]]` and `#tags`, in active use. Other Claude sessions currently edit its `.md` files directly, which makes it a real test of the unknown-author path (D-21).
- **D-20:** While Tapestry is open it watches the vault live and records changes within moments. On opening, it catches up on everything that changed while it was closed.
- **D-21:** A file change with no known author is recorded as `actor plugin obsidian.bridge` with a message like `observed change to Rody.md`. Tapestry never guesses the author. Edits that go through the bridge's agent tools carry `agent.<name>` because the bridge knows who made them (D-09).
- **D-22:** Tapestry writes edits to vault notes about a second after typing pauses, so Obsidian sees words and sentences, not every keystroke.
- **D-23:** Changes Tapestry notices within the same moment are grouped into one history entry listing every changed file, and they undo together. Kaelen chose this over one entry per file.
- **D-24:** A file renamed in Obsidian stays the same note under a new name: its position, connections and history remain, and the rename is recorded. The link rewrites Obsidian makes in other files are recorded as observed changes, grouped per D-23.
- **D-25:** A file deleted from the vault removes its note from the frame and cuts its connections, including cross-tree ones. The other trees record the cut too. Everything stays in history and can be restored. This is consistent with Phase 2 D-20: deleting a container removes its connections.
- **D-26:** Vault folders (such as `Characters/`) appear as labeled groups inside the vault's frame, and notes can be arranged within a group. Moving a note to another group moves its file to that folder, which is a write to the source.
- **D-27:** A new note created inside the vault frame becomes `Title.md` in the folder of the group it was placed in (for example `Characters/Luna.md`). An untitled note is `Untitled.md` until it gets a title.
- **D-28:** A vault note's title and file name are always the same, as in Obsidian, so retitling a note in Tapestry renames its file.
- **D-29:** Non-Markdown files in the vault (images, PDFs, `.canvas`) appear as file notes showing the name, the type and a link to open the file. The file's bytes are not copied into the tree. Embeds like `![[map.png]]` become connections to the file note.

### Markdown ↔ notes mapping
- **D-30:** One `.md` file is one note.
- **D-31:** A `[[link]]` becomes a connection labeled with the actual line it sits in, for example `Best friends with [[Max]]` in `Rody.md`. Tapestry never extracts or guesses a shorter label. Kaelen may add a short label in Tapestry, stored as Tapestry's (D-14).
- **D-32:** A connection drawn in Tapestry between two vault notes adds a `[[link]]` line to the source note: `[[Max]]`, or `best friends with [[Max]]` when a label was given. Obsidian sees the link. This refines D-14.
- **D-33:** `#tags` and frontmatter become readable, filterable properties on the note (for example `tags: Guy`). The file text is unchanged.
- **D-34:** A link to a note that doesn't exist yet (such as `[[create a link]]` in `Welcome.md`) shows as a faint, empty placeholder note connected to the link. Typing in the placeholder creates the `.md` file.

### Claude's Discretion
- The exact MCP tool list, within D-03, D-04, D-05 and D-08.
- MCP transport, and how the server reaches the kernel given the single-writer journal lock and `KernelBridge.submit` living in the Electron main process. This includes writes to Tapestry-native trees (not vault files) while the app is closed. Research must propose a design consistent with D-06 and D-09.
- Where the agent sign-in log lives and its readable format. It must be readable without Tapestry.
- How Tapestry tells its own `.md` writes apart from outside edits, and what counts as "the same moment" for grouping (D-23).
- Where the app gets the user name for `user.<name>` (D-07).

### Open for research and planning to propose (not discussed; bring back to Kaelen if a choice is visible to users)
- What a Tapestry-native note loses when written to the vault (text color, font, alignment) under D-12 and D-17. Kaelen's own notes must never be silently degraded.
- Whether a cross-tree connection (D-16) also appears in a vault note's `.md`, given that Obsidian cannot resolve a link into another tree.
- How Phase 2.1 passage-level links map to Obsidian. Neither of Kaelen's vaults uses block references (`^id`), embeds or `.canvas`.
- Whether Tapestry shows backlinks the way the Tapestry Tales vault now does.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `KernelBridge.submit` (app/src/main/kernel-bridge.ts): the one durable write path. Agent tools and the vault watcher must both end in validated, attributed commits through it or an equivalent kernel instance.
- `CommandContribution` (sdk/src/contributions.ts) and plugin-host command execution (app/src/main/plugin-host.ts, around line 762): existing namespaced command registry and invocation over IPC, a candidate for the shared note/connection command set.
- Journal durability (tapestry/kernel/journal): append-only SHA-256 chain, flock single writer, torn-tail repair. Fits D-10 (append-only, never rewritten) directly.
- Plugin lifecycle and failure containment (Phase 2 D-33..D-35): the Obsidian bridge and agent bridge should run as plugins, so a missing bridge never stops a world opening.

### Established Patterns
- All mutations go through `Kernel::submit` with an actor; scratch-copy-then-swap atomicity.
- Content deletion vs structure deletion (Phase 2 D-20); D-25 follows it.
- Autosave with debounce already exists for note typing (Phase 2 D-02); D-22 adds a similar pause before writing `.md`.
- Unknown plugin node types and properties survive in `.tree` with readable fallbacks (Phase 1); vault-mirror entries and Tapestry-added entries (D-14) can use namespaced types and properties.

### Integration Points
- The kernel bridge holds a single kernel/world today. D-15 (several trees in one space) needs one journal per tree and a renderer canvas that draws several framed worlds.
- No file watching or Markdown code exists yet: no `fs.watch`, `chokidar`, Markdown or wikilink handling found in `app/`, `sdk/` or `plugins/`.
- Actor enforcement: plugin-host passes actor kind and id straight through. The bridge needs host-side stamping (D-06) and a check that plugins cannot submit as `human`.
- The renderer currently sends `human` with id `local`; D-07 changes where that id comes from.

</code_context>
