**Trees are added from the forest bar and closed or revealed from each frame's Tree options menu, and a tree that will not open — damaged, locked by another Tapestry, or missing — stays in the space as a dashed frame carrying the kernel's own reason and a way forward, instead of silently disappearing or being silently repaired.**

## Accomplishments

- **A tree that will not open is a member of the space, not an absence.** `tryOpen` classifies `missing` (no file), `locked` (another Tapestry holds the journal lock) and `damaged` (any other open failure, or a journal that opened with a status other than `Ok`), and keeps the entry listed with the kernel's own words until Kaelen chooses Close tree. This is T-02.2-32 — a frame that vanished when a file moved would be indistinguishable from a world that was lost.
- **A damaged journal is closed again immediately and never written to.** When `status().kind` is not `Ok` the bridge is released before the tree is ever adopted, so no handle exists through which anything could append. Nothing is repaired: the test asserts the file's size is unchanged, and that a later opener can still take the lock — which is what leaves an explicit repair possible.
- **The refusal has one home.** `refusalFor(id)` is the single place a write is refused for naming an unavailable tree, and `resolveTree` consults it *before* the id-shape check, so a damaged tree is refused as damaged rather than as "unknown tree" (T-02.2-29).
- **Failure classification reads the kernel, not the plan's assumption.** The plan specified matching an error "containing `locked`" — but the kernel's locked detail is "another process holds the journal lock", in which the word `locked` never appears. Had that been implemented literally, every locked tree would have been mislabelled damaged. Caught because the test builds a genuinely locked fixture rather than a fake error string.
- **Two menus, one surface.** The forest bar's Add tree menu (arrow keys, Escape, focus returned to its button) is an ordered list so Plan 07 inserts `Add Obsidian Vault...` at its head and nothing else moves; each frame header's reserved right slot now holds the 32px icon-only Tree options button.
- **The space explains itself.** The empty canvas names the way in to a vault; frame names counter-scale below 0.72 zoom so a space full of frames does not become a space full of unreadable labels; and one polite plus one assertive live region carry to a screen reader what the dashed border only says visually.

## Decisions Made

See `key-decisions` in the frontmatter. The three worth repeating:

- **`list()` stayed `OpenTree[]`.** The plan said `list()` and `summary()` should both include unavailable entries, but `notes.ts` iterates `list()` and reads `.bridge` for `list_trees` and `search_notes`. Widening it would have handed the MCP tools trees with no bridge — a crash, or worse, an agent told a tree exists that it cannot read. Status is reported through `summary()`, which is what the renderer actually consumes.
- **A tree-identity clash is still an error, not a damaged frame.** Recording "the same world is already open from another path" as damage would be both untrue and sticky — it would sit in the space as a broken tree until closed.
- **`trees:open` returns `ok` for a tree that would not open.** It genuinely joined the space, as a frame with a reason. Returning an error would have produced a file picker that appeared to do nothing.

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `list()` could not include unavailable entries**
- **Found during:** Task 2
- **Issue:** The plan states "Registry methods list() and summary() include unavailable entries". `app/src/main/commands/notes.ts:413,452` calls `registry.list()` and then reads `tree.bridge`; an entry without a bridge fails typecheck and, if forced through, would hand an agent a tree it cannot read.

- **Files modified:** `app/src/main/trees/registry.ts`
- **Verification:** `registry.test.ts#lists unavailable entries...` asserts `list()` is empty while `summary()` holds the damaged entry; typecheck exit 0; 146/146 tests pass
- **Committed in:** `998c672`

**2. [Rule 1 - Bug] The plan's locked/missing detection would never have fired**
- **Found during:** Task 2
- **Issue:** The plan specifies "A thrown error containing `locked` becomes status locked" and "a detail naming `Missing`". Neither string exists: `Journal.cpp` reports a second writer as `another process holds the journal lock` (no "locked"), and its missing detail is the file path alone (no "Missing"). Implemented literally, every locked tree would have been reported damaged, which would then have refused writes for the wrong reason and offered the wrong way out (Show in Finder instead of Reopen tree).
- **Fix:** Locked is matched on the kernel's real phrase (`/journal lock|\blocked\b/i`, keeping the plan's word as an alternative in case the message changes); missing is decided by `existsSync`, as the plan's own first clause said. A comment in `classifyOpenFailure` records why the word itself is not matched.
- **Files modified:** `app/src/main/trees/registry.ts`
- **Verification:** `registry.test.ts#reports a tree already locked by another Tapestry as locked` builds a genuinely locked fixture (a second `KernelBridge` holding the path) rather than a synthetic error string, so it fails if the real message stops matching
- **Committed in:** `998c672`

**3. [Rule 3 - Blocking] A Plan 05 test asserted the summary shape this plan changes**
- **Found during:** Task 2
- **Issue:** `registry.test.ts#summarises open trees without their bridges` asserted the exact summary object, which necessarily broke when `summary()` gained the `status` field this plan requires.
- **Fix:** Updated that expectation to include `status: 'ok'`, with a comment recording why the field is now part of every summary. The file is in this plan's `files_modified`.
- **Verification:** 17/17 in `registry.test.ts`
- **Committed in:** `998c672`

**4. [Rule 1 - Bug] My own test expectation was wrong, not the implementation**
- **Found during:** Task 2
- **Issue:** The damaged-tree test asserted that reopening the truncated file would throw, while its own comment said the opposite. A torn journal *does* open — the kernel loads the verified prefix and refuses appends — so the assertion contradicted the kernel's documented behaviour.
- **Fix:** Inverted to `not.toThrow()` and added `expect(after.status().kind).not.toBe('Ok')`. This is the stronger assertion: the open succeeding is what proves the registry released the lock, and the non-Ok status proves the file is still the damaged one. Had a bridge been leaked, this now fails on the lock.
- **Committed in:** `998c672`
