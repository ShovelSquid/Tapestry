## Summary

This phase adds no kernel verb, no value type and no dependency. Every write is an ordinary `setProperty` (and at most one `unsetProperty`) commit submitted through `bridge.submitAs(actor, message, ops)`, the same path `createFrom` and `updateNote` already use. The keys it writes (`position.x`, `position.y`, `pinned`) already exist: `pinned` is the knot key that `App.tsx:304` writes as `type: 'bool'`. **Nothing in this phase needs a new `.tree` key, type string or edge label.** The one place that could tempt one, "follow any anchor", is already deferred by D-01.

The central design fact is that **three layers must agree on where a following note is**: main (for `look` relations and for D-09 collision checks), the renderer's frame bounds (`Canvas.tsx:258-272`), and the renderer's card and edge layers (`TreeFrame.tsx:110-163`, `NoteCard.tsx:135-136`). They can only agree deterministically if they call **one pure function**. The renderer's TypeScript config makes that impossible today: `tsconfig.web.json` has `"rootDir": "src/renderer"`, and I confirmed with the repo's own `tsc` 5.9.3 that a renderer file importing a file outside that root fails with `TS6059` even under `noEmit`. Phase 2.3's plan 02 (`02.3-02-PLAN.md:215`) already prescribes the fix: add `src/shared/**/*` to both `include` lists and widen the web `rootDir` to `src`. This phase should make **byte-identical** edits and put the geometry in `app/src/shared/placement/`, so the two branches converge rather than conflict.

The biggest environment finding: **the native addon is not built in this worktree** (`app/native/build` does not exist). Every kernel-backed vitest file fails to load. The full suite shows `Test Files 11 failed | 1 passed (12)`. Only `frames.test.ts` (13 tests) runs. Typecheck passes. Wave 0 must run `npm --prefix app run build:native` (a local cmake build, not a package install) before any command test can go green. `shim.test.ts` also needs `npm --prefix app run build:js`, and `app/out` does not exist either.

**Primary recommendation:** Build one pure, Electron-free module, `app/src/shared/placement/geometry.ts`, that owns the constants, the D-09/D-10 resolver, the relation classifier and `displayPositions()`. Main's `look` and later `place`, and the renderer's follow drawing, all call that module. Wave 1 ships `look`, the follow drawing and the drag takeover. Wave 2, which is blocked on the Phase 2.4 merge, ships `place` and `create_note`'s `where`.

## User Constraints (from CONTEXT.md)

### Locked Decisions

#### What a placement writes (Area 1)
- **D-01: A following note follows its `grew-from` parent, with no new key.** Every agent note already carries a `grew-from` edge to its parent (02.2 D-04, `notes.ts:45`, edge from child to parent). `place near <parent>` makes the note follow that parent. `place near X` for any other X, and every `beyond`, writes a **fixed** position. Widening "follow" to arbitrary anchors needs a new key or label, which is a one-way door (see Deferred). — **Reversibility:** reversible — additive; a later key can widen it without changing what this writes.
- **D-02: A note with no `pinned` key is fixed.** Only an explicit `pinned false` (type `bool`, the existing knot key) makes a note follow. This is the opposite of knots, which treat a missing key as unpinned (`TreeFrame.tsx:140-144`). The inversion is deliberate: every existing note, and every `create_note` without `where`, must render exactly where it does today. — **Reversibility:** costly — once worlds contain `pinned false` notes, changing the meaning of the missing key changes how saved worlds render.
- **D-03: A person's drag on a following note writes position plus `pinned true` in one commit**, the knot pattern (`App.tsx:297-305`). The file shows readably that a person took over the note, and the note stops following.
- **D-04: `place` commits with a message that states the intent**, for example `Place note near n7` or `Place note beyond n7 from n4`. This is free text, not a key. The bridge stamps the actor as `agent.<name>` (02.2 D-06); the agent never supplies it.

#### Following and sensing (Area 2)
- **D-05: Following is computed by the renderer at draw time**, like unpinned knots (`TreeFrame.tsx:121-156`). Moving an anchor writes no commits for its followers, so history holds only what someone actually did.
- **D-06: The stored `position.x/y` on a following note is the spot resolved at place time.** It is readable without Tapestry, and it is what replay reproduces: the recorded outcome, never a new guess. This matches the knot plan, which stores the midpoint at creation (`02.1-01-PLAN.md:103`). Positions are frame-local (02.2 D-15).
- **D-07: Main resolves spots and answers `look` using stored `width`/`height`, falling back to fixed defaults.** Measured DOM sizes are never used. This keeps resolution deterministic and testable without a window. The tool description must say plainly that a card whose text made it taller than the default can overlap on screen while `look` reports it clear.

#### The placement rule (Area 3)
- **D-08: The snapshot is the record, and there is no rule key.** The resolution rule lives in code, as today's right-of-parent rule does. Replay never re-derives a position. Only the live drawing of a following note (D-05) uses the current rule.
- **D-09: `near X` starts at today's spot and steps downward until clear.** Today's spot is right of X, `CHILD_GAP` (80) clear. From there the note moves down in note-height steps until its footprint (D-07) overlaps nothing. The step count is bounded; when no clear spot is found, the call is refused with a message naming the anchor, and nothing is committed.
- **D-10: `beyond X from Y` extends the line from Y's centre through X's centre** by one `CHILD_GAP` plus one card width past X, then applies the same collision step as D-09. The result is always fixed (D-01).
- **D-11: `{ on: <space> }` is deferred to the placement-edges phase.** Roadmap criterion 2 is edited to drop it (approved by `tapestry-e2`).

#### Boundaries (Area 4)
- **D-12: An anchor in a different tree from the note is refused**, for example `near n7 is in <other tree>, not <this tree>`, and nothing is committed. Notes stay inside their tree's frame (02.2 D-15). Copying across frames stays a person's drag (02.2 D-17).
- **D-13: On a vault note, `place` changes only its Tapestry-side position** (02.2 D-14). It never changes the note's folder group, so it never moves a `.md` file (02.2 D-26).
- **D-14: Before Phase 2.4 exists, `look` returns relations only, with coordinates for no note.** This is strictly less than the final rule, "coordinates only for placements the caller may write", so it is safe to release early. When 2.4 lands, coordinates switch on through the lock check. No authorship gate is used.
- **D-15: `place` waits for Phase 2.4, with no interim gate.** It is planned against `lock.layout` as specified in `Spec - Locks and Rank` §2: presence means locked, the value is the owner's actor id, and `lock.layout.allow` lists actors who may write anyway. It is refused when locked, and the message names the owner. It executes only after 2.4 is merged into this branch, which is Kaelen's call. The superseded 02.2 D-05 authorship gate (`assertOwnNote`, `notes.ts:614`) must **not** be reused. By the Decision Register (#8), a user-made note's layout starts locked, so an agent cannot move it by default.

#### Error surface (from the spec, not a gray area)
- Every refusal returns `{ ok: false, error }` with a sentence naming what was wrong, in the idiom `grewFrom n99 is not a live note in …` (`notes.ts:269,280`), and writes nothing. Cases:
  - the anchor is not a live note;
  - the anchor is in another tree (D-12);
  - the note is placed relative to itself;
  - no clear spot was found (D-09);
  - the placement is locked (D-15).
- Arguments are node ids only, and every schema is `.strict()`, like the eight existing tools (`mcp/schemas.ts`).

## Evidence From the Code (answers to the orchestrator's questions)

### Q1. `createFrom`: exact shape [VERIFIED: app/src/main/commands/notes.ts:244-336]

- **Signature:** `createFrom(actor: Actor, args: { tree: string; grewFrom: string; title: string; text: string }): CommandResult<{ tree: string; note: string; edge: string; seq: number }>` (lines 244-247).
- **Order of checks:**
  1. `tree = this.registry.resolveRef(args.tree)` in try/catch, which returns `{ ok: false, error: errorText(err) }` (249-253).
  2. `validateTitle` and `validateText` (255-261).
  3. The id shape is checked before any world access: `if (typeof args.grewFrom !== 'string' || !NODE_ID_RE.test(args.grewFrom)) { return { ok: false, error: \`grewFrom ${String(args.grewFrom)} is not a live note in ${tree.name}\` } }` (268-270), with `const NODE_ID_RE = /^n[1-9][0-9]*$/` (48).
  4. Inside `try`: `this.prepareWrite(tree, actor)` (276), **then** the liveness check `const parent = bridge.getNode(args.grewFrom); if (!parent) { return { ok: false, error: \`grewFrom ${args.grewFrom} is not a live note in ${tree.name}\` } }` (278-281).
- **Position:** `const parentX = numericProp(parent, 'position.x', 0)`, `const parentY = numericProp(parent, 'position.y', 0)` and `const parentWidth = numericProp(parent, 'width', DEFAULT_NOTE_WIDTH)` (285-287). The ops write `'position.x': { type: 'real', value: parentX + parentWidth + CHILD_GAP }` and `'position.y': { type: 'real', value: parentY }` (296-297). The constants are `const DEFAULT_NOTE_WIDTH = 280` (64) and `const CHILD_GAP = 80` (67). `numericProp` falls back when a prop is missing or non-finite (187-192).
- **Ops:** one `createNode` with `type: NATIVE_NOTE_TYPE` (`'tapestry.notes/note@1'`, line 37) and props `position.x`, `position.y`, `title` and `body` (`plainTextToDocJson(text)`), plus one `createEdge` `{ from: next.node, to: args.grewFrom, label: GREW_FROM_LABEL }` (291-308). `next` comes from `bridge.getNextIds()` (289).
- **Commit:** `const result = bridge.submitAs(actor, \`grow note "${title}" from ${args.grewFrom}\`, ops)` (310). The actor comes from the caller (`runAgentTool`), which gets it from the socket token and never from args (`agent-tools.ts:9-11`).
- **After commit:** it verifies the predicted id (315-320), calls `this.hooks.onCommitted?.(tree.id, actor, result)` (322), and returns `{ ok: true, value: { tree: tree.id, note: next.node, edge: result.edgeIds[0], seq: result.seq } }` (324-332). Any throw becomes `{ ok: false, error: errorText(err) }` (333-335).
- **How a `place` command submits `setProperty`:** copy the `writeToOwnNote` shape without the `assertOwnNote` call (570-597), and use `updateNote`'s op shape (505-513): `{ op: 'setProperty', target: args.note, key: 'body', type: 'text', value: … }`. For placement the ops are:
  ```ts
  { op: 'setProperty', target: note, key: 'position.x', type: 'real', value: x }
  { op: 'setProperty', target: note, key: 'position.y', type: 'real', value: y }
  { op: 'setProperty', target: note, key: 'pinned', type: 'bool', value: false }   // only for near <grew-from parent>
  { op: 'unsetProperty', target: note, key: 'pinned' }                              // only when a fixed placement replaces a current `pinned` value
  ```
  The addon accepts exactly these shapes: `verb == "setProperty"` reads `target`, `key`, `type` and `value`, and `verb == "unsetProperty"` reads `target` and `key` [VERIFIED: app/native/addon.cpp:258-277]. `bool` requires a JS boolean: `if (!jsVal.IsBoolean()) { throwTypeError(env, "bool value must be a boolean")` [VERIFIED: addon.cpp:159-164]. `real` requires a JS number (153-158). The locks spec states that `UnsetProperty` is refused when the property is absent [CITED: Spec - Locks and Rank §2: "which the kernel refuses if the property isn't there"], so emit `unsetProperty pinned` **only** when `note.props['pinned']` exists.
- **Rewound-tree pitfall:** `prepareWrite` → `prepareWriteFor` → `tree.bridge.discardRedo()` (165-170), which calls `this.instance.replayUpTo(lastSeq)`, sets `this.currentSeq = lastSeq` and sets `this.undoStack = []` [VERIFIED: kernel-bridge.ts:350-358]. It appends nothing to the file, but a **refused** call that runs after `prepareWrite` has still thrown away Kaelen's redo. `createFrom` accepts this, because its liveness check follows `prepareWrite`. For `place`, run every check that does not depend on the world head (argument shape, self-reference, tree resolution) **before** `prepareWrite`. Liveness, lock and collision checks come after it, as `writeToOwnNote` documents (562-569).

### Q4. Renderer: where a following note's position must come from

**The four readers of a stored position** (all must see the derived position):
1. **Frame bounds:** `const boxes: ContentBox[] = tree.nodes.map((node) => { … x: drag ? drag.x : Number(node.props['position.x']?.value ?? 0), y: drag ? drag.y : Number(node.props['position.y']?.value ?? 0), width: dims?.width ?? DEFAULT_NODE_WIDTH, … }); frameRects.set(tree.id, computeFrameBounds(tree.frame, boxes))` [VERIFIED: Canvas.tsx:258-272]. If a follower is left out here, it can be drawn outside its frame, which breaks 02.2 D-15.
2. **Connection preview line:** `const localX = drag ? drag.x : Number(node.props['position.x']?.value ?? 0)` [VERIFIED: Canvas.tsx:680-681].
3. **Edge endpoints:** `getNodeCenter` reads `const px = drag ? drag.x : Number(node.props['position.x']?.value ?? 0)` [VERIFIED: TreeFrame.tsx:111-119], and `resolveNodeCenter` wraps it: `const auto = threadCenterAuto.get(nodeId); if (auto) return { … }; return getNodeCenter(nodeId)` (159-163). Every edge uses `resolveNodeCenter(edge.from)` and `resolveNodeCenter(edge.to)` (225-231).
4. **Card:** `const x = Number(getNodeProp(node, 'position.x', 100))` and `const y = Number(getNodeProp(node, 'position.y', 100))` [VERIFIED: NoteCard.tsx:135-136], then `left: \`${effectiveX}px\`` and `top: \`${effectiveY}px\`` (569-570). Note that the fallback here is **100** while everywhere else it is **0**. A placed note always has both keys, so this does not matter for followers. It is still a reason to define "placed" as "has both numeric keys".

**The knot pattern to copy [VERIFIED: TreeFrame.tsx:121-156]:** "computed ONCE for this tree and shared by its edge layer and its node layer. An unpinned center is RENDERED at the midpoint of its endpoints rather than at its stored position, so edges must resolve it from here or the thread arms end at a phantom point". Knots treat a missing `pinned` as unpinned: `const isPinned = node.props['pinned']?.value === true || node.props['pinned']?.value === 'true'` (140-141). D-02 inverts this for notes.

**Prescribed placement of the derivation:**
- Add a pure `displayPositions(nodes, edges, overrides)` to the shared module. `overrides` is the live `dragPositions` for that tree, in frame-local coordinates.
- Call it **once per tree in `Canvas.tsx`, inside the loop at 258-272, before `frameRects`**. Use its result for `boxes`, for the preview line at 680, and pass it to `<TreeFrame displayPositions={…}>` (716-730).
- In `TreeFrame`, `getNodeCenter` reads `displayPositions.get(nodeId)`, falling back to stored or drag values. Knot midpoints are therefore computed from followers' derived centres automatically, because `threadCenterAuto` calls `getNodeCenter` (148-149). The `NoteCard` branch passes a new optional prop `displayPosition`. In `NoteCard.tsx:135-136`: `const x = displayPosition?.x ?? Number(getNodeProp(node, 'position.x', 100))`.
- Only notes whose `pinned` is exactly `false` (`props.pinned?.type === 'bool' && props.pinned.value === false`) **and** that have a live `grew-from` parent in the same tree get a derived entry. Every other node maps to its drag or stored position.
- **A parent's drag moves its followers live**, because the parent's display position includes its `dragPositions` override.
- **A follower being dragged uses its own drag position**, because the override wins over derivation.

**Draw-time rule (D-05/D-08) that stays deterministic:**
- Process followers in ascending numeric node id. Parse the `n<k>` integer and never sort id strings, since `"n10" < "n9"`.
- A follower's derived spot is `resolveNear(parentDisplayRect, followerSize, obstacles)`. Its obstacles are the display rectangles of every **non-follower** node plus every **already-resolved** follower, excluding itself.
- Sizes come from D-07 (stored `width`/`height`, else the defaults), **never** from `getDims`. This is what makes a freshly placed follower draw exactly at its stored spot.
- If the resolver finds no clear spot, the follower draws at its stored position.
- Because a `grew-from` parent always predates its child, the parent's id is lower, and ascending id order already resolves parents first. If a parent's id is **higher** (only possible from a hand-edited or plugin-written edge), treat the note as fixed. That also rules out cycles.

### Pattern 1: A refusal-first command that commits one `setProperty` batch
**What:** resolve the tree, check the argument shape, `prepareWrite`, check the world, build ops, `submitAs`, `onCommitted`, return `{ ok: true }`. Every branch before `submitAs` returns `{ ok: false, error }`.
**When to use:** `place`, and `createFrom` with `where`.
**Example (skeleton; the keys and op shapes are verbatim from notes.ts:505-513, App.tsx:302-304 and addon.cpp:258-277):**
```ts
// Source: app/src/main/commands/notes.ts:570-597 (writeToOwnNote) minus assertOwnNote
place(actor: Actor, args: { tree: string; note: string; where: Where }): CommandResult<{ tree: string; note: string; seq: number }> {
  let tree: OpenTree
  try { tree = this.registry.resolveRef(args.tree) } catch (err) { return { ok: false, error: errorText(err) } }
  const anchor = 'near' in args.where ? args.where.near : args.where.beyond
  if (anchor === args.note || ('from' in args.where && args.where.from === args.note)) {
    return { ok: false, error: `${args.note} cannot be placed relative to itself` }
  }
  try {
    prepareWriteFor(tree, actor, this.hooks)
    // live + placed checks → `near n7 is not a live note in ${tree.name}` / `near n7 is not placed in ${tree.name}`
    // [Phase 2.4] lock.layout check → `the placement of ${args.note} in ${tree.name} is locked by ${owner}`
    // resolve with shared geometry → null ⇒ `no clear spot near ${anchor} in ${tree.name}`
    const ops: OpObject[] = [
      { op: 'setProperty', target: args.note, key: 'position.x', type: 'real', value: spot.x },
      { op: 'setProperty', target: args.note, key: 'position.y', type: 'real', value: spot.y },
      // follows ? { op: 'setProperty', target: args.note, key: 'pinned', type: 'bool', value: false }
      //         : (hasPinned ? { op: 'unsetProperty', target: args.note, key: 'pinned' } : none)
    ]
    const result = tree.bridge.submitAs(actor, message /* D-04 */, ops)
    this.hooks.onCommitted?.(tree.id, actor, result)
    return { ok: true, value: { tree: tree.id, note: args.note, seq: result.seq } }
  } catch (err) { return { ok: false, error: errorText(err) } }
}
```

There is no `on` and no `facing` form (D-11, #12). A `{ on: … }` or `{ facing: … }` object fails both strict members.

### Pattern 3: The `look` result shape (wave 1)
```ts
// Fields from roadmap criterion 1 / spec §3. `placement` is omitted entirely before 2.4 (D-14).
type LookNeighbour = {
  note: string
  space: string            // the tree id: the tree's implicit space (spec §6 "Today")
  relation: 'near' | 'beyond' | 'overlapping' | 'contains' | 'contained-by'
  order: number            // 1-based
  guess: boolean           // true iff the neighbour is following (explicit pinned false with a live grew-from parent)
}
```
**Relation classification (deterministic, D-07 rects, with `from` as A and the neighbour as B):**
1. A contains B (B inside A on both axes, edges inclusive), then `contains`.
2. B contains A, then `contained-by`.
3. The intersection has positive area on both axes (strict `<`), then `overlapping`.
4. The edge-to-edge gap ≤ `NEAR_GAP`, then `near`.
5. Otherwise `beyond`.

Here `gap = max(0, max(B.x − (A.x+A.w), A.x − (B.x+B.w)), max(B.y − (A.y+A.h), A.y − (B.y+B.h)))`, which is the Chebyshev gap between rects. **Recommend `NEAR_GAP = 2 * CHILD_GAP = 160`**, so a `createFrom` child (80 clear) and one step of stacking both count as `near`.

**Ordering:** ascending `(gap², centreDist², numericId)`.

**Toward filter:** keep B only if `dot(cB − cA, cT − cA) > 0` and `dot² ≥ ½·|cB − cA|²·|cT − cA|²`. That is a 45° half-angle cone, with no trig.

**Limit:** default 20 (the `DEFAULT_SEARCH_LIMIT` precedent at notes.ts:78) and no maximum.

**Candidates:** every live node in the tree except `from`, except knots (on this base, `node.type.includes('thread-center')`, the same predicate as TreeFrame.tsx:30-32), and except nodes without both numeric `position.x`/`position.y`. Positions come from `displayPositions(nodes, edges, {})`, so a follower is reported where it is drawn.

### Pattern 4: The D-09 / D-10 resolver
```ts
// near: start = (A.x + A.w + CHILD_GAP, A.y); step k = 0..MAX_PLACE_STEPS-1:
//   candidate = { x: start.x, y: start.y + k * (size.h + STACK_GAP), w: size.w, h: size.h }
//   return candidate if it overlaps no obstacle (strict positive-area intersection); else null
// beyond X from Y: d = cX - cY; len2 = d·d; if len2 === 0 → refuse "beyond X from Y has no direction"
//   u = d / Math.sqrt(len2); c = cX + u * (CHILD_GAP + size.w); start = c - size/2; then the same downward steps
```
With equal widths along a horizontal line, D-10 lands the new card's left edge exactly `CHILD_GAP` right of X, the same spot as D-09's start. This is the self-check test.

**Recommend `STACK_GAP = 24`**, the gutter that 02.2-07's vault layout uses (`02.2-07-PLAN.md:184`, "row step 200 + 24"), and **`MAX_PLACE_STEPS = 64`**. The obstacles are every placed non-knot node except the note being placed. For a follower placement, use the same obstacle rule as draw time (non-followers plus lower-id followers), so that the draw-time spot equals the stored spot right after the commit.

### Anti-Patterns to Avoid
- **Reusing `assertOwnNote` / `writeToOwnNote` for `place`:** forbidden by D-15. `writeToOwnNote` calls `assertOwnNote` unconditionally (notes.ts:586).
- **Using `getDims` (measured DOM) in the follow computation:** it breaks agreement with main (D-07) and flickers on first paint.
- **Deriving a follower in `TreeFrame` only:** the frame bounds in Canvas would not contain it (02.2 D-15).
- **Treating a missing `pinned` as following:** that is the knot default, and D-02 inverts it. Use a strict `type === 'bool' && value === false`.
- **Writing `pinned true` when an agent re-places a follower elsewhere:** the file would read as a person's takeover. Use `unsetProperty pinned`.
- **Putting coordinates in any `look` output or any refusal message:** that leaks D-14. Messages name ids and trees only.
- **Sorting ids as strings.**
- **Changing `createFrom`'s no-`where` path:** criterion 2 says it must behave exactly as today, with no collision stepping and no `pinned` key.

## Common Pitfalls

### Pitfall 1: The addon is not built in this worktree
**What goes wrong:** every command test fails on import, and the executor mistakes it for a code failure.
**Why it happens:** `app/native/build` is per-checkout and was never built here. `node_modules` is a symlink, but the addon output is not.
**How to avoid:** Wave 0 runs `npm --prefix app run build:native` and `npm --prefix app run build:js`, then confirms the baseline suite is green before any change.
**Warning signs:** `Failed to load native addon from …/agent-trees/app/native/build/Release/tapestry_addon.node`.

### Pitfall 2: The draw-time follower disagrees with the stored spot
**What goes wrong:** right after `place`, the card jumps away from where the file says it is.
**Why it happens:** main and renderer use different sizes (measured versus D-07), obstacle sets, or iteration order.
**How to avoid:** one function, D-07 sizes, and the obstacle rule "non-followers plus lower-id followers" on both sides. Unit test: after `resolveNear` for follower F, `displayPositions(...)` with F's stored spot returns the same spot.

### Pitfall 3: A refusal still discards redo
**What goes wrong:** a malformed `place` wipes the person's undo history.
**How to avoid:** run shape and self checks before `prepareWriteFor`. Test with `undo()` followed by a self-placement: `isRewound` must still be `true`.

### Pitfall 4: The "commits nothing" assertion is too weak for property writes
**What goes wrong:** a refused `place` that wrote a position still passes a node and edge count check.
**How to avoid:** extend the fingerprint with file size **and** the note's `position.x`, `position.y` and `pinned`, and assert the `onCommitted` count.

### Pitfall 5: The shim test pins the tool list
**What goes wrong:** adding `look` breaks `advertises exactly the eight tools`.
**How to avoid:** update the list and the read-only list in the same task that adds the definition. Rebuild `build:js` before running the test.

### Pitfall 6: Merge surface with Phase 2.3 and the primary branch
**What goes wrong:** conflicts in `TreeFrame.tsx`, `Canvas.tsx` and `App.tsx`. Phase 2.3-01 renames thread-center to knot (`isThreadCenter` becomes an exact `KNOT_TYPE` compare, `02.3-01-PLAN.md:77-80`). The primary branch has already rewritten TreeFrame (+220 lines) for vault cards.
**How to avoid:** keep the renderer edits small and additive: a new prop, a new handler, and one call site per reader. Keep all logic in the shared module. Make the tsconfig edit byte-identical to 02.3-02.

### Pitfall 7: The knot predicate and the vault card path change after merges
**What goes wrong:** `look` counts knots as neighbours after 02.3 renames the type, or vault cards (drawn by `VaultNoteCard` on the primary branch) ignore `displayPosition`.
**How to avoid:** export one `isKnot(type)` from the shared module and update it on merge. Vault notes never follow (they have no `grew-from`), so `VaultNoteCard` needs nothing.

### Pitfall 8: D-12's example message cannot occur with id-only arguments
**What goes wrong:** the planner writes a test for `near n7 is in <other tree>, not <this tree>` that can never pass. Node ids are per tree (every tree has an `n1`), and `place` takes a single `tree`.
**How to avoid:** implement D-12 structurally. Anchors resolve **only** inside `args.tree`. Test that an id live only in a second open tree is refused as `near n7 is not a live note in <tree>` and writes nothing. Raise the message wording as an open question.
