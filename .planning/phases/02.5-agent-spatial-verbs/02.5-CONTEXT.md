# Phase 2.5: Agent Spatial Verbs - Context

**Gathered:** 2026-09-16
**Status:** Ready for planning — execution of `place` is held for Phase 2.4 (see D-15)

<domain>
## Phase Boundary

Agents get two task-space MCP verbs over the existing command set:

- **`look`** (read-only): an agent names a note and receives its neighbours in the same tree, nearest first, as relations — never raw coordinates before the lock model exists.
- **`place`** (write): an agent names a note and a relation (`near`, or `beyond … from …`) and the host resolves it into a position, refusing when `lock.layout` forbids it.

`create_note` gains the same optional `where`. The host, not the agent, turns relations into geometry, as it already does for `grewFrom` (`notes.ts:283-297`).

**This phase is the plain verbs only.** The anchor cursor, agent bodies made of threads, agents moving as clusters, and `facing` stay in the anchor-cursor phase that Kaelen created after 2.3 (`02.3-CONTEXT.md:149`). Splitting the verbs out ahead of that phase was **Decision Register #22**. **Kaelen confirmed it on 2026-09-16, typed in the agent-trees window, verbatim: "yes build those now"**, in answer to: "2.5 ships only the plain verbs first (`look` and `place`; no cursor, bodies, clusters or facing). OK to build those now?"

**Out of this phase:**
- `{ on: <space> }`, which has no meaning until a tree has more than one space.
- `facing` and any write to D-27's `direction` (Decision Register #12).
- Any new `.tree` key, type string or edge label.
- The frozen migration of position onto placement edges.
- The lock model itself, which is Phase 2.4 on `ws/notifications-rank`.
</domain>

<decisions>
## Implementation Decisions

All decisions below were answered by the orchestrator `tapestry-e2` under Kaelen's standing grant of 2026-09-16 ("may approve recommended options … except one-way doors, shared dependency installs, instruction/config files, and merges"). Every choice is the recommended option; no one-way door was chosen.

### What a placement writes (Area 1)
- **D-01:** **A following note follows its `grew-from` parent, with no new key.** Every agent note already carries a `grew-from` edge to its parent (02.2 D-04, `notes.ts:45`, edge from child to parent). `place near <parent>` makes the note follow that parent. `place near X` for any other X, and every `beyond`, writes a **fixed** position. Widening "follow" to arbitrary anchors needs a new key or label, which is a one-way door (see Deferred). — **Reversibility:** reversible — additive; a later key can widen it without changing what this writes.
- **D-02:** **A note with no `pinned` key is fixed.** Only an explicit `pinned false` (type `bool`, the existing knot key) makes a note follow. This is the opposite of knots, which treat a missing key as unpinned (`TreeFrame.tsx:140-144`). The inversion is deliberate: every existing note, and every `create_note` without `where`, must render exactly where it does today. — **Reversibility:** costly — once worlds contain `pinned false` notes, changing the meaning of the missing key changes how saved worlds render.
- **D-03:** **A person's drag on a following note writes position plus `pinned true` in one commit**, the knot pattern (`App.tsx:297-305`). The file shows readably that a person took over the note, and the note stops following.
- **D-04:** **`place` commits with a message that states the intent**, for example `Place note near n7` or `Place note beyond n7 from n4`. This is free text, not a key. The bridge stamps the actor as `agent.<name>` (02.2 D-06); the agent never supplies it.

### Following and sensing (Area 2)
- **D-05:** **Following is computed by the renderer at draw time**, like unpinned knots (`TreeFrame.tsx:121-156`). Moving an anchor writes no commits for its followers, so history holds only what someone actually did.
- **D-06:** **The stored `position.x/y` on a following note is the spot resolved at place time.** It is readable without Tapestry, and it is what replay reproduces: the recorded outcome, never a new guess. This matches the knot plan, which stores the midpoint at creation (`02.1-01-PLAN.md:103`). Positions are frame-local (02.2 D-15).
- **D-07:** **Main resolves spots and answers `look` using stored `width`/`height`, falling back to fixed defaults.** Measured DOM sizes are never used. This keeps resolution deterministic and testable without a window. The tool description must say plainly that a card whose text made it taller than the default can overlap on screen while `look` reports it clear.

### The placement rule (Area 3)
- **D-08:** **The snapshot is the record, and there is no rule key.** The resolution rule lives in code, as today's right-of-parent rule does. Replay never re-derives a position. Only the live drawing of a following note (D-05) uses the current rule.
- **D-09:** **`near X` starts at today's spot and steps downward until clear.** Today's spot is right of X, `CHILD_GAP` (80) clear. From there the note moves down in note-height steps until its footprint (D-07) overlaps nothing. The step count is bounded; when no clear spot is found, the call is refused with a message naming the anchor, and nothing is committed.
- **D-10:** **`beyond X from Y` extends the line from Y's centre through X's centre** by one `CHILD_GAP` plus one card width past X, then applies the same collision step as D-09. The result is always fixed (D-01).
- **D-11:** **`{ on: <space> }` is deferred to the placement-edges phase.** Roadmap criterion 2 is edited to drop it (approved by `tapestry-e2`).

### Boundaries (Area 4)
- **D-12:** **Anchors are looked up only in the tree the call names.** An id that is live only in another open tree is refused as `near n7 is not a live note in <tree>`, and nothing is committed. *(Wording corrected 2026-09-16 with `tapestry-e2`'s agreement: node ids exist separately in each tree and `place` names one tree, so the original "is in <other tree>" message could never be detected. The guarantee is unchanged.)* Notes stay inside their tree's frame (02.2 D-15). Copying across frames stays a person's drag (02.2 D-17).
- **D-13:** **On a vault note, `place` changes only its Tapestry-side position** (02.2 D-14). It never changes the note's folder group, so it never moves a `.md` file (02.2 D-26).
- **D-14:** **Before Phase 2.4 exists, `look` returns relations only, with coordinates for no note.** This is strictly less than the final rule, "coordinates only for placements the caller may write", so it is safe to release early. When 2.4 lands, coordinates switch on through the lock check. No authorship gate is used.
- **D-15:** **`place` waits for Phase 2.4, with no interim gate.** It is planned against `lock.layout` as specified in `Spec - Locks and Rank` §2: presence means locked, the value is the owner's actor id, and `lock.layout.allow` lists actors who may write anyway. It is refused when locked, and the message names the owner. It executes only after 2.4 is merged into this branch, which is Kaelen's call. The superseded 02.2 D-05 authorship gate (`assertOwnNote`, `notes.ts:614`) must **not** be reused. By the Decision Register (#8), a user-made note's layout starts locked, so an agent cannot move it by default.

### Settled after research (agreed with `tapestry-e2`, 2026-09-16)
- **D-16:** **Resizing a following note from its left or top edge pins it**, exactly like a drag (D-03). That resize also writes position (`NoteCard.tsx:474-477`), so it goes through the same takeover write: position plus `pinned true`, one commit.
- **D-17:** **When an agent moves a following note to a fixed spot, the command removes `pinned` (`unsetProperty`)** rather than writing `pinned true`. `pinned true` stays the readable mark of a person's takeover (D-03). This adds no key and is reversible. **An agent's `place` never removes or overwrites an existing `pinned true`:** a fixed placement unsets `pinned` only when its current value is bool `false`, and leaves `pinned true` as it is (it already means fixed). `place near <own grew-from parent>` on a note with `pinned true` is refused, for example `n2 was pinned by a person; it will not follow n1 again`, and nothing is committed. *(Settled with plan-check, 2026-09-16: a note an agent created and a person then dragged carries no default layout lock, so `pinned true` is the only record of the takeover.)*
- **D-18:** **The placement geometry lives at `app/src/renderer/layout/placement.ts`**, a pure module with no DOM and no Electron, beside `frames.ts`. Main imports it (`tsconfig.node.json` has `rootDir: ".."`). The research's `app/src/shared/placement/` location needs a tsconfig edit, which is outside the grant; moving the module there to match 02.3-02 is a follow-up listed for Kaelen. **No tsconfig change is made in this phase.**
- **D-19:** **The `place` wave is provisional on Phase 2.4.** Its first task does not run on its own: it reads what 2.4 actually ships (the lock check's name, signature and refusal text) and adapts the plan before any code is written. The Locks spec §2 shape, including its `open` value, is the working assumption until then.

### Error surface (from the spec, not a gray area)
- Every refusal returns `{ ok: false, error }` with a sentence naming what was wrong, in the idiom `grewFrom n99 is not a live note in …` (`notes.ts:269,280`), and writes nothing. Cases:
  - the anchor is not a live note;
  - the anchor is not live in the named tree (D-12);
  - the note is placed relative to itself;
  - no clear spot was found (D-09);
  - the placement is locked (D-15).
- Arguments are node ids only, and every schema is `.strict()`, like the eight existing tools (`mcp/schemas.ts`).

### Claude's Discretion
- Tool names (`look` or `look_around`, `place` or `place_note`), provided they match the style of the existing snake_case names.
- The default card height main uses (D-07). `NoteCard.tsx:99` sets `MIN_HEIGHT = 60`; the renderer's fallbacks in `TreeFrame.tsx:27-28` are for knots. Pick one constant, share it, and document it.
- The distance threshold separating `near` from `beyond` in `look`'s `relation`, and the exact overlap test, provided both are deterministic and use D-07 sizes.
- The collision step bound in D-09.
</decisions>

<specifics>
## Specific Ideas

- Kaelen's framing (`Concept - Task Space and Shape Space`): "the brain sends the goal, not every muscle command". Agents state intent, and the host resolves shape.
- A tentacle reaching outward is `beyond X from Y`, repeated.
- `look` reports `overlapping` as a relation. An agent can move its own notes off a locked note without ever reading that note's coordinates.
</specifics>

<deferred>
## Deferred Ideas

### One-way doors that need Kaelen (not chosen under the grant)
- **`placement.near` property**: a text key naming any anchor, so a note can follow any note, not just its `grew-from` parent. It widens D-01.
- **A new edge label for anchoring** (for example `placed-near`). It also overlaps spatial-canvas's pending `placement` edge design (`Spec - Placement Edges` §1), which waits on Pending #21.
- **`placement.rule` stamp**: each placement would name the rule version that resolved it, so old rules could be reproduced when drawing.
- **A readable placement policy property on the tree**: the spec's §4.2 shape. It would pre-empt the pending spaces and forest decisions (#2, #21).

### Belongs to other phases
- `{ on: <space> }` — the placement-edges phase (D-11).
- `facing` and agent writes to D-27 `direction` — the anchor-cursor phase (#12).
- Agent bodies, clusters, gait notes, and waypoint motion — the anchor-cursor phase (`02.3-CONTEXT.md:149`; `Concept - Embodied Agents`).
- Coordinates in `look` for writable placements — switch on with the 2.4 lock check (D-14).
</deferred>
