# Phase 2.7: File Windows & Workspace Sandbox - Context

**Gathered:** 2026-09-24
**Status:** Ready for planning
**Branch:** `ws/windows` (worktree `~/Tapestrees/windows`, branched from `ws/agent-trees`)

<domain>
## Phase Boundary

A person opens a workspace folder in Tapestry. The folder becomes a tree whose frame is the "file window": folders are groups and each file is a note holding that file's text. Editing a note edits the real file on disk, and changes made outside Tapestry (git, editors, other Claude sessions) are recorded in the tree. Agents connected over the existing MCP bridge get file tools that reach only files inside open workspaces, and locks apply to files.

**Urgency (Kaelen, 2026-09-24):** "we want to get this working as soon as possible with getting working windows that can connect to claude in the tapestry app; editing files in worktrees ASAP." The first plan must be the dogfood tracer. Anything not needed for it comes after.

Out of scope: Markdown semantics for workspace files (links, tags and frontmatter stay the vault's job), diff views, git operations, terminals and running commands, and cross-tree copies.
</domain>

<decisions>
## Implementation Decisions

### Workspace and file window
- **D-01:** A workspace is a folder the person opens (via "Add tree" in the forest bar, next to adding a vault). Several can be open at once. The main case is one per git worktree under `~/Tapestrees/`.
- **D-02:** **A file window is a folder in the tree that shows each file as a note.** The workspace is its own tree and frame. Sub-folders are labeled groups, as in 02.2 D-26. Each text file is one note whose text is exactly the file's text, for any extension, not only `.md`. Binary or oversized files are file notes that show only the name and type; their bytes never enter the tree (02.2 D-29, vault-fs limits).
- **D-03:** Source-mirror model, the same as 02.2 D-10: the tree records what the files contain and never keeps a diverging version.

### Writes
- **D-04:** **Edits go straight to disk and change the actual files.** A human edit in a file note is written to the file after typing pauses for about a second (02.2 D-22). An agent write lands on disk immediately. The tree then records what the file says.
- **D-05:** If the file changed on disk before a pending Tapestry edit was flushed, the file wins, and the losing edit stays in history (02.2 D-11).

### Outside changes
- **D-06:** **Outside changes update the tree.** While Tapestry is open it watches the workspace and records changes within moments, grouped per moment (02.2 D-20, D-23). On open, it catches up on what changed while it was closed. An observed change with no known author is signed by the bridge actor and never guessed at (02.2 D-21). Changes made through the agent tools carry `agent.<name>`.

### Agents
- **D-07:** Agents get file tools over the existing MCP bridge: at minimum `list_files`, `read_file` and `write_file` (a full replacement), plus a targeted `edit_file` (replace an exact string) because agents such as Claude Code work that way. Commits read `actor plugin agent.<name>` (02.2 D-06).
- **D-08:** **Sandbox.** Every agent path is resolved against an open workspace root. The following are refused with a clear message: `..` escapes, absolute paths outside the root, any symlink along the path, paths inside `.git`, and any workspace that is not open. A refusal writes nothing to disk and commits nothing to the tree. With no workspace open, the file tools refuse and never fall back to a default directory.
- **D-09:** **Locks apply to files.** A file's note takes part in the 2.4 lock model. `lock.text` on it refuses agent `write_file`/`edit_file` to that file, and `lock.layout` refuses `place`. Otherwise the 2.4 rule holds: allow unless locked. Agents may edit any workspace file that is not locked, whoever wrote it.
- **D-10:** **Connect Claude from inside the app.** The existing Agents panel and connect command (02.2-04) are the way in, and they must also work for a Claude Code session whose working directory is one of the worktrees.

### In-app chat panel (added 2026-09-24, Kaelen)
- **D-12:** **Tapestry has a Claude chat panel inside the app**, next to the file windows. Claude does not only run in an outside terminal.
- **D-13:** **The engine is the Claude Code CLI, the norm for most people.** Tapestry spawns the user's `claude` (installed and signed in) as a subprocess in the workspace root (`cwd`). It uses `-p --input-format stream-json --output-format stream-json --verbose`, optionally `--include-partial-messages` for live text, and `--resume <session-id>` to continue a chat. It runs on the user's existing Claude Code login and subscription limits. There is no API key and no per-token billing setup. Claude Code 2.1.281 on this machine has all of these flags: `--tools`, `--allowedTools`, `--disallowedTools`, `--mcp-config`, `--strict-mcp-config`, `--permission-mode`, `--append-system-prompt`, `--session-id`, `--model`.
- **D-14:** **By default the panel's Claude sees only Tapestry's sandboxed workspace tools.** It gets `--mcp-config` pointing at Tapestry's MCP shim with `--strict-mcp-config`, and built-in tools are turned off through `--tools`. It is attributed as `agent.<name>` like any bridge agent (D-07), so its edits go through the D-08 sandbox and the D-09 locks.
- **D-15:** **A shell toggle comes after the CLI panel works, as its own plan.** Each chat has an "Allow shell" switch, off by default and clearly labelled "not sandboxed". Switching it on enables Claude Code's Bash and built-in file tools in the workspace folder. Edits made that way bypass Tapestry's tools, so they reach the tree as observed changes (D-06).
- **D-16:** **A small engine interface, with an API-key engine later.** The panel talks to a `ChatEngine` interface (start or resume, send, a stream of events, stop), and the CLI engine is its first implementation. An API-key engine comes in a later plan, after the shell toggle: `@anthropic-ai/sdk` with its tool runner over the same sandboxed tools, for developers. That plan must load the `claude-api` skill for model IDs and SDK shapes. Only the interface seam is in scope before then.
- **D-17:** **Plan order:** the dogfood tracer (01) → the CLI chat panel (02) → the shell toggle (03) → the earlier hardening and watcher plans → the API-key engine last. Getting "windows that connect to Claude in the app" working comes first.

### Naming (2026-09-24, Kaelen)
- **D-18:** The actor for changes Tapestry notices on disk without knowing who made them is **`plugin workspace.watcher`**, not `workspace.bridge`. In Kaelen's words: "bridge more connotes a connection between two separate tapestries or entities", while this is sensing what changed and recording it. The constant is `WORKSPACE_WATCHER_ACTOR`, and it stays reserved under the `workspace.` prefix. It is renamed before any real `.tree` history is written, so no old name exists in user data. `obsidian.bridge` is unchanged, because a vault really is a connection to another app and already has history.

### Dogfood gate (tracer acceptance)
- **D-11:** Open `~/Tapestrees/windows` as a workspace in Tapestry and connect Claude Code through the Agents panel. Claude Code then edits a real source file through the Tapestry file tools. The edit shows in `git diff`, the file note updates in its window, and the tree records it as `agent.claude`. A human edit in the window also reaches the file.

### Claude's Discretion
- **Tree file location:** default to Tapestry's app data folder, e.g. `<userData>/workspaces/<folder-name>-<short hash of root path>.tree`, not inside the workspace, so git worktrees stay clean. The tree must still be readable. This is reversible; tell Kaelen in the summary.
- **What gets mirrored:** skip `.git`. In a git repo, mirror only the files git would show (`git ls-files --cached --others --exclude-standard`) so `node_modules`, `out` and build folders never flood the window. Outside git, use the vault ignore rules plus `node_modules`. Never follow symlinked directories.
- **Scale:** this repo has about 740 tracked files. Collapsed groups or lazy note bodies are fine if the canvas struggles, but correctness and the dogfood loop come first.
- **Generalise, don't fork:** factor the shared folder-mirror, watcher and write-to-source machinery out of `obsidian/` rather than copying it. The vault keeps its Markdown layer on top. This phase lands the watcher and the write half that 02.2 Plans 10, 11 and 13 describe, in a generic form those plans can reuse.
</decisions>
