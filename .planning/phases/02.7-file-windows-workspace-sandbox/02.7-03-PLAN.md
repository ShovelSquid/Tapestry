## Phase Goal

**As** Kaelen, **I want** a per-chat switch that lets Claude in the panel use Claude Code's shell and built-in file tools when I choose, clearly marked as not sandboxed, **so that** I can let it run tests or builds in the workspace without leaving Tapestry, while every chat starts safe.

(Sourced from 02.7-CONTEXT.md D-15 and ROADMAP Phase 2.7 success criterion 7.)

<objective>
The "Allow shell" switch (D-15), built on the 02.7-02 panel.

Purpose: D-17 puts this right after the CLI panel works. It is a small change to one argv builder and one service, but it is the one place a chat leaves the sandbox. So the default, the consent step, the reset on relaunch and the honest attribution of what happens with the shell on are each tested.

Output:
- buildClaudeArgs `allowShell`;
- `ClaudeCliEngine.setAllowShell`;
- `ChatService.setAllowShell`, with notices, persistence, reset on relaunch and the end-of-turn catch-up;
- IPC;
- the switch, its confirmation and the banner in ChatPanel.

Recorded choices:
- **Shell-on tool set.** It is exactly `Bash,Read,Edit,Write,Glob,Grep`, passed as one comma-joined element to `--tools`. `--allowedTools` becomes `mcp__tapestry,Bash,Read,Edit,Write,Glob,Grep`, and `--permission-mode dontAsk` still denies anything not listed. WebFetch, WebSearch and subagents stay off. The executor confirms these names against the `tools` list in a live `system/init` event (or `claude --help`) and records the result in the SUMMARY.
- **The switch resets to off on every relaunch.** A person's consent is for this session of the app. chats.json keeps the last state so the chat can say "Shell access was on in this chat before Tapestry restarted; it is off now." (fail-safe; reversible).
- **Built-in edits are caught up at the end of each turn.** After every turn that ran with the shell on, the chat service awaits `WorkspaceService.catchUp(treeId)`. Edits made through Bash or the built-in tools therefore enter the tree as observed changes (D-06) right after the turn, with no dependence on the live watcher. Until 02.7-05 they appear at the end of the turn rather than live.
- **The system prompt is not changed.** 02.7-02's text already covers both states, and `--system-prompt-snapshot` would ignore a changed prompt on resume anyway. Claude learns the tool change from the tools it is given.
- **No `--restricted`.** It would confine the built-in file tools to the working directory, but Bash is unconfined either way. Claiming partial confinement would contradict the "not sandboxed" label.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.7-35 | Elevation of Privilege | the shell switch defaulting on, or silently staying on | high | mitigate | The default is false in buildClaudeArgs, ClaudeCliEngine and ChatService. New chats and every relaunch start off. Turning it on needs a confirmation dialog. Tests assert the default argv has no built-in tool for new and resumed spawns, and that a relaunch resets the switch |
| T-02.7-36 | Elevation of Privilege | a shell-on chat reaching outside the workspace | high | mitigate | Only by explicit per-chat, per-session consent, with the risk stated in the dialog, a persistent banner and "not sandboxed" in the switch label. cwd is always the workspace root, tools are limited to SHELL_TOOLS, and dontAsk denies anything else. | T-02.7-37 | Repudiation | shell or built-in edits credited to the chat agent | medium | mitigate | These edits bypass Tapestry's tools, so they enter the tree only through catchUp as plugin workspace.bridge (D-06); a test asserts no agent.claude-chat commit for them |

| T-02.7-39 | Tampering | renderer turning the shell on without the person | low | accept | The renderer is Tapestry's own trusted UI (sandboxed, contextIsolation), and the dialog is the consent step. A compromised renderer is out of scope, as for every other renderer-originated write |
