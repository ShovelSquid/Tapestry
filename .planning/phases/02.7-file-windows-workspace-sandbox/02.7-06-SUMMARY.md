# Phase 2.7 Plan 06: Live watching, self-healing status, Retry write and scale Summary

**Open workspaces are now watched with recursive `fs.watch` (FSEvents). An outside change (an editor, git, Claude Code's own Edit tool) is recorded as `plugin workspace.watcher` within about a second of the folder going quiet, grouped per 750 ms moment. Tapestry's own writes never echo, and a reconcile can no longer revert an agent write that lands while it reads. Watch failures restart themselves after 5 s, and the frame header says when nothing is being recorded. On an 800-file workspace an idle reconcile reads nothing, and reopening after 200 edits costs about the same as after none.**

## What Kaelen should know

- **Live watching.** A workspace is watched from the moment it is added or restored, until its frame is closed or Tapestry quits. An outside edit shows in the file's card about 0.8 to 1.5 s after the last write of a burst (750 ms of quiet, forced at 5 s). A git checkout that rewrites many files becomes one history entry listing them. A moment too large for one commit (over 32 MiB of text) is split, and each part is tagged `(group <stamp>, i of n)`.
- **Who changed it.** Every observed change is signed `plugin workspace.watcher`, and the card footer reads `workspace.watcher · author unknown` with the eye glyph. Nothing guesses an author from timing or from which agent was active.
- **Header status.** A workspace frame's status now reads **Watching**. If the watcher fails, it reads "Not watching -- <reason>. Tapestry will try again in 5 seconds." in red, and it retries every 5 s. If the folder disappears (renamed, unmounted), it reads "The folder is missing; nothing is being recorded." Nothing is deleted from the tree, and it recovers by itself when the folder comes back.
- **Retry write.** If a window save fails, for example because a folder is read-only, the card shows **Not written to file** in red, with the reason in its tooltip, and a **Retry write** button. Retrying sends the same text against the version the edit started from. If the file changed in the meantime, the file still wins, as before. The edit is in history either way.
- **The chat's end-of-turn catch-up** (02.7-04) now uses the same reconcile path, and with watching on it normally finds nothing. It is kept as a backstop.

## Scale numbers (spike risk 1)

From `scale.test.ts`, on this Mac. The synthetic workspace has 801 text files of 1 to 4 KB, 20 binary files and 70 folders (60 leaf folders under 10 parents). Numbers from the final full-suite run; single runs varied by about ±30%.

| Measure | Result |
|---|---|
| `[scale] import` | **166 ms** (129 to 166 ms across runs) |
| `[scale] idle reconcile` | 65 ms (34 to 65 ms), with 821 listed, **0 read**, 821 reused, 0 commits |
| `[scale] reopen after import` | 37 ms (2 commits) |
| `[scale] reopen after 200 edits` | **33 ms (202 commits)** (35 to 37 ms across runs) |
| `[scale] 200 agent edits` | 8338 ms, **41.7 ms per edit** |

**Is reopen cost growing with commits?** Not measurably at this size. Reopening after 202 commits costs the same as after 2 (30 to 37 ms either way, within run-to-run noise). The quadratic `Kernel::fromJournal` risk from the spike is not visible for a workspace tree with a few hundred small commits. This measures a few hundred commits, not the tens of thousands a long dogfood could produce. The fix, if one is ever needed, is still Phase 3 kernel snapshots.

**New finding: an agent edit costs about 40 ms of main-process time on an 800-file tree.** This is not reopen cost. Each file-tool call reads the whole tree through `getNodes()` several times (lock check, observe-first, planPathChange, noteForPath), and each read copies every file's text across N-API. A window save takes the same path, but it runs about a second after typing stops, so it should not show as typing lag. If the backstop check finds lag, the next steps are a `getNodes` cache per commit seq, or a path index in the service, alongside the lazy text over IPC already noted in the plan.

## Decisions Made

- `'all'` reconciles trust the stat cache (see key-decisions). The plan's Task 1 wording could be read as re-reading everything on `'all'`, but Task 3 requires an idle `reconcileNow(treeId, 'all')` to read 0. The Task 3 reading is the one implemented. A file changed in place with the same size, mtime and inode would be missed until its next event; with nanosecond mtimes on APFS and an atomic rename changing the inode, that case is theoretical.
- A folder that goes missing while watched disposes the watcher and polls every 5 s (one lstat), then restarts with a full catch-up. It does not trust FSEvents to follow a path that was renamed away.
- A frame header prefers a watching problem over the save state, and a save error over "Watching". Before main has reported anything, it shows the save state as before.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Ordering] Task 2's service behaviours were built with Task 1**
- **Found during:** Task 1
- **Issue:** `startWatching` needed an error path from the start: `fs.watch` throws when a folder is missing. That path is Task 2's status, restart and folder-missing logic.
- **Fix:** Built `onStatus`, `restartDelayMs` and folder-missing into `b63d4a9`. Task 2's RED commit therefore failed only on the renderer pieces (the badge label and the status store module). The service behaviours it adds (restart with catch-up, missing folder, three-in-one moment, deletion, ignore) passed as soon as they were written. The TDD gate is honest for the renderer side only.
- **Commits:** b63d4a9, 339b2c9

**2. [Rule 2 - Correctness] `workspace:statuses` pull for a late renderer**
- **Found during:** Task 2
- **Issue:** Restored workspaces start watching as they open, which can happen before the window finishes loading, so the first `workspace-status` event could be lost.
- **Fix:** `WorkspaceService.allStatuses()`, `ipcMain.handle('workspace:statuses')` and preload `workspace.statuses()`. The store pulls once on first subscription, and an event already heard is never overwritten.
- **Commit:** a2c5b52

**3. [Rule 1 - Correctness] Memoised card forwards handlers through a wrapper**
- **Found during:** Task 3
- **Issue:** The plan's ref was updated only on renders the card itself performs. Canvas handlers close over Canvas and App state (`onPositionChange` then `settleFrames`, and `handleBorderSelect` over `selectedRef`), so a card that skipped several renders would drag or select through an older closure.
- **Fix:** A thin exported wrapper stores the latest props in a ref on every parent render and passes stable forwarding handlers to the memoised inner card. The inner card's expensive render is still skipped when its data is equal.
- **Commit:** 10bf222

**4. [Rule 2 - Test seam] `afterModelRead` option**
- **Found during:** Task 1
- **Issue:** The plan's seq-guard test starts `reconcileNow` and runs `editFile` before awaiting it. Because the reconcile starts in a later microtask, the edit always lands before the read, so that test passes even without the guard.
- **Fix:** Kept the plan's test. Added an `afterModelRead` seam so a second test lands the agent write between reading and planning. A mutation check confirmed that this test fails when the guard is disabled.
- **Commit:** b63d4a9

**5. [Addition] Extra measurements and tests**
- The scale test also logs a reopen right after import (the baseline) and the time for the 200 edits, so "growing with commits" can be answered.
- Two Retry write contract tests: it writes once the folder is writable again, and a file changed in the meantime still wins. There is also a unit test for the memo comparator.

**Total deviations:** 5 (1 ordering, 2 correctness, 1 test seam, 1 addition). No scope change, no new dependency.

## Issues Encountered

- FSEvents also reports events from just before a watcher starts. The tests wait 400 ms after `startWatching` before writing. Those early events only cause a reconcile that finds nothing.
- FSEvents reports the watched root's own rename as its basename. That rel is not a listed file, so as a hint it does nothing.

## Hands-on checks for later (not run; the app must not be launched unattended)

With `~/Tapestrees/windows` open as a workspace in Tapestry:
1. **Live edit (Task 1 and the backstop truth).** Ask Claude Code in a terminal to change a comment in any file using its built-in Edit tool, not the tapestry tools. Within about 2 s that file's card shows the change, and its footer reads `changed by workspace.watcher · author unknown` with the eye glyph. The frame header's second row reads "Watching".
2. **Grouped checkout (Task 2).** In a scratch clone opened as a workspace, run `git checkout <other-branch>` in a terminal. One history entry, `observed changes: ...`, lists the changed files.
3. **Retry write (Task 2).** In a scratch workspace, run `chmod a-w <folder>`, then type in the window of a file inside it. After about 1 s the card shows red "Not written to file", with the reason in the tooltip, and a Retry write button. Run `chmod u+w <folder>` and choose Retry write. The file on disk now has the typed text.
4. **Folder missing.** Rename a scratch workspace folder away in Finder. The header says "The folder is missing; nothing is being recorded." and no cards disappear. Rename it back. Within about 5 s the header says "Watching" again.
5. **Feel (Task 3, backstop).** Pan and zoom across the whole frame of `~/Tapestrees/windows`, and type in an opened window. Report any lag: it decides whether lazy text over IPC, or a getNodes cache for the ~40 ms agent-edit cost, is needed next.
