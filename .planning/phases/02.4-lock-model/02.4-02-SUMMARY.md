# Phase 02.4 Plan 02: Allow Lists and Agent-Facing Lock Rule Summary

**Agents listed in `lock.<aspect>.allow` can now write through a lock, whether the lock is explicit or a default. The list must be a text value; it is split on whitespace and matched exactly, and any other value type admits nobody. End-to-end tests now pin five cases: bridge and plugin creators, people and plugins, deleted notes, growing and connecting, and a lock hidden by undo. The MCP tool text now tells agents about locks instead of authorship.**

## Accomplishments

- `resolveLock` fills `allow` using a new private helper, `readAllow(props, aspect)`, which reads `props[allowKey(aspect)]`. It uses the value only when the type is `text`, and splits it with `.trim().split(/\s+/)`, dropping empty strings. `checkLock` still admits an agent with `state.allow.includes(actor.id)`, so membership stays exact.
- 21 new test cases, 15 of them in Task 1: 7 allow-list cases (5 pure, 2 end to end) and 6 characterization cases. The Plan 01 pure test that pinned `allow: []` now expects the list to be read.
- The titles and descriptions of `update_note`, `rename_note` and `delete_note` now state the lock rule and say that a refusal names the lock's owner. No `lock.*` key names appear in them.
- Every D-05 citation in the files this phase touched now carries its phase prefix.
