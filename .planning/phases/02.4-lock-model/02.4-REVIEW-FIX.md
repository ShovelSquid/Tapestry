## Fixed Issues

### WR-01: A default lock's owner is matched by id alone, dropping the kind check D-05 had

**Files modified:** `app/src/main/commands/locks.ts`, `app/src/main/commands/locks.test.ts`
**Commit:** 52c5f6c
**Applied fix:**
- `LockState`'s locked variant has a new optional field, `ownerKind`. `resolveLock` sets it only on a default lock, to `createdBy.kind`.
- `checkLock` now admits the owner only when `state.owner === actor.id` and either `ownerKind` is unset or it equals `actor.kind`.
- Explicit `lock.<aspect>` owners still match on id alone, as D-08 requires, because they carry no `ownerKind`. Allow lists are unchanged.
- An agent-created note under `agentNotesOpenToAgents = false` still admits its own creator: that creator's kind is `plugin`, so the pair matches, as it did under the old D-05 gate.

**Tests:** I wrote the tests first and confirmed they failed (2 red) before the fix, then passed after it.
- Pure test: a default lock created by `human agent.claude` or `system agent.claude` refuses `plugin agent.claude` for both the `text` and `delete` aspects.
- Pure test: the creating agent still passes its own default lock, and a different agent is still refused.
- End-to-end test through `NoteCommands`: fixtures are written with a raw `submitAs` signed `human agent.claude` / `system agent.claude`. `updateNote` is refused and so is `deleteNote` (following `NON_AGENT_NOTES_DELETE_LOCKED`). `worldFingerprint()` is unchanged on each refusal (D-11).
- Existing default-lock `toEqual` expectations now include `ownerKind`. Explicit-lock expectations are unchanged.

**Status:** fixed. This is a logic change, so a human should confirm that "a default owner is the creator's kind and id together" is the intended reading of D-04.
