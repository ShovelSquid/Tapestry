# Phase 2.4: Code Review Report

**Reviewed:** 2026-09-16T12:40:00Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

This phase replaces the 02.2 D-05 authorship check with a pure lock resolver in `locks.ts`, which `NoteCommands.writeToNote` / `assertMayWrite` call. I checked each of the security properties in the brief:

- **Malformed `lock.*` fails closed.** It does. A non-`text` value stays locked. Only the exact text `open` unlocks. An empty or blank owner stays locked. A non-`text` allow list admits nobody.
- **Owner and allow-list matching is exact, not by prefix.** It is: the code uses `===` and `Array.includes` on whitespace-split tokens.
- **Refusals commit nothing.** They don't: `assertMayWrite` returns before `build`/`submitAs`, and the `worldFingerprint` assertions cover this.
- **Actor identity comes only from the host-stamped `Actor`.** It does. No MCP schema has an actor field, and `runAgentTool` passes the `actor` argument through.
- **No production path writes `lock.*`.** None of the reviewed files does. The only `lock.*` writes are the test fixture `setLockProp`.

`npx vitest run` on `locks.test.ts` and `notes-policy.test.ts` passed (64/64).

I found no blockers. There are three warnings:
1. The new owner match compares only the actor id. The check it replaced compared both kind and id.
2. A refused agent call still discards Kaelen's redo.
3. Nothing enforces the "nothing writes `lock.*`" rule. Any non-agent plugin can unlock every note.

## Warnings

### WR-01: A default lock's owner is matched by id alone, dropping the kind check D-05 had

**File:** `app/src/main/commands/locks.ts:157-161, 206`
**Issue:** For a note not created by an agent, `resolveLock` sets `owner: createdBy.id`. `checkLock` then admits any agent whose `actor.id === state.owner`. The actor kind is not compared. The old `assertOwnNote` checked `createdBy.kind !== actor.kind || createdBy.id !== actor.id`, so this is a regression.

Under D-04, a note "not created by an agent" is locked to its non-agent creator. An agent can therefore never be that owner. Yet a commit whose actor line is `human agent.claude` or `system agent.claude` produces the default lock `{owner: 'agent.claude'}`, and `plugin agent.claude` passes it. For example, `checkLock('n1', {}, {kind:'human', id:'agent.claude'}, {kind:'plugin', id:'agent.claude'}, 'text')` returns `null`.

The kernel's token rule accepts such ids (see the `actor.ts` header), and `locks.test.ts:249` itself treats `human agent.x` as a journal shape that can occur. In-app constructors can't produce it: `humanActor` forces `user.`. It can still arrive from a hand-edited or externally written `.tree`, and `.tree` files are human-editable by design.
**Fix:** Keep the creator's kind for default locks, and match on the pair. Alternatively, never let an agent satisfy a default lock owned by a non-agent:
```ts
// resolveLock, default branch for non-agent creators
const lockedToCreator: LockState = {
  locked: true,
  owner: createdBy.id,
  ownerKind: createdBy.kind,          // new, optional for explicit locks
  allow: readAllow(props, aspect),
}
// checkLock
const ownerMatches =
  state.owner === actor.id && (state.ownerKind === undefined || state.ownerKind === actor.kind)
if (ownerMatches || state.allow.includes(actor.id)) return null
```
Add a pure test: `checkLock('n1', {}, {kind:'human', id:'agent.claude'}, AGENT_CLAUDE, 'text')` should refuse.

### WR-02: A refused agent write still discards Kaelen's redo history

**File:** `app/src/main/commands/notes.ts:593-596` (also `connections.ts:122`)
**Issue:** `writeToNote` calls `prepareWrite` (which runs `discardRedo()`: it replays to the head and clears `undoStack`) *before* `assertMayWrite`. As a result, an agent call that is refused because the note is locked or not live still moves Kaelen's view to the head and throws away his redo stack. `locks.test.ts:731-749` locks this in by asserting `isRewound === false` after a refusal.

D-11 requires the check to run against the head state. It also says "a refusal writes nothing". The file is indeed unchanged, but the user-visible undo state is not. A misbehaving agent can repeatedly wipe Kaelen's redo with calls that are all refused and leave no journal trace. The only record is an `onRedoDiscarded` notice for a write that never happened.
**Fix:** Resolve the lock against the head *without* committing to the discard. One option is to snapshot and restore the undo state on refusal. Another is to add a bridge method that reads node props and history at `getLastSeq()`, and to call `discardRedo()` only after the check passes:
```ts
const refusal = this.assertMayWriteAtHead(tree, noteId, actor, aspect) // no discard
if (refusal) return { ok: false, error: refusal }
this.prepareWrite(tree, actor)
```
If D-11's ordering is meant to stay as written, record this trade-off explicitly in the Decision Register. Also stop announcing `onRedoDiscarded` for refused writes.

### WR-03: Nothing enforces "no production path writes `lock.*`"; any plugin can unlock every note

**File:** `app/src/main/commands/locks.ts:24-26` (the stated invariant). Unguarded writers: `app/src/main/plugin-host.ts:74` and `app/src/main/kernel-bridge.ts:411`.
**Issue:** The invariant holds only by convention. The generic plugin submit path (`plugin <id>`) and `kernel:submit` accept arbitrary `setProperty` ops, including `lock.text = open` and `lock.text.allow = agent.x`. A third-party plugin, which D-10 leaves unchecked, can open every note Kaelen and the Obsidian bridge created to all agents. It can also add itself to allow lists that agents then pass. That undoes D-04's protection with no lock-aware audit trail, and it writes the one-way `lock.*` keys (Decision Register #19) into append-only journals before the naming has been decided.
**Fix:** Until a `setLock` command exists, reject any op whose `key` starts with `lock.` on the plugin submit path, for example with a shared guard in `plugin-host.ts` beside `assertPluginSubmitKind`:
```ts
export function assertNoLockWrites(ops: OpObject[]): void {
  for (const op of ops) {
    if (op.op === 'setProperty' && typeof op.key === 'string' && op.key.startsWith('lock.')) {
      throw new Error('lock.* properties cannot be written yet (Decision Register #19)')
    }
    if (op.op === 'createNode' && op.props && Object.keys(op.props).some((k) => k.startsWith('lock.'))) {
      throw new Error('lock.* properties cannot be written yet (Decision Register #19)')
    }
  }
}
```
Decide separately whether the human `kernel:submit` path gets the same guard. Add a test that a plugin submit carrying `lock.text` is refused.

## Info

### IN-01: Non-text lock values still grant ownership to their stringified value

**File:** `app/src/main/commands/locks.ts:154`
**Issue:** A non-`text` `lock.<aspect>` resolves to `owner: String(explicit.value)`. An agent whose id equals that string would pass, which conflicts with D-08 ("`lock.<aspect>` is a `text` property"). It can't be exploited today: the kernel requires a `ref` to be a node or edge id and a `time` to be an event time, so no non-text value can equal `agent.*`. It is still a latent fail-open if a string-like type is ever added.
**Fix:** For non-text values, use a sentinel owner that no actor can match. For example, return `owner: \`${explicit.type}:${String(explicit.value)}\``, or set a flag that makes the owner check fail.

### IN-02: Pure tests exercise ref values the kernel would refuse

**File:** `app/src/main/commands/locks.test.ts:171-178, 291-293`
**Issue:** The `{type:'ref', value:'open'}` and `{type:'ref', value:'agent.chatgpt'}` cases can't exist in a real world, because `parseValue(Ref)` accepts only node or edge ids. The assertions are correct but test unreachable inputs, and they suggest ref-typed locks are a real risk. The reachable malformed types (`int`, `bool`, `real`, `time`) are covered only for `int`/`bool`.
**Fix:** Replace these with `real`/`time` cases, or add a comment saying they are defensive only.

### IN-03: Deleting an open note also removes connections made by other actors

**File:** `app/src/main/commands/notes.ts:558-562`
**Issue:** Under `AGENT_NOTES_OPEN_TO_AGENTS = true`, any agent may `deleteNode` any agent-created note. That cascades to edges Kaelen drew to it. Only the note's own `delete` aspect is checked, which matches the phase scope ("only the note itself is checked"). The effect on other actors' connections isn't mentioned in the `delete_note` tool description or the doc comment.
**Fix:** Record this in the deferred scope-cascade item, or mention it in the `deleteNote` comment.

### IN-04: Unused re-export of `isAgentActor`

**File:** `app/src/main/commands/notes.ts:22-23`
**Issue:** `export { isAgentActor } from './locks'` is kept "so existing importers keep working", but a repo-wide grep finds no importer of `isAgentActor` from `./notes`. The only other use is the local import on line 20.
**Fix:** Remove the re-export, or keep it and say which external consumer needs it.
