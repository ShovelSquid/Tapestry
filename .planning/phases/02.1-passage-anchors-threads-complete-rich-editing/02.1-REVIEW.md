## Summary

Reviewed the shared ProseMirror editor stack (schema, hook, passage plugin, toolbar commands), the four new/refactored React components, Canvas integration, CSS, and package.json for Phase 2.1. Cross-referenced consumers with grep across `app/src` and read the relevant App.tsx handlers (node creation, `handlePositionChange`, `handleEdgeCreate`).

The editor hook refactor (`use-prosemirror.ts`) is the strongest piece: echo detection, external sync, and debounce flushing on unmount are handled carefully. The rest of the phase has a wiring problem more than a code-style problem: **three of the headline features are unreachable in the running application**.

- No code creates `thread-center` nodes or `thread-arm` edges (`App.tsx handleEdgeCreate` still emits `label: 'link'`), no code ever sets `pinned`, and empty centers are `pointer-events: none` with no external hover path -- so thread centers cannot be created, revealed, or pinned.
- `FloatingToolbar` and `PassageChooser` are never rendered by any component; `NoteCard`'s `onSelectionChange` / `hasTextSelection` props are never passed by Canvas.
- The plan summaries' "TypeScript compiles clean" self-checks are vacuous: `npm run typecheck` only covers `tsconfig.node.json`, and the root `tsconfig.json` has `files: []`, so `npx tsc --noEmit` checks zero renderer files. No `node_modules` are present in this worktree, so I could not run a type check myself.

Beyond wiring, there are definite logic bugs: the toolbar's event-listener cleanup removes the wrong functions, `collectPassages` merges non-contiguous passage fragments into one range (highlighting unmarked text after an ordinary mid-passage delete), a title edit is silently lost if the card unmounts inside the 300 ms debounce window, alignment silently does nothing on headings, and list markers are invisible because the global CSS reset zeroes `ul`/`ol` padding while the editor clips overflow.

No structural findings were supplied to this review.

## Critical Issues

### CR-01: Dragging a thread center never pins it and submits a kernel command on every pointer move

**File:** `app/src/renderer/components/ThreadCenterNode.tsx:104-112` (also `:66-67`, `app/src/renderer/components/Canvas.tsx:534`)
**Issue:** `handlePointerMove` calls `onPositionChange` on every `pointermove` event. Canvas passes `App.tsx handlePositionChange`, which does a `kernel.submit` with two `setProperty` ops per call -- so a single drag emits dozens to hundreds of "Move note" commits into the branching history. Worse, nothing anywhere sets `pinned` (grep for `pinned` outside Canvas/ThreadCenterNode returns nothing; `handlePositionChange` only writes `position.x/y`). Since `posX = isPinned ? x : autoX` (line 66), the node keeps rendering at `autoX/autoY` throughout and after the drag: the user sees the node not move at all while the kernel history fills with position writes. The header comment ("After dragging, keeps user's position") and Plan 01 summary ("pinnable by drag") describe behavior that does not exist.
**Fix:**
```tsx
// ThreadCenterNode.tsx -- keep a local drag position, commit once on pointer-up
const [localPos, setLocalPos] = useState<{ x: number; y: number } | null>(null)
const posX = localPos?.x ?? (isPinned ? x : autoX)
const posY = localPos?.y ?? (isPinned ? y : autoY)

const handlePointerMove = useCallback((e: React.PointerEvent) => {
  if (!isDraggingRef.current) return
  const dx = (e.clientX - dragStartRef.current.mx) / zoom
  const dy = (e.clientY - dragStartRef.current.my) / zoom
  setLocalPos({ x: dragStartRef.current.ox + dx, y: dragStartRef.current.oy + dy })
}, [zoom])

const handlePointerUp = useCallback((e: React.PointerEvent) => {
  if (!isDraggingRef.current) return
  isDraggingRef.current = false
  ;(e.target as HTMLElement).releasePointerCapture(e.pointerId)
  setLocalPos((p) => { if (p) onPinnedPositionChange(nodeId, p.x, p.y); return p })
}, [nodeId, onPinnedPositionChange])
```
and add an App-level handler that submits `position.x`, `position.y`, **and** `pinned: { type: 'bool', value: true }` in one commit. Clear `localPos` when `x`/`y` props converge (same pattern as NoteCard lines 239-245).

### CR-02: Empty ("ghost") thread centers can never be revealed, so they can never be edited

**File:** `app/src/renderer/App.css:435-445` (also `app/src/renderer/components/Canvas.tsx:499, 571, 578`)
**Issue:** `.thread-center-node.ghost` sets `pointer-events: none`. The only ways out of `ghost` are the `hovered` class (`isHovered = hoveredNoteId === node.id`, set exclusively by the node's own `onMouseEnter`, which cannot fire with `pointer-events: none`) or `editing` (`editingNodeId === node.id`, set only by the node's own click handler -- same problem). D-18 says centers appear on *thread* hover, but the SVG overlay has `pointerEvents: 'none'` (Canvas line 499) and `ConnectionLine` has no pointer handlers, so thread hover does not exist either. Result: a freshly created center is a permanent invisible, unclickable element.
**Fix:** Derive `isHovered` for a center from its endpoints, not from itself:
```tsx
// Canvas.tsx, inside the thread-center map
const endpointIds = [sourceEdge?.from, destEdge?.to].filter(Boolean) as string[]
const isHovered =
  hoveredNoteId === node.id || (hoveredNoteId !== null && endpointIds.includes(hoveredNoteId))
```
and/or give `ConnectionLine` a wide transparent hit-path with `pointer-events: stroke` and an `onHover` callback that sets `hoveredNoteId` to the thread center id. Also consider `setEditingNodeId(centerId)` right after creating a center so the first one is immediately editable.

(and the same in ThreadCenterNode), then thread `onSelectionChange`/`hasTextSelection` from Canvas so `applyPassageMark` has a caller. Until that is done, either delete these files or record them explicitly as unwired in the phase verification so the roadmap does not treat D-15/D-24 as complete.

### CR-04: FloatingToolbar removes the wrong event listeners, so handlers leak and keep firing against a stale view

**File:** `app/src/renderer/components/FloatingToolbar.tsx:97-103`
**Issue:** The effect registers two anonymous arrow functions (`() => setTimeout(update, 10)`), assigns their `void` return value to `plugin` / `keyup`, then the cleanup calls `removeEventListener('mouseup', update)` with a *different* function. Nothing is ever removed. Every time `view` or `containerRef` changes, a new pair of listeners is added on top of the old ones; the old listeners close over the previous `view` and will call `setPosition`/`setVisible` on this component (or, after unmount, on a dead component) and `view.coordsAtPos` on a possibly-destroyed EditorView, which throws once `docView` is gone.
**Fix:**
```tsx
const onMouseUp = () => setTimeout(update, 10)
const onKeyUp = () => setTimeout(update, 10)
view.dom.addEventListener('mouseup', onMouseUp)
view.dom.addEventListener('keyup', onKeyUp)
return () => {
  view.dom.removeEventListener('mouseup', onMouseUp)
  view.dom.removeEventListener('keyup', onKeyUp)
}
```
Enable `noUnusedLocals` in `tsconfig.web.json`; it would have flagged `plugin` and `keyup` immediately.

### CR-05: `collectPassages` merges disjoint fragments with the same anchorId into one span, decorating unmarked text

**File:** `app/src/renderer/editor/passage-plugin.ts:55-78`
**Issue:** For each inline node carrying a passage mark, the scan extends an existing entry with `Math.min(from)` / `Math.max(to)`. That is only correct if every fragment with the same `anchorId` is contiguous. It is not: select the middle of a passage and press Delete/Backspace, or paste unmarked text into its middle (the `inclusive: false` mark is not applied to pasted content), and you get two marked fragments with an unmarked gap. The plugin then reports the whole `[min, max]` range as the passage -- the gap text gets the idle/active highlight and hovering over unmarked text fires `onPassageHover(anchorId)`. Because the same range feeds the sort by span length, gradient ordering between overlapping passages is also computed from the wrong lengths. Copying a passage's text elsewhere in the same note (WR-08) makes this worse by bridging the entire document.
**Fix:** Keep one entry per contiguous run instead of per anchorId:
```ts
function collectPassages(doc: EditorState['doc']): PassageInfo[] {
  const passages: PassageInfo[] = []
  doc.descendants((node, pos) => {
    if (!node.isInline) return
    for (const mark of node.marks) {
      if (mark.type.name !== 'passage' || !mark.attrs.anchorId) continue
      const last = passages.findLast((p) => p.anchorId === mark.attrs.anchorId)
      if (last && last.to === pos) last.to = pos + node.nodeSize   // contiguous: extend
      else passages.push({ anchorId: mark.attrs.anchorId, from: pos, to: pos + node.nodeSize })
    }
  })
  return passages
}
```
Then either treat each run as its own hover target, or group runs by anchorId when computing "containing" but decorate only the actual runs.

### CR-06: A title edit is silently lost if the card unmounts within the 300 ms debounce

**File:** `app/src/renderer/components/NoteCard.tsx:497-506`
**Issue:** The title `onChange` starts a 300 ms timer that later reads `viewRef.current` to build the body and calls `onSave`. Nothing cancels or flushes `titleDebounceRef` on unmount. The hook's cleanup (use-prosemirror.ts 226-241) only flushes the *body* debounce. If the card unmounts inside the window (close file, delete note, plugin toggle, `node.id` change), the timer still fires: it calls `onMarkClean(node.id)` -- so the save indicator reports "Saved" -- then finds `viewRef.current === null` and skips `onSave`. The typed title is gone and the UI claimed it was persisted. This is a data-loss path in exactly the "type then immediately close" case the D-02 autosave design is supposed to protect.
**Fix:**
```tsx
useEffect(() => {
  return () => {
    if (titleDebounceRef.current) {
      clearTimeout(titleDebounceRef.current)
      titleDebounceRef.current = null
      onMarkClean(node.id)
      const view = viewRef.current
      const b = view ? JSON.stringify(view.state.doc.toJSON()) : body
      onSaveRef.current(node.id, b, localTitleRef.current)
    }
  }
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [node.id])
```
Order matters: declare this effect *before* the `useProseMirror` call so its cleanup runs while the view still exists, or have the hook expose `forceSave` with a title parameter and call it here.

## Warnings

### WR-01: Alignment silently does nothing on headings, and converting to a heading drops alignment

**File:** `app/src/renderer/editor/toolbar-commands.ts:82-92` (also `:17-26`, `app/src/renderer/editor/schema.ts:109-128`)
**Issue:** `setAlignment` calls `setNodeMarkup(pos, undefined, { ...node.attrs, align })` for headings, but only `paragraph` was given an `align` attribute in the schema; `heading` is the unmodified `prosemirror-schema-basic` spec. `NodeType.create` → `computeAttrs` builds attrs only from the type's declared attrs, so `align` is dropped without error, and the basic heading `toDOM` would not render it anyway. The user picks "Center" on a heading and nothing happens. Conversely, `setHeading`/`setParagraph` pass fresh attrs (`{ level }` / none) so any existing `align` on the paragraph is lost on conversion.
**Fix:** Extend the heading spec the same way as the paragraph (attrs `{ level, align }`, `toDOM` emitting `text-align`), update `nodesWithAlign` with both, and preserve `align` in `setHeading`:
```ts
const { $from } = view.state.selection
setBlockType(node, { level, align: $from.parent.attrs.align ?? null })(view.state, view.dispatch)
```

### WR-02: List toggling nests instead of converting, and uses `lift` instead of `liftListItem`

**File:** `app/src/renderer/editor/toolbar-commands.ts:28-54`
**Issue:** `toggleBulletList` inside an *ordered* list finds `isInList(bullet_list) === false` and calls `wrapInList(bullet_list)`, which wraps the current item's content in a new bullet list nested inside the ordered item rather than converting the list type. `isInList` also matches any ancestor, so in a bullet list nested inside an ordered list, "toggle ordered" lifts the paragraph one level (out of the bullet list) instead of leaving the ordered list. `lift` is the generic block lift; `liftListItem(list_item)` from `prosemirror-schema-list` is the idiomatic, multi-item-aware command.
**Fix:**
```ts
import { wrapInList, liftListItem } from 'prosemirror-schema-list'
function toggleList(view: EditorView, listType: NodeType) {
  const { $from } = view.state.selection
  const range = $from.blockRange()
  const parentList = range && $from.node(range.depth - 1)
  if (parentList?.type === listType) {
    liftListItem(tapestrySchema.nodes.list_item)(view.state, view.dispatch)
  } else if (parentList && parentList.type.spec.group?.includes('block') && parentList.type !== listType
             && (parentList.type === tapestrySchema.nodes.bullet_list || parentList.type === tapestrySchema.nodes.ordered_list)) {
    view.dispatch(view.state.tr.setNodeMarkup($from.before(range!.depth - 1), listType))
  } else {
    wrapInList(listType)(view.state, view.dispatch)
  }
  view.focus()
}
```

### WR-03: Toolbar active-state indicators go stale after clicking a toolbar button

**File:** `app/src/renderer/components/FloatingToolbar.tsx:106-110, 122`
**Issue:** `boldActive`, `italicActive`, and `blockType` are computed during render from `view.state`, but the component only re-renders when its own `visible`/`position`/`openSubmenu` state changes. Toolbar buttons use `onMouseDown` with `preventDefault`, and the subsequent `mouseup` lands on the button (outside `view.dom`), so neither `update` listener runs. After clicking **B**, the document is bold but the button does not show `.active` until the user next clicks or types inside the editor.
**Fix:** Force a re-render after each command, e.g. keep a `const [, bump] = useReducer((n) => n + 1, 0)` and wrap every handler: `onMouseDown={(e) => { e.preventDefault(); toggleBold(view); bump() }}`. Better: subscribe to the view once via a tiny plugin `view()` hook or by wrapping `dispatchTransaction` in `useProseMirror` to emit a "transaction" event the toolbar listens to.

### WR-04: Toolbar position ignores canvas zoom

**File:** `app/src/renderer/components/FloatingToolbar.tsx:89-93`
**Issue:** `top`/`left` are computed as differences of `getBoundingClientRect` values (screen pixels) and applied as `position: absolute` offsets inside a container that lives under `transform: scale(zoom)` (`.tapestry-canvas-container`). Absolute offsets inside a scaled ancestor are in the ancestor's *local* units, so at zoom 2 the toolbar lands twice as far from the selection; at zoom 0.5 it overlaps the text. NoteCard divides every screen delta by `zoom` for exactly this reason (lines 313-314, 372-373); the toolbar has no `zoom` prop at all. The hard-coded `44` is also a magic offset.
**Fix:** Accept a `zoom` prop and divide: `top: (start.top - containerRect.top) / zoom - TOOLBAR_OFFSET`, `left: ((start.left + end.left) / 2 - containerRect.left) / zoom`.

### WR-05: Passage plugin dispatches a transaction on every pixel of mouse movement, including during IME composition

**File:** `app/src/renderer/editor/passage-plugin.ts:200-215`
**Issue:** `mousemove` dispatches whenever `posAtCoords` differs from the stored `hoverPos`; moving across a line changes `pos` at every character, so this fires a full `state.apply` + `updateState` + decoration diff per pixel. It never checks `view.composing`. ProseMirror documents that dispatching state updates while an IME composition is in progress can flush the composition; decorations changing under the composed text are a classic cause of dropped or duplicated characters. IME composition is an explicit acceptance criterion in the feasibility gate (CLAUDE.md "Editable note plugin" row). `posAtCoords` also returns a nearest position when the pointer is in the margin beside a line, so passages light up while the pointer is not over any text.
**Fix:**
```ts
mousemove(view, event) {
  if (view.composing) return false
  const pos = view.posAtCoords({ left: event.clientX, top: event.clientY })
  const docPos = pos && pos.inside >= 0 ? pos.pos : null   // only when actually over content
  ...
}
```
and consider throttling with `requestAnimationFrame` so at most one hover transaction per frame is dispatched.

### WR-06: `onPassageHover` side effect lives inside the plugin state reducer

**File:** `app/src/renderer/editor/passage-plugin.ts:189-192`
**Issue:** `state.apply` is expected to be pure. ProseMirror calls it for every transaction that is *applied*, not only ones that are *dispatched*: `EditorState.applyTransaction` re-runs the chain when any plugin's `appendTransaction` adds a step, and callers (including the hook's `view.state.apply(tr)` on line 202 of use-prosemirror.ts) may apply speculatively. The callback fires React state updates in Canvas from inside ProseMirror's reducer, and if a consumer ever calls `state.apply` without `updateState` the callback fires for a state that never became current. It also fires during `init`-adjacent rescans on every `docChanged` transaction even when nothing hover-related changed.
**Fix:** Move the notification into the plugin's `view()` lifecycle, comparing previous and current plugin state:
```ts
view() {
  return {
    update(view, prevState) {
      const prev = passagePluginKey.getState(prevState)?.activeAnchorId ?? null
      const next = passagePluginKey.getState(view.state)?.activeAnchorId ?? null
      if (prev !== next) onPassageHover?.(next)
    },
  }
}
```

### WR-07: Unvalidated `color` / `family` attributes are interpolated into inline `style` -- CSS injection via paste

**File:** `app/src/renderer/editor/schema.ts:59-64, 72-73, 88-89, 98`
**Issue:** `parseDOM` accepts any `data-text-color` / `data-font-family` value from pasted HTML and `toDOM` writes it verbatim into `style="color: ${...}"`. The renderer sets no Content-Security-Policy (grep for `Content-Security-Policy` in `app/src` and `index.html` is empty). Pasting `<span data-text-color="red; background:url(https://attacker.example/beacon)">` from a web page persists the value into the `.tree` file and issues a network request every time the note is rendered, on every machine that opens the world. Font family is unbounded the same way. Impact is bounded (no script execution) but it is persistent, user-invisible, and violates the "readable, under your control" constraint because the stored value is not a color.
**Fix:** Validate in `getAttrs` and reject anything outside the allowlist the toolbar offers:
```ts
const HEX = /^#[0-9a-fA-F]{6}$/
getAttrs(dom) {
  const c = dom.getAttribute('data-text-color') ?? ''
  return HEX.test(c) ? { color: c } : false     // false = do not match this rule
}
```
Do the same for font family against `FONT_FAMILIES`, and add a restrictive CSP meta tag to the renderer HTML.

### WR-08: Copy/paste duplicates passage `anchorId`s across notes and within a note

**File:** `app/src/renderer/editor/schema.ts:35-42` (also `app/src/renderer/editor/use-prosemirror.ts:189-193`, no `transformPasted`)
**Issue:** The passage `parseDOM` rule re-creates the mark from `data-passage-id` on paste. ProseMirror's clipboard serializer emits that span, so copying passage text and pasting it into another note (or elsewhere in the same note) produces a second region claiming the same `anchorId`. Anchors are meant to be unique endpoints of a thread; after a paste, the thread has two sources, `collectPassages` bridges them (CR-05), and the kernel-side edge target becomes ambiguous. Plan 01 summary lists this as a "known risk" but no mitigation was implemented.
**Fix:** Strip passage marks from pasted content in the editor hook:
```ts
new Plugin({
  props: {
    transformPasted(slice) {
      const passage = tapestrySchema.marks.passage
      return new Slice(
        mapFragment(slice.content, (n) => n.mark(passage.removeFromSet(n.marks))),
        slice.openStart, slice.openEnd)
    },
  },
})
```
(or alternatively set `clipboardSerializer` to drop the `data-passage-id` attribute).

### WR-09: `deserializeBody` silently turns schema-invalid JSON into visible text, then re-saves it as text

**File:** `app/src/renderer/editor/use-prosemirror.ts:98-109`
**Issue:** `tapestrySchema.nodeFromJSON(parsed)` is inside the same `try` as `JSON.parse`. If a body is valid JSON but fails schema validation (unknown node/mark from a newer plugin version, corrupted attrs), the `RangeError` is swallowed by the `catch` whose comment says "Not JSON". The user then sees the raw JSON text in the note, and their next keystroke saves that JSON as plain paragraphs -- the readable body is replaced by an escaped blob. History preserves the original, but nothing tells the user a downgrade happened.
**Fix:** Separate the two failure modes; only plain-text fallback when the body is not JSON at all:
```ts
let parsed: unknown
try { parsed = JSON.parse(body) } catch { return plainTextToDoc(body) }
if (parsed && typeof parsed === 'object' && (parsed as any).type === 'doc') {
  try { return tapestrySchema.nodeFromJSON(parsed) }
  catch (err) { console.error('Body failed schema validation', err); return null /* render read-only fallback */ }
}
return plainTextToDoc(body)
```
and make the caller render a non-editable "unreadable body" state instead of an editor when `null` is returned for a JSON body.

### WR-10: ThreadCenterNode `isEmpty` check is wrong; a cleared center never returns to ghost state

**File:** `app/src/renderer/components/ThreadCenterNode.tsx:133`
**Issue:** `!body || body === '""' || body === ''` -- the first clause already covers `''`, and `'""'` (a two-character string of quotes) is never produced by `serializeBody` or by App.tsx (which creates `body: ''`). After the user types one character and deletes it, the hook saves `{"type":"doc","content":[{"type":"paragraph"}]}`, which is non-empty by this test, so the center stays permanently visible even though it has no text. The D-18 rule ("once they have text they remain visible") is evaluated on serialization shape, not on text.
**Fix:**
```ts
function bodyHasText(body: string): boolean {
  if (!body) return false
  try { const j = JSON.parse(body); return j?.type === 'doc' ? tapestrySchema.nodeFromJSON(j).textContent.trim().length > 0 : body.trim().length > 0 }
  catch { return body.trim().length > 0 }
}
const isEmpty = !bodyHasText(body)
```

### WR-11: PassageChooser dismiss timer can never be cancelled and fires after unmount

### WR-12: List bullets and numbers are invisible inside note editors

### WR-13: Thread-arm connection lines are drawn to the stored position, not the displayed auto-position

**File:** `app/src/renderer/components/Canvas.tsx:502-505` (with `:200-213`, `:551-558`)
**Issue:** `edges.map` resolves both endpoints via `getNodeCenter`, which reads `position.x/y` props. For an unpinned thread center the node is *rendered* at `autoX/autoY` (midpoint of its endpoints), but its stored position is whatever it was created with. Both `thread-arm` lines therefore terminate at a phantom point that drifts further from the visible center every time an endpoint note is moved. The "-100" / "-22" offsets (lines 553, 557) also assume the rendered height is exactly 44px, so a center with two lines of text is off-center vertically.
**Fix:** Compute the thread-center auto positions once (a `Map<centerId, {x,y}>`) before rendering edges, and have `getNodeCenter` consult that map for unpinned centers using the registered dims from `nodeDimsRef` for the half-height instead of the literal 22.

### WR-14: `npm run typecheck` never checks renderer code; the plan summaries' "compiles clean" claims are vacuous

**File:** `app/package.json:13` (with `app/tsconfig.json`)
**Issue:** The `typecheck` script is `tsc --noEmit -p tsconfig.node.json`, which includes only `src/main` and `src/preload`. The root `tsconfig.json` has `files: []` plus project references, so a bare `npx tsc --noEmit` (what the summaries say was run) type-checks zero files and exits 0. Every file in this review lives under `src/renderer` and is therefore only transpiled by Vite (which, as CLAUDE.md notes, "transpiles TS without checking it"). The `void`-typed `plugin`/`keyup` locals in CR-04 would at minimum have been flagged with `noUnusedLocals`. This script is pre-existing, but this phase relied on it for its self-checks.
**Fix:**
```json
"typecheck": "tsc --noEmit -p tsconfig.node.json && tsc --noEmit -p tsconfig.web.json"
```
and add `"noUnusedLocals": true, "noUnusedParameters": true` to `tsconfig.web.json`. Re-run before closing the phase; I could not run it here because `node_modules` is absent in this worktree.
