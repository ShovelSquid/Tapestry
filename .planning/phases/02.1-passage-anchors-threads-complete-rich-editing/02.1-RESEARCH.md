# Phase 2.1: Passage Anchors, Threads & Complete Rich Editing - Research

**Researched:** 2026-09-09
**Domain:** ProseMirror inline annotations, spatial node graph, rich text formatting
**Confidence:** MEDIUM

## Summary

This phase adds passage-level linking (persistent text range anchors), thread center nodes, gradient-of-focus hover highlighting, and a complete floating formatting toolbar to the existing Electron + React + ProseMirror editor. The technical core is a custom ProseMirror mark type (`passage`) with `excludes: ""` that permits overlapping instances, each carrying a unique anchor ID. These marks persist in the serialized ProseMirror JSON document and map to kernel edges connecting the passage anchor to its destination. Thread center nodes are a new kernel node type (`tapestry.notes/thread-center@1`) positioned automatically at the midpoint between endpoint nodes.

The gradient-of-focus hover hierarchy requires a ProseMirror plugin that tracks the cursor position, identifies all passage marks at that position, sorts them by span length, and applies CSS classes or inline styles with descending opacity. The floating formatting toolbar is a React component positioned using ProseMirror's `EditorView.coordsAtPos()` API, with submenu hover delays matching the UI-SPEC's 300ms collapse timer.

**Primary recommendation:** Use ProseMirror marks (not decorations) for passage anchors, because marks persist in the document model and survive serialization/deserialization through the existing JSON codec. Use a ProseMirror plugin with the `decorations` prop to render the gradient-of-focus highlighting as inline decorations derived from the mark state.

### Pattern 1: Passage Anchor as ProseMirror Mark with `excludes: ""`

**What:** Define a custom `passage` mark type with `excludes: ""` so multiple passage marks can overlap on the same text. Each mark instance carries a unique `anchorId` attribute that connects it to a kernel edge.

**When to use:** Whenever text needs a persistent, identifiable range that survives editing and serialization.

**Example:**
```typescript
// Source: ProseMirror guide (marks section) + discuss.prosemirror.net
const passageMark: MarkSpec = {
  attrs: {
    anchorId: { default: '' },  // unique ID linking to kernel edge
  },
  excludes: '',  // allow overlapping with self and all other marks
  inclusive: false,  // new text typed at boundaries does NOT inherit the mark
  parseDOM: [{
    tag: 'span[data-passage-id]',
    getAttrs(dom: HTMLElement) {
      return { anchorId: dom.getAttribute('data-passage-id') || '' }
    },
  }],
  toDOM(mark) {
    return ['span', {
      'data-passage-id': mark.attrs.anchorId,
      class: 'tapestry-passage',
    }, 0]
  },
}
```

**Key behaviors:**
- `excludes: ""` permits multiple passage marks on the same text range [CITED: discuss.prosemirror.net/t/copy-pasting-overlapping-marks-of-the-same-type/1744]
- `inclusive: false` prevents new text typed at the boundary from inheriting the passage mark, matching D-11's "boundary-insertion affinity" contract -- text inserted at the edge of a passage does NOT automatically become part of it
- The `anchorId` is generated in the renderer (UUID or similar) when the user creates a passage link, then stored as an edge property in the kernel so the connection between anchor and destination survives save/reload

### Pattern 2: Gradient-of-Focus via ProseMirror Decoration Plugin

**What:** A ProseMirror plugin that listens for cursor/hover position changes, finds all passage marks at that position, sorts them by span length (shortest = strongest), and creates inline decorations with CSS classes encoding the focus level.

**When to use:** D-14 requires a hover hierarchy where the smallest passage at the pointer is visually strongest.

**Example:**
```typescript
// Source: ProseMirror guide (decorations section)
import { Plugin, PluginKey } from 'prosemirror-state'
import { DecorationSet, Decoration } from 'prosemirror-view'

const passagePluginKey = new PluginKey('passage')

// In the plugin's props.decorations callback:
function computeGradientDecorations(
  doc: Node,
  hoverPos: number | null,
  allPassages: Array<{ anchorId: string; from: number; to: number }>
): DecorationSet {
  const decorations: Decoration[] = []

  // Idle state: all passages get subtle background
  for (const p of allPassages) {
    decorations.push(
      Decoration.inline(p.from, p.to, {
        class: 'tapestry-passage-idle',
        // rgba(74, 124, 255, 0.08) per UI-SPEC
      })
    )
  }

  if (hoverPos !== null) {
    // Find passages containing hoverPos, sort by length (ascending)
    const containing = allPassages
      .filter(p => p.from <= hoverPos && p.to >= hoverPos)
      .sort((a, b) => (a.to - a.from) - (b.to - b.from))

    for (let i = 0; i < containing.length; i++) {
      const level = i === 0 ? 'active' : i === 1 ? 'level1' : 'level2'
      decorations.push(
        Decoration.inline(containing[i].from, containing[i].to, {
          class: `tapestry-passage-${level}`,
        })
      )
    }
  }

  return DecorationSet.create(doc, decorations)
}
```

### Pattern 3: Thread Center Node Auto-Positioning

**What:** Thread center nodes are kernel nodes of type `tapestry.notes/thread-center@1` with `position.x`, `position.y`, and `pinned` properties. When `pinned` is false (default), the renderer computes position as the midpoint between the two endpoint node centers. When the user drags the center node, `pinned` is set to true and the user's position persists.

**When to use:** D-17 requires automatic midpoint placement until manually dragged.

**Example:**
```typescript
// Midpoint calculation for auto-positioned thread center nodes
function computeThreadCenterPosition(
  fromCenter: { x: number; y: number },
  toCenter: { x: number; y: number },
): { x: number; y: number } {
  return {
    x: (fromCenter.x + toCenter.x) / 2,
    y: (fromCenter.y + toCenter.y) / 2,
  }
}
```

### Pattern 4: Shared ProseMirror Editor Hook

**What:** Extract ProseMirror initialization, lifecycle, and serialization into a shared React hook (`useProseMirror`) that both `NoteCard` and `ThreadCenterNode` consume. This ensures D-26 (universal editing) -- identical editor behavior across both node types.

**When to use:** Any component that needs the full ProseMirror editor with passage marks, formatting, and autosave.

### Anti-Patterns to Avoid

- **Decorations for persistence:** Do not use ProseMirror decorations as the primary storage for passage anchors. Decorations are ephemeral rendering hints -- they must be rebuilt on every state change and do not serialize with the document. The Remirror annotation extension uses decorations but requires a separate position-tracking data store that must be manually mapped through every edit. Marks avoid this complexity. [CITED: remirror.io/docs/extensions/annotation-extension/]

- **Multiple ProseMirror schemas:** Do not create separate schemas for NoteCard vs ThreadCenterNode. D-26 requires identical editing behavior. Use one shared schema imported from `editor/schema.ts`.

- **Inline styles for passage highlighting:** Do not apply passage highlight colors as inline styles on the ProseMirror DOM. Use CSS classes with the opacity values from UI-SPEC. Inline styles would fight with ProseMirror's DOM reconciliation.

- **Polling for hover position:** Do not use `setInterval` to check cursor position. Use ProseMirror's `handleDOMEvents` plugin prop to listen for `mouseover`/`mousemove` and `posAtCoords` to convert mouse coordinates to document positions.

- **Storing passage ranges as kernel properties:** Do not store the from/to character offsets of passages as kernel node properties. They would go stale on every text edit. The ProseMirror mark IS the position -- it moves with the text automatically through ProseMirror's content-aware editing.

## Common Pitfalls

### Pitfall 1: Overlapping Mark Copy/Paste Corruption
**What goes wrong:** When copying text containing overlapping marks of the same type (`excludes: ""`), the clipboard HTML nests `<span>` elements. ProseMirror's `DOMParser` may fail to reconstruct all mark instances from the nested DOM, dropping inner marks.
**Why it happens:** ProseMirror's flat inline model does not natively map from nested DOM elements back to multiple marks of the same type. The parser sees `<span data-passage-id="a"><span data-passage-id="b">text</span></span>` and may only parse the outer mark.
**How to avoid:** Implement a custom `clipboardParser` or `clipboardSerializer` in the editor view props that explicitly handles the overlapping passage mark case. Test copy/paste of overlapping passages as a specific verification scenario.
**Warning signs:** Passage marks disappearing after paste, or passages merging into a single anchor after copy/paste. [CITED: discuss.prosemirror.net/t/copy-pasting-overlapping-marks-of-the-same-type/1744]

### Pitfall 2: ProseMirror Mark Boundary Editing Behavior
**What goes wrong:** With `excludes: ""`, typing at the exact boundary between two adjacent passage marks may apply neither, one, or both marks to the new text, depending on `inclusive` settings and cursor position.
**Why it happens:** ProseMirror's `inclusive` property on marks controls whether new text typed at a mark boundary inherits the mark. With `inclusive: false`, text at boundaries does not inherit. With `inclusive: true`, it does. The behavior at exact boundaries between two marks is ProseMirror's storedMarks mechanism.
**How to avoid:** Set `inclusive: false` on the passage mark. When a user explicitly types inside a passage (cursor between passage start and end), the passage mark will already be on the text nodes there. New text at the exact start or end boundary should NOT inherit the mark, matching D-11's "boundary-insertion affinity" design.
**Warning signs:** New text typed at passage edges unexpectedly gaining or losing passage marks.

### Pitfall 3: Stale Passage Decorations After Transaction
**What goes wrong:** The gradient-of-focus decorations show highlighting for passages that no longer exist, or miss newly created passages.
**Why it happens:** The decoration computation uses a cached list of passages that was not updated when a transaction changed the document.
**How to avoid:** Recompute the passage list from the current document state on every transaction in the plugin's `apply` method. Extract all passage marks from the document using `doc.descendants()` and store them in plugin state. Map the hover position through the transaction mapping.
**Warning signs:** Ghost highlights on text that has no passage mark, or new passages that don't highlight.

### Pitfall 4: Toolbar Position Drift During Scroll/Pan
**What goes wrong:** The floating toolbar stays at its original screen position while the user pans or zooms the canvas, ending up far from the selected text.
**Why it happens:** `coordsAtPos()` returns viewport-relative coordinates at call time, but the canvas transform changes independently.
**How to avoid:** Recompute toolbar position on every canvas pan/zoom change. Listen for the canvas `view` state (panX, panY, zoom) changes and call `coordsAtPos()` again. Also recompute on window scroll/resize.
**Warning signs:** Toolbar floating in empty space after panning, or jumping when the user starts typing.

### Pitfall 5: Focus Steal Between ProseMirror Editors
**What goes wrong:** During passage-to-passage connection (D-10 Flow B), clicking in the destination note to begin editing steals focus from the source note, and the source text selection (which defines the source passage) is lost.
**Why it happens:** DOM focus is exclusive -- only one element can be focused. Moving focus to the destination ProseMirror editor destroys the selection in the source editor.
**How to avoid:** When the user clicks the connect bubble to "hold" the source passage (Flow B step 2), capture the from/to positions and the anchor ID into React state. The held passage state is independent of ProseMirror selection. The source passage bracket renders from this React state, not from the ProseMirror selection.
**Warning signs:** Source passage highlight disappearing when clicking in the destination note.

### Pitfall 6: Thread Center Node Z-Order and Click Passthrough
**What goes wrong:** Thread center nodes sit on top of connection lines in the canvas. Clicking a connection line to follow a thread instead hits the transparent background of a nearby center node.
**Why it happens:** Thread center nodes are positioned between endpoints, directly on top of the connection lines. If their hit area is too large, they intercept clicks meant for the line.
**How to avoid:** Empty thread center nodes should have `pointer-events: none` except for a small clickable target (the 44px dashed circle per UI-SPEC). Only visible (text-containing) center nodes should capture all pointer events.
**Warning signs:** Inability to hover or click thread lines when center nodes are nearby.

### Shared ProseMirror Schema with Passage Mark, Lists, Colors, Fonts

```typescript
// editor/schema.ts
// Source: ProseMirror guide + prosemirror-schema-list README
import { Schema, MarkSpec, NodeSpec } from 'prosemirror-model'
import { schema as basicSchema } from 'prosemirror-schema-basic'
import { addListNodes } from 'prosemirror-schema-list'

// Custom marks for D-23 formatting
const textColorMark: MarkSpec = {
  attrs: { color: { default: '#2C2C2C' } },
  parseDOM: [{
    tag: 'span[data-text-color]',
    getAttrs: (dom: HTMLElement) => ({ color: dom.getAttribute('data-text-color') }),
  }],
  toDOM(mark) {
    return ['span', { 'data-text-color': mark.attrs.color, style: `color: ${mark.attrs.color}` }, 0]
  },
}

const fontFamilyMark: MarkSpec = {
  attrs: { family: { default: '' } },
  parseDOM: [{
    tag: 'span[data-font-family]',
    getAttrs: (dom: HTMLElement) => ({ family: dom.getAttribute('data-font-family') }),
  }],
  toDOM(mark) {
    return ['span', {
      'data-font-family': mark.attrs.family,
      style: mark.attrs.family ? `font-family: ${mark.attrs.family}` : '',
    }, 0]
  },
}

const passageMark: MarkSpec = {
  attrs: { anchorId: { default: '' } },
  excludes: '',
  inclusive: false,
  parseDOM: [{
    tag: 'span[data-passage-id]',
    getAttrs: (dom: HTMLElement) => ({ anchorId: dom.getAttribute('data-passage-id') }),
  }],
  toDOM(mark) {
    return ['span', { 'data-passage-id': mark.attrs.anchorId, class: 'tapestry-passage' }, 0]
  },
}

// Add list nodes to basic schema nodes
const listNodes = addListNodes(basicSchema.spec.nodes, 'paragraph block*', 'block')

// Add text alignment as a node attribute on paragraph and heading
// (alignment is a block-level property, not a mark)
const alignedParagraph: NodeSpec = {
  ...basicSchema.spec.nodes.get('paragraph')!,
  attrs: { align: { default: null } },
  // parseDOM and toDOM handle the align attribute
}

export const tapestrySchema = new Schema({
  nodes: listNodes.update('paragraph', alignedParagraph),
  marks: basicSchema.spec.marks
    .addBefore('link', 'passage', passageMark)
    .addToEnd('textColor', textColorMark)
    .addToEnd('fontFamily', fontFamilyMark),
})
```

### Toolbar Positioning with coordsAtPos

```typescript
// Source: ProseMirror reference manual (EditorView.coordsAtPos)
function getToolbarPosition(
  view: EditorView,
  canvasPanX: number,
  canvasPanY: number,
  canvasZoom: number,
): { left: number; top: number } | null {
  const { from, to } = view.state.selection
  if (from === to && view.state.doc.content.size === 0) return null

  const start = view.coordsAtPos(from)
  const end = view.coordsAtPos(to, -1)

  // Selection bounding box in viewport coordinates
  const left = Math.min(start.left, end.left)
  const right = Math.max(start.right, end.right)
  const top = Math.min(start.top, end.top)

  return {
    left: (left + right) / 2,  // center horizontally
    top: top - 16,              // 16px gap above selection (UI-SPEC md spacing)
  }
}
```

1. **Copy/paste of overlapping passage marks**
   - What we know: ProseMirror's `DOMParser` has known issues reconstructing overlapping marks of the same type from nested DOM. A custom `clipboardParser` may be needed.
   - What's unclear: Whether the current ProseMirror versions (1.24+) have fixed this, and what the exact custom parser implementation looks like.
   - Recommendation: Implement basic passage marks first, test copy/paste, and add a custom clipboard handler if marks are lost.

2. **Passage mark behavior during text deletion at boundaries**
   - What we know: D-11 says deleting all enclosed text leaves an empty point anchor. ProseMirror marks cannot exist on zero-width text ranges.
   - What's unclear: How to implement an "empty point anchor" -- a zero-width mark is not possible in ProseMirror. Options: (a) use a zero-width space character carrying the mark, (b) convert to a widget decoration at the empty position, (c) keep the mark on the kernel edge and display a widget when the text is empty.
   - Recommendation: Option (c) -- when all passage text is deleted, remove the mark from ProseMirror but keep the kernel edge. Render a small inline widget decoration at the position to show the anchor point. The kernel edge preserves the thread.

3. **Thread center node deletion cascading**
   - What we know: D-19 says deleting the thread center's structure cuts the thread and its connections. D-20 says clearing content preserves the node.
   - What's unclear: When a thread center is deleted, should the two `thread-arm` edges be deleted by the kernel's cascade (DeleteNode cascades edges touching it), and should the main `thread` edge also be deleted?
   - Recommendation: Yes -- the kernel already cascades edges on DeleteNode. The `thread` edge connects the two endpoints directly; deleting the center node should also explicitly delete the `thread` edge in the same atomic commit. This requires a multi-op commit: deleteNode(center) + deleteEdge(thread).

4. **Multiple ProseMirror editors on one canvas and focus coordination**
   - What we know: Each NoteCard and ThreadCenterNode has its own ProseMirror EditorView. Only one can be focused at a time.
   - What's unclear: How to coordinate the floating toolbar across multiple editors -- should one toolbar instance be shared (rendered by App/Canvas) or should each editor render its own?
   - Recommendation: One shared toolbar rendered by Canvas, positioned based on whichever editor is currently focused. The toolbar receives the active EditorView as a prop and dispatches commands to it.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| XSS via rich text body injection | Tampering | `plainTextToDoc` builds ProseMirror nodes from text, never parses HTML. The existing `deserializeBody` tries `JSON.parse` then falls back to `plainTextToDoc` -- never `DOMParser.parseFromString`. [VERIFIED: NoteCard.tsx:121-128, 134-147] |
| Malicious anchor IDs in passage marks | Tampering | Anchor IDs are opaque strings stored in ProseMirror mark attrs and kernel edge properties. They are never used in DOM IDs, CSS selectors, or JavaScript execution. Rendered only as `data-passage-id` attributes. |
| Plugin-injected passage marks | Tampering | All durable changes go through `kernel.submit()` (PLUG-06). A plugin cannot write passage marks directly into the ProseMirror editor -- it can only create edges through the kernel API. |
