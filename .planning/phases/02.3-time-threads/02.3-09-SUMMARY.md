# Phase 02.3 Plan 09: A vault thread's file, and an edit made outside Tapestry Summary

**A vault note can carry the D-25 thread property set without ever bending 02.2's `md.*`-is-the-file rule: `VaultService.writeThreadFile` is the one atomic, echo-free path a Tapestry write takes to reach the `.md` file, and `ThreadService.applyObservedEdit` records any edit found outside Tapestry — in the file or in a divergent `body` checkpoint — as exactly one honest `observed` cluster, never spread out and never silently overwriting either side.**

## Accomplishments

- **`vault-thread.ts`** (`isVaultThread`, `writeVaultThreadFile`, `diffFlatText`, `observeVaultEdit`): the vault-side half of D-25, holding zero filesystem access of its own — every real write goes through `VaultService`, matching the plan's own architectural boundary.
- **`VaultService.writeThreadFile`**: the single, atomic (write-then-rename) path a byte ever takes from Tapestry into a vault `.md` file, with `md.text`/`md.sha256` kept in sync in the same commit and the write skipped entirely once the hash already matches — no echo into the journal from Tapestry's own repeated flushes.
- **`ThreadService.applyObservedEdit`** (sharing `applyEditToHandle` with `applyAgentEdit`): commits a `cause: 'observed'` record for any range, without D-22's authorship restriction, because an observed range was not necessarily written by the reconciling actor.
- **Body-checkpoint reconciliation in `ThreadService.open()`**: a `body` property that disagrees with thread.log replay (RESEARCH Pattern 6's no-plugin-fallback-edit case) is recorded as one observed cluster on the very next open, rather than silently letting either side win. A brand-new thread's empty checkpoint is correctly left alone.

## Known Stubs

- **`ThreadCard`'s vault footer is unreachable in production today.** `TreeFrame.tsx` (out of this plan's file list) routes every `obsidian.vault/note@1` node to `VaultNoteCard`, never to `ThreadCard`, regardless of whether that node also carries thread properties. Making an actual vault note into a thread — the UI gesture itself, and the routing decision for how it then renders — is not this plan's job (CONTEXT.md's own "Claude's Discretion" list defers "how a thread is started"); this plan stores the plumbing (`isVaultThread`, the footer copy) the way D-27's frame fields were stored ahead of their own cursor UI in an earlier plan.
- **There is no live filesystem watcher.** `observeVaultEdit` is fully implemented and tested against a caller-supplied "observed text" string, but nothing in this codebase calls it from a real `fs.watch` handler yet — that is 02.2 Plan 10's other half (naming this the same known gap 02.2-07-SUMMARY.md already recorded: "Live watching is Plan 10").
- **The body-checkpoint reconciliation's attribution (whoever calls `open()`) is a documented judgment call, not a proven-correct rule.** See `key-decisions`; a later plan may want a different, more specific actor for this path once a real caller (e.g. an actual fallback body editor) exists.
- **`diffFlatText` ignores paragraph boundaries** (inherited from `readFlatText`'s own documented scope, `thread-tools.ts`'s "cannot match across a paragraph break" limit) — a vault file with multiple lines will diff correctly only to the extent the rest of this tracer's flat-text model already supports multi-line documents, which is itself a known, previously-documented limitation of `thread-service.ts`'s `replayFlatText` (02.3-02-SUMMARY.md's own Known Stubs).

None of the above are placeholder UI shown to a user as if it were real data — every value this plan's code produces is either fully live (a real file write, a real kernel commit) or an honestly-scoped simplification documented above with its own reopening seam.
