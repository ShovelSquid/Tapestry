<objective>
**As a** person who writes by deleting and rewriting, **I want to** see everything I removed still sitting on the line where I first typed it, **so that** the record shows how the document actually came to be rather than only how it ended up.

This plan makes the line honest about editing: ghosts for deleted and undone letters, a mark at the moment each thing went, and markers where a paste, a format or a link happened.

Purpose: D-03's "nothing is erased" is what separates a thread from an autosave. It needs a letter identity that survives edits, which is the `LetterIndex` — the one genuinely new algorithm in this phase, and the only file in it with no analog anywhere in the repo.

Output: the letter index, the full cause vocabulary in the recorder, and ghosts and markers on the stage.
</objective>

  <action>
    Add `app/src/shared/threads/letters.ts` exporting `LetterIndex`: a run table in document order, each run `{ firstLetterId, graphemeCount, utf16Length, actor, insertedAtMs }`.

    Letter ids are **implicit and never written to the file**: the k-th grapheme inserted in thread record order is letter k. That makes them deterministic on replay, so the file stays free of identifiers a reader would have to decode.

    Update runs through `step.getMap().forEach((oldStart, oldEnd, newStart, newEnd) => …)`. Never do manual offset arithmetic — structure steps shift positions in ways hand-rolled maths gets wrong, as the probed Enter step shows by mapping 10 to 12. Keep `utf16Length` and `graphemeCount` separately per run, because one emoji occupies eight UTF-16 positions and treating positions as letters misplaces every glyph after it.

    Resolve deleted ranges to letter ids and stamp them with `deletedAtMs` rather than removing them — the index keeps every letter forever, which is what lets the stage draw ghosts. Handle the split-grapheme case: when a deletion cuts a grapheme in half, mark the whole old letter deleted and insert the remainder as a new letter at the same time, so no partial grapheme is ever addressable.

    Expose `authorOf(letterId)`, `lettersIn(from, to)` and `runsForDecorations()`, the last shaping the per-letter author wash Plan 08 renders.

    Write `letters.test.ts` as a property test against a deliberately naive oracle: a plain per-UTF-16-unit array that records the same operations the slow, obvious way. Run at least 10,000 randomized edit sequences over a corpus that includes ASCII, a ZWJ family emoji, a regional-indicator flag, a combining-accent sequence and multi-paragraph structure edits, and assert the index and the oracle agree on letter ids, authorship and deletion times after every operation.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pasted content → document marks | Content from an arbitrary source carries marks into the document |
| document text → letter identity | Arbitrary Unicode drives grapheme segmentation and index updates |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.3-05-01 | Spoofing | paste carrying author marks | high | mitigate | Author and passage marks are stripped from pasted content in the recorder, so a paste cannot import another actor's attribution. Authorship remains derived from the host-stamped commit actor and is never a document mark |
| T-02.3-05-02 | Denial of Service | pathological grapheme sequences | medium | mitigate | Segmentation uses `Intl.Segmenter` rather than hand-rolled loops; the 10,000-sequence oracle property test includes ZWJ, regional-indicator and combining cases, and the split-grapheme rule bounds the fallout of a partial delete |
| T-02.3-05-03 | Denial of Service | marker flood from rapid editing | medium | mitigate | Markers share the glyph layer's instanced buffers with doubling capacity and update-range marking, so marker count costs no extra draw call; the `--shots` and `--bench` runs exercise a heavily edited stretch |
| T-02.3-05-04 | Tampering | editor metadata forging a cause | low | accept | `threadCause` is set only by in-process toolbar and passage commands within the same renderer; an attacker able to dispatch transactions there already controls the document. The cause affects display only — it never affects authorship or access |

No package-manager install occurs in this plan, so no package-legitimacy gate applies.
