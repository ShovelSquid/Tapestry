<objective>
**As a** person returning to a thread after days away, **I want to** see my writing broken into the sittings it actually happened in, **so that** I can find the evening I wrote something and go back to the document as it was then.

This plan turns a continuous stream of keystrokes into sessions: a time-out draws a dash and ends a sitting, the next keystroke draws a time-in dash and starts a new one, and each sitting becomes a note on a bridge across the 2D canvas.

Purpose: D-07 is what makes a thread navigable rather than merely long. It also delivers the per-thread settings D-10 and D-13 promise, and the honest rule that governs them — a setting change never moves a dash already written.

Output: session derivation, time-out detection in the authority, the canvas bridge, the session list that stands in for the stage, and the settings popover.
</objective>

    Add `app/src/shared/threads/sessions.ts` exporting `DEFAULT_TIMEOUT_SECONDS = 150` (2.5 minutes, matching Apple Messages' timestamp spacing), `detectTimeout(lastActivityMs, nowMs, timeoutSeconds)` and `deriveSessions(records)` returning, for each session, its start, end, letter count, authors and markers.

    The rule that governs this module is **recorded outcomes, not re-derivation**. An `out` record is written when the time-out was detected, under the timeout setting in force at that moment. Changing `thread.timeout` afterwards must never move a dash already on the line. `deriveSessions` therefore reads the `in` and `out` records that exist rather than recomputing session boundaries from timestamps and the current setting. Only where an `out` is missing — a crash before it could be written — does the reader derive one, and the service writes it on the next write.

    Anchor times per batch from `Date.now()` at batch start with monotonic offsets inside the batch, and clamp offsets to at least zero. A laptop sleeping mid-session or a wall clock jumping backwards must not produce a negative or absurd offset. Treat any gap larger than the timeout as an `out` followed by an `in`.

    Extend `ThreadService` to detect the time-out on its existing cadence timer, write the `out` record, and flush it — the time-out is already one of its five flush triggers. On the next keystroke after an `out`, write the `in` record that opens the next session. Read the timeout and slowdown from the node's own properties so each thread uses its own settings.

    Write `sessions.test.ts` covering: a gap longer than the timeout yielding `out` then `in`; a gap shorter than the timeout yielding neither; `deriveSessions` reconstructing boundaries from records alone; and the case that pins the rule — records written under a 150s timeout, then the property changed to 600s, still derive the original session boundaries unchanged. Extend `thread-service.test.ts` with a fake-clock test asserting the `out` record is written at the detected moment and that no past `out` moves when the setting changes.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| settings input → node properties | User-entered timeout and slowdown values are committed to the journal |
| `thread.log` records → derived sessions | Session boundaries are reconstructed from possibly incomplete records |
| system clock → session times | Sleep and clock jumps affect recorded offsets |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.3-06-01 | Tampering | settings values | medium | mitigate | The timeout is validated to the 10s-60min range before commit, and the slowdown text is parsed by `parseSlowdown` with a rejection on malformed input; an invalid value commits nothing |
| T-02.3-06-02 | Repudiation | re-derived session boundaries | high | mitigate | Sessions read the `in` and `out` records that were written, never recomputed from the current setting, so a later settings change cannot rewrite when a person actually stopped writing. The 150-to-600 test pins it |
| T-02.3-06-03 | Tampering | clock jump or sleep | medium | mitigate | Times anchor per batch from `Date.now()` with monotonic offsets inside the batch, offsets clamp to zero, and any gap over the timeout becomes an explicit `out`/`in` pair rather than a single impossible span |
| T-02.3-06-04 | Elevation of privilege | agents changing thread settings | medium | mitigate | Settings are committed through the human path from the settings popover only; no thread MCP tool writes `thread.timeout`, `thread.slowdown` or `thread.format` (enforced in Plan 08's tool surface) |

No package-manager install occurs in this plan, so no package-legitimacy gate applies.
</threat_model>
