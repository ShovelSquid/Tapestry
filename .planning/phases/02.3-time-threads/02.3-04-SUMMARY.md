**1. [Rule 2 - Missing Critical] `App.css` had no `--tap-ink`/`--tap-muted`/`--tap-paper`/`--tap-accent` tokens for `tokens.ts` to read**
- **Found during:** Task 1, writing `stage/tokens.ts`
- **Issue:** The plan's action text says to declare `--tap-thread-line` and `--tap-destructive-text` (the latter already existed from Plan 03); but `tokens.ts` reads a small fixed set of tokens the stage needs (`--tap-paper`, `--tap-ink`, `--tap-muted`, `--tap-thread-line`, `--tap-accent`), and none of the other four existed anywhere in `App.css` as CSS custom properties (only as raw hex literals scattered through the file). Without declaring them, `getComputedStyle` would return empty strings and the stage would render solid black.
- **Fix:** Added all four to the `:root` block alongside `--tap-thread-line`, each matching the existing raw-hex value already used elsewhere in the file for the same role (e.g., `--tap-ink: #2C2C2C` matches the body rule's existing color).
- **Files modified:** `app/src/renderer/App.css`
- **Verification:** `readStageTokens()` returns non-black colors when the bench page loads (visually confirmed via `--shots`).
- **Committed in:** `dc101ba`

**2. [Rule 3 - Blocking] `Ribbon.extendLast()` threw on an empty ribbon**
- **Found during:** Task 2, first `--bench`/`--shots` run — `Uncaught TypeError: Cannot read properties of undefined (reading 'start')`
- **Issue:** The bench page's render loop starts calling `extendLast()` immediately via `requestAnimationFrame`, before the first `buildLoad()` ever runs (and `ThreadOverlay`'s own tick loop has the same theoretical race between mount and history load resolving). `extendLast()` assumed at least one chunk always exists.
- **Fix:** `extendLast()` now starts a fresh zero-length kind-0 chunk at `t` when the ribbon has no chunk yet, matching the same "continue live from here" pattern `addSpan(t0, t0, 0)` already uses elsewhere.
- **Files modified:** `app/src/renderer/threads/stage/ribbon.ts`
- **Verification:** `--bench`/`--shots` no longer throw; `npm --prefix app run test` unaffected.
- **Committed in:** `88bfaa2`

**3. [Rule 1 - Bug] The live view's fade was age-based, contradicting D-14**
- **Found during:** Task 2, investigating why the bench screenshots showed almost nothing
- **Issue:** `createLiveView` set `uFadeOn = 1`, directly copying thread.js's live-view branch — but that ports the spike's own exploratory 20-second age-based alpha fade (`FADE = 20`), which D-14 explicitly supersedes for this phase: "the live view fades by distance only... there is no age-based fading anywhere, and live text is never drawn below full strength." With `uFadeOn = 1`, anything typed more than 20 seconds ago was fully invisible regardless of distance — devastating for any load with more than a few seconds of history.
- **Fix:** Set `uFadeOn = 0` for the live view, so `fadeFor` always returns 1.0 and only ordinary perspective projection governs apparent size/coverage, matching D-14's "distance only" requirement.
- **Files modified:** `app/src/renderer/threads/stage/live-view.ts`
- **Verification:** `--shots` screenshots before/after this fix, compared side by side; after the fix the composition matches spike 001's own reference screenshot (`a-procedural-8hc-live.png`) — a line collapsing to individual dots growing larger toward the now-head.
- **Committed in:** `88bfaa2`

**4. [Rule 1 - Bug] The shared stage canvas never had its CSS size set, so at devicePixelRatio 2 only its top-left quadrant ever fell inside the container**
- **Found during:** Task 2, the same `--shots` investigation as #3 above — after fixing the fade, the ribbon and a debug test cube were *still* rendering crammed into the container's bottom-right corner instead of near center as their computed NDC coordinates predicted.
- **Issue:** `renderer.ts`'s `resize()` called `renderer.setSize(width, height, false)` — the `false` (`updateStyle`) means three.js does not set the canvas's CSS `width`/`height`. On a DPR-2 display the drawing buffer is `width*2 x height*2` physical pixels, but with no CSS size the canvas displays at its own intrinsic pixel dimensions (twice the intended size), so the container only ever shows the top-left quadrant of the full render — content mathematically near the centre of the *intended* frame lands at the visible area's bottom-right corner. Confirmed by projecting a plain `THREE.Mesh` cube through the camera's own matrices (matching its math) while its actual rendered position matched only the corner-crammed layout.
- **Fix:** `resize()` now also sets `canvas.style.width`/`canvas.style.height` explicitly to the logical (non-DPR-scaled) `width`/`height`.
- **Files modified:** `app/src/renderer/threads/stage/renderer.ts`
- **Verification:** `--shots` screenshots after the fix show a diagonal line from a collapsed near-solid stroke fading to individually visible growing dots — matching spike 001's own composition. `--bench` still reports 59.9fps/0% drop/≤95MB after the fix (smaller effective canvas, if anything cheaper to rasterize).
- **Committed in:** `88bfaa2`

**5. [Rule 3 - Blocking] `useThreadEditor` had no way to tell `ThreadOverlay` what was typed and when, at the grapheme level**
- **Found during:** Task 2, wiring live keystrokes to the stage

- **Verification:** `npm --prefix app run test -- src/renderer/threads/recorder.test.ts` (9 tests, all passing).
- **Committed in:** `88bfaa2`
