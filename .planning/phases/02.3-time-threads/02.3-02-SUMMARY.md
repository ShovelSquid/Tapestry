# Phase 02.3 Plan 02: One letter, end to end — typed, committed, reopened, redrawn Summary

**Thread tracer built and wired top to bottom: the `thread.log` grammar codec, a C++ `getPropertyValues` kernel read API, `ThreadService` as single write authority with a 300ms/1s flush cadence, `prosemirror-collab`-backed catch-up-then-editable typer, and the `tapestry-threads` plugin — a person can type into a thread, close the world, reopen it, and get the same text back from `thread.log` records alone.**

## Accomplishments

- Locked, tested `thread.log` grammar codec (`grammar.ts`): `in`/`out`/`ins`/`del`/`mark+`/`mark-`/`step`/`marker` verbs, integer-millisecond offsets, FORMAT.md's inline escape set, `cont`-line splitting past 1 MiB, negative-offset clamping — 9 round-trip tests, all passing.
- D-27 stored frame and D-10/D-13 settings (`settings.ts`), including the ordinary `position.x/y` a thread needs on the 2D canvas alongside its separate `thread.origin.*` frame.
- `getPropertyValues` end to end: a pure C++ scan over `Journal::commits()` (4 doctest cases), an argument-validated addon method, a `KernelBridge` method, and a thin main-process wrapper (4 vitest cases) — reading every `thread.log` value a node was ever given, in commit order.
- `ThreadService`, the single write authority: replays `thread.log` on open (never the `body` checkpoint), applies pushed ProseMirror steps to one authoritative document, classifies each into its grammar record from the document it itself holds before and after, rejects a failing step (including one that throws rather than returning `StepResult.fail`) without committing anything, and flushes on idle 300ms OR max-wait ~1s OR close OR actor switch. The cadence test proves ≥4 commits from a step pushed every 100ms for 5s against a fake clock; the reopen test proves a typed letter survives close/reopen reading `thread.log` alone.
- `thread:open`/`thread:push`/`thread:close` IPC plus `thread:confirmed`/`thread:flush-error` broadcasts, so "Saved" is never shown while a batch is unflushed and a refused flush surfaces as "Not saved" rather than silence (T-02.3-02-06).
- `ThreadOverlay.tsx`: the D-09 live-writing view implementing UI-SPEC's Loading-and-catch-up rules 1-4 verbatim — the checkpoint text shows immediately and read-only, the catch-up status and under-typer line are both gated behind `STATUS_DELAY_MS = 400`, and the `[total] changes` count comes from the addon's own count.
- `tapestry-threads` plugin (manifest + `ThreadCard`), registered through the identical public API `tapestry-notes` uses; `TreeFrame.tsx` selects it by exact type; `App.tsx` can create a thread and opens the overlay.

## Known Stubs

- **The catch-up header status shows `n = total` for its whole visible duration** rather than incrementing (`ThreadOverlay.tsx`, `Catching up (${totalChanges} of ${totalChanges} changes)`). Replay in this plan is a single synchronous scan-and-parse with no incremental progress channel, so there is no real "n so far" to report yet. This is honest given the data available and does not block the tracer's goal (letters surviving reopen); a later plan streaming replay progress for very large threads should replace the static count with a real one.
- **`ThreadCard` has no drag-to-reposition or resize.** A thread's position is fixed once created via `defaultThreadFrame`. Not part of D-06 or this plan's acceptance criteria; NoteCard's ~150 lines of drag/resize logic were deliberately not duplicated for a card that exists to prove the tracer, not full canvas parity.
- **IME composition is buffered and flushed as one batch of raw steps at composition end, not grapheme-resynthesized.** The plan's action text calls for segmenting composed text into graphemes; this tracer instead defers every intermediate composing step and sends them together once composition ends, which avoids Pitfall 5's noise (no mid-composition churn reaches `thread.log`) without needing a doc-diff/grapheme-resynthesis module that has no consumer until a later plan's LetterIndex exists. `recorder.ts` exports a tested `graphemes()` primitive for that module to use directly.
- **`replayFlatText` (in `thread-service.ts`) only replays `ins`/`del` records into a flat, single-paragraph string.** `mark+`/`mark-`/`step`/`marker`/`in`/`out` records are parsed but not applied during replay. This is sufficient for the tracer's own goal — the literal typed text survives a reopen — but a document with formatting, links or multi-paragraph structure will not fully reconstruct until the LetterIndex/replay.ts module (explicitly out of this plan's file list) lands.

None of the above are placeholder UI shown to a user as if it were real data — every value displayed is either fully live (typed text, save state) or an honestly-scoped simplification documented above.
