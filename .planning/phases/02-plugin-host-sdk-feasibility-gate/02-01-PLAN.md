NATIVE ADDON (app/native/): Create CMakeLists.txt that finds node-addon-api include dirs (via cmake-js), adds the tapestry kernel source directory as a subdirectory (the existing tapestry/CMakeLists.txt with TAPESTRY_BUILD_RENDER=OFF, TAPESTRY_BUILD_APP=OFF, TAPESTRY_BUILD_TESTS=OFF), and builds a shared library tapestry_addon linking tapestry_kernel and node-addon-api. The addon.cpp file wraps tapestry::kernel::Kernel in a Napi::ObjectWrap with these methods: static create(path, worldName) returning a new wrapper, static open(path) returning a wrapper, submit(actorKind, actorId, message, ops) where ops is a JS array of operation objects that the binding converts to std::vector of tapestry::kernel::Op, getNodes() returning an array of {id, type, props} objects, getNode(id) returning a single node object, getEdges() returning an array of {id, from, to, label, props}, status() returning the journal status. Each Op object from JS has a field "op" naming the verb (createNode, setProperty, etc.) and the verb-specific fields. The binding constructs the C++ Op variant from these. Actor comes from separate actorKind/actorId string arguments. Submit returns {seq, digest, nodeIds, edgeIds}. Value conversion: JS string to Value::ofText, JS number to Value::ofInt (if integer) or Value::ofReal, JS boolean to Value::ofBool. Property maps returned as plain JS objects with typed values.

Add scripts: "build:native" running cmake-js build --directory native with the appropriate cmake flags to disable render/app/tests on the kernel, "dev" running electron-vite dev, "build" running npm run build:native then electron-vite build, "typecheck" running tsc --noEmit. Add a postinstall script that runs npm run build:native so the addon is compiled after npm install.

KERNEL BRIDGE (app/src/main/kernel-bridge.ts): Load the native addon via require with the built .node file path. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Renderer to Main | IPC messages cross the contextBridge; renderer has no direct Node.js access |
| Main to Native Addon | Function calls from JS to compiled C++ kernel code |
| Plugin to Host | Plugin JS/TS code executes and calls the SDK API |
| Filesystem to App | .tree files and plugin manifests are read from disk |
| npm to Developer | Package installation from the npm registry |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | Plugin direct file access | high | mitigate | Plugins receive only the KernelAPI (submit/getNodes); no file handles or journal access exposed. All mutations go through Kernel::submit which validates and records (D-31, PLUG-06). |
| T-02-02 | Denial of Service | Plugin crash/hang | medium | mitigate | Plan 03 implements D-34 crash detection and auto-restart; this plan establishes the plugin loading boundary. |
| T-02-03 | Elevation of Privilege | Renderer Node.js access | critical | mitigate | nodeIntegration: false, contextIsolation: true, sandbox: true in BrowserWindow webPreferences. All kernel access goes through the contextBridge preload. |
| T-02-04 | Spoofing | Plugin identity | low | accept | Plugin identity derived from its directory name and manifest; user's trust decision per D-31. |
| T-02-05 | Information Disclosure | Cross-plugin data | medium | accept | Single-process Electron model; user trusts installed plugins per D-31. Plugin isolation is not a Phase 2 requirement. |
| T-02-SC | Tampering | npm package installs | high | mitigate | Package legitimacy gate (Task 0) with blocking human checkpoint for all [ASSUMED] packages. |
</threat_model>
