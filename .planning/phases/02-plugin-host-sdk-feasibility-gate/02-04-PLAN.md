SDK CONTRIBUTION TYPES (sdk/src/contributions.ts per D-27, PLUG-02): Define the full contribution surface that plugins use to register capabilities:

NodeViewContribution: nodeType string (dotted-path/name@version), displayName string, component string (name of the React component to render this node type). The component is registered by name and resolved at render time.

CommandContribution: id string (namespaced, e.g. "notes.createNote"), displayName string, handler function receiving (context: CommandContext) where CommandContext includes kernel, selectedNodes, and arguments. Commands must go through kernel.submit for durable effects (PLUG-06, D-31).

PropertyPanelContribution: nodeType string, displayName string, component string (panel component name). Shown in the contextual inspector when a node of that type is selected.

InspectorContribution: id string, displayName string, component string. A general panel contribution not tied to a node type.

Expand the PluginContext interface in sdk/src/index.ts to include registerNodeView(contribution: NodeViewContribution), registerCommand(contribution: CommandContribution), registerPropertyPanel(contribution: PropertyPanelContribution), registerInspector(contribution: InspectorContribution). PluginContext also exposes kernel: KernelAPI (read/write through submit, getNodes, getNode, getEdges, status).

Add a PluginManifest.api field (string, e.g. "1") declaring the SDK API version the plugin was built against. The host checks this at load time.

PLUGIN HOST EXPANSION (plugin-host.ts per D-28, D-29, D-30): Restructure the plugin host into a PluginHost class with these methods:

discoverPlugins(): Scan the plugins/ directory (the directory path is resolved relative to the app root, or to app.getPath("userData")/plugins for packaged apps). Each subdirectory containing a tapestry.plugin.json is a plugin candidate. Parse each manifest and validate required fields (name, version, main, api).

loadPlugin(name): Load the plugin's main entry, construct a PluginContext, call plugin.activate(context). Track the plugin's registered contributions in an internal registry keyed by plugin name. Catch any error thrown during activate and mark the plugin as failed.

unloadPlugin(name): Call plugin.deactivate() if it exists. Remove all contributions registered by that plugin from the registry. Release references. Catch errors during deactivate.

reloadPlugin(name per D-29): Unload then load the plugin. This is explicit by default — a developer must call it (or trigger it via a dev-mode IPC). The host exposes an IPC handler plugin:reload(name).

enablePlugin/disablePlugin(name): Toggle the plugin's enabled state. Disabling calls unloadPlugin. Enabling calls loadPlugin. Both record a journal event through the kernel (D-32): submit a Proposal with actor kind "system", actor id "tapestry", and a message describing the event (e.g. "enabled plugin tapestry-notes"), with no ops (the event itself is the record). This records the fact in the .tree history.

getContributions(): Return the full registry of contributions across all loaded plugins, grouped by type (nodeViews, commands, propertyPanels, inspectors).

MANIFEST AND COMPOSITION (D-28): Each plugin's tapestry.plugin.json is the readable manifest. The plugin's main entry (index.ts) is the composition file that describes pieces and how they fit together. The host does not require any specific file structure beyond these two — the plugin author decides how to organize their code (D-27).

JOURNAL RECORD PROTECTION (D-31): The KernelAPI exposed to plugins does NOT include any method to read or write raw journal bytes, truncate, repair, or saveAs. Plugins can only submit Proposals through the kernel.submit method, which validates and records through the normal Kernel::submit path. The native addon does not expose Journal methods to JS.

PRELOAD EXPANSION: Expose plugin:list, plugin:reload, plugin:enable, plugin:disable, plugin:getContributions through the contextBridge. The renderer uses these to know which components to render for each node type.

MISSING PLUGIN FALLBACK (D-33, PLUG-07): When the app opens a .tree file containing nodes whose type (e.g. example.physics/body@1) has no loaded plugin providing a nodeView for that type, render those nodes using a FallbackNodeView component instead of hiding them. The FallbackNodeView reads the node's properties through kernel.getNode and displays them in a generic readable format: the node type as a header, each property as a key-value pair with the value formatted using the kernel's formatInline equivalent (text as quoted string, int/real as number, bool as true/false, ref as the target id, time as the ISO string). The fallback card uses the same card styling as a regular note (white background, border, shadow) but with a muted header indicating the plugin name is unavailable.

The canvas's node rendering logic: for each node, check if a nodeView contribution exists for that node's type. If yes, render the contributed component. If no, render FallbackNodeView. This ensures a world always opens regardless of which plugins are installed (D-33).

DISABLED PLUGIN CONTENT (D-35, PLUG-04): When a plugin is disabled, its contributions are removed but its nodes remain in the world. Those nodes render through FallbackNodeView. The user can still read the node's data. The fallback view also allows basic property editing through a generic key-value editor: clicking a value makes it editable inline, and saving submits a SetProperty through the kernel. Custom commands, editors, themes, or other UI from the plugin are not available, but the data is accessible (D-35).

CRASH HANDLING (D-34): Wrap plugin.activate() calls in a try-catch. If a plugin throws during activate or during a command handler execution:
1. Immediately show a PluginErrorNotification component with the text "[Plugin name] stopped working. Restarting..." (from UI-SPEC copywriting).
2. Attempt one automatic restart by calling unloadPlugin then loadPlugin.
3. If the restart succeeds, dismiss the notification automatically after 3 seconds.
4. If the restart fails, update the notification to "[Plugin name] could not restart. Your work is safe." with two action buttons: Restart (tries loadPlugin again) and Dismiss (hides the notification and leaves the plugin disabled).
5. Disable the failed plugin. Its nodes render through FallbackNodeView.
6. Any unfinished durable transaction from the plugin is never applied — the kernel's submit is atomic, so a partially constructed Proposal that was never submitted leaves the world intact. If a submit was in progress when the plugin crashed, the kernel's scratch-copy-then-swap ensures the prior state is preserved.

VERSION COMPATIBILITY (PLUG-05): When loading a plugin, compare its manifest.api field against the host's supported API versions (for Phase 2, only version "1" is supported). If the plugin's api field is missing, does not match, or names a version the host does not support, refuse to load the plugin and record a PluginLoadResult with status "incompatible" and a reason string (e.g. "Plugin requires API version 2, host supports version 1"). Surface this to the user through a notification or in the plugin:list response.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Plugin to Host | Plugin code runs in the main process; SDK restricts what it can access |
| Manifest to Host | Plugin manifests are parsed from disk; malformed manifests must not crash the host |
