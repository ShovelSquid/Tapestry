# Roadmap: Data Drawing

## Overview

Data Drawing's first milestone puts a pressure pen in the user's hand first and builds the deterministic core underneath it in the same phase. Phase 1 is one vertical slice: a fixed-point C++20 sim with its determinism harness, compiled to WebAssembly and running in a renderer Web Worker, driving a plugin-owned canvas inside Tapestry where strokes from a pressure pen land as nodes on a plane facing a fixed camera, placed by a spring-damper brush body whose mass can be felt and seen. Strokes live in memory only; nothing is written to a `.tree`. Phase 2 makes the world persist: the sample-block grammar is judged on real painted sessions with Kaelen, the brush and material contract is completed (dead zone, finish line, settling) so the grammar is frozen once, and a golden example enters Tapestry's readability suite. Phase 3 makes time navigable and marks revisable: play, scrub, reverse, reopen with hash verification, and erase, undo, and inspect as recorded actions that history keeps.

This ordering deliberately inverts the research's headless-first sequence (harness, behaviour, grammar, host, painting, timeline). Feel is what the milestone is for, and the grammar is a one-way door that is better judged after painting has shown what a stroke actually needs. The risks research front-loaded stay front-loaded, inside Phase 1: the fixed-point rule and hash harness (SIM-01, SIM-02) are Phase 1's first wave, because they cannot be retrofitted, and the pen surface builds on them rather than before them; the `wasm` preset is pinned on the harness skeleton before any behaviour exists to blame; the Tapestry host surface extension point (CANV-04) is an external dependency that now gates Phase 1 rather than Phase 3 and is raised with the outer Tapestry roadmap on day one; and the pen is measured on this Mac at the start of the surface wave rather than in a side spike. What moves later is only the one-way door itself: no `.tree` is written until Phase 2, so Phase 1's in-memory action shape costs nothing to change.

Branching, snapshots on disk, model rendering, and the replay oracle CLI are out of scope or v2 (see REQUIREMENTS.md); scrubbing in this milestone is replay from tick zero with an in-memory keyframe ring.

## Phase Details

### Phase 1: Painting with the Pen

**Goal**: The user paints with a pressure pen inside Tapestry and watches nodes land on a plane facing a fixed camera, placed by a deterministic fixed-point sim running live in a Worker, with a brush body whose mass can be felt and seen.
**Mode:** mvp
**Depends on**: Nothing (first phase). External: the Tapestry host surface extension point (CANV-04) is built in the outer Tapestry project; raise it with the Tapestry roadmap on day one, since painting cannot ship as a plugin without it.
**Requirements**: SIM-01, SIM-02, SIM-03, STRK-01, STRK-02, STRK-03, STRK-04, STRK-06, CANV-01, CANV-02, CANV-03, CANV-04
**Success Criteria** (what must be TRUE):

  1. Inside Tapestry, the Data Drawing plugin owns a WebGL or WebGPU canvas through a public SDK extension point (no app edits outside that extension point, no Electron APIs in the plugin), and drawing on it with a pressure pen places nodes on a plane facing the fixed camera with drawing-program feel: pressure drives node weight, the heavy preset visibly lags and carries momentum through curves, and the light preset follows closely.
  2. Only samples with a pen tip down are recorded (mouse painting behind a setting), captured at the device's full sample rate through pointer capture and coalesced events; predicted events shape the preview tail only and never enter a recorded stroke. Each recorded sample is integer plane position, pressure, and tilt and twist when the pen reports them, stamped with tick and sample index; each stroke carries its plane frame and node positions are stored as 3D with z from the plane, so replay never depends on the camera.
  3. The sim runs as WebAssembly in a renderer Web Worker reached only through a flat C ABI; the renderer reads state through read-only views copied between steps and can never mutate it. The placeholder renderer colors each node from a hash of its brush description, and a cursor overlay draws the pen position, the brush body position, and the spring between them.
  4. Three or four brush presets differing in description and mass can be picked; editing a brush creates a new version, and a stroke made with the old version keeps it and replays to the same nodes.
  5. Replaying the session's recorded action list from tick zero in the Worker reproduces the node field and hash shown live; in the native build, replaying the same synthetic stroke log twice, across Debug and Release, across two processes, and after a serialize/restore round trip yields the same SHA-256 state hash at every checkpoint; the build fails if `float`, `double`, `<cmath>`, `<random>`, or `unordered_` appear in the sim target; nodes are emitted at the brush's spacing with ids derived from stroke ordinal and emission index, so replaying with one stroke inserted leaves every other stroke's node ids unchanged.

Planning notes:

- Wave 1 is the harness, and the pen surface builds on it: fx64 Q32.32 on int64 with portable widening multiply, ids with reserved branch-tag bits, seeded PRNG with per-entity streams, POD state, canonical serialize/restore/hash, CI grep, `-fwrapv` and UBSan in tests, all passing on a no-op `step()` before any behaviour rule exists. Pin the tick rate (60 Hz recommended) as a constant here; changing it later is a new world. Establish the `wasm` CMake preset and pin the Emscripten version on this skeleton so toolchain failures surface with no behaviour to blame.
- Wave 2 is sim behaviour, native and headless: the Stroke action with tick-stamped samples (position, pressure, tilt, twist fields from the start so STRK-06 never reopens the sample shape), BrushBody as semi-implicit Euler spring-damper with stiffness and damping derived from mass and clamped to the stable region, Emit at spacing with `(stroke ordinal, emission index)` ids, a versioned immutable brush table with presets; golden hashes on synthetic strokes, the insert-a-stroke id-stability test, and identical geometry whether stepped one tick at a time or four.
- Raise CANV-04 with the outer Tapestry roadmap on day one; it is the one item outside this project's control and it now gates Phase 1's last wave. Needs codebase research in the outer project: `TreeFrame.tsx`, `plugin-host.ts`, preload/IPC, and the SDK contribution model; verify Vite worker and `.wasm` bundling under electron-vite 2 and whether `crossOriginIsolated` is reachable (design avoids `SharedArrayBuffer` regardless). Waves 2 through 4 can proceed in the plugin's own dev loop (a Vite page loading the Worker sim) while the extension point lands, but the phase is not complete until the surface is mounted in Tapestry through the public extension point; a surface compiled into the app is not an acceptable interim.
- Wave 3 is the host: flat C ABI (`create/apply/step/hash/serialize/positions`), Wasm loaded in a Web Worker with transferred `ArrayBuffer` snapshots, a `SimHost` that is async from day one with a fixed-timestep accumulator draining whole ticks only (no fractional final step), actions applied at the start of their stamped tick before physics, and pause in the interface even though transport UI is Phase 3.
- Wave 4 is the surface, and it starts by measuring the pen on this Mac in the Electron dev build (pressure range, tilt presence and sign, `pointerType`, coalesced rate, eraser end, `pointerrawupdate`, `isSecureContext`); the numbers become the fence's constants, not a side spike's notes. The deterministic fence: a native (non-React) pointer listener with `setPointerCapture` and `touch-action: none`, paint only on `pointerType === 'pen'` with `buttons & 1`, ray-plane unproject and quantize once at the boundary, tick-stamp, optimistic feed to the live sim. Renderer choice (three.js `WebGPURenderer` with WebGL 2 fallback vs raw WebGL2 like the Phase 2.3 thread stage) is confirmed in discussion against the extension point's constraints; check `about:gpu` under Electron 32. Measure pen-to-ink latency with and without the Worker split.
- Deliberately deferred: no `.tree` writing and no save; the in-memory action carries the integer fields the journal will carry, quantized once at the fence, but no serialized form is chosen, so the pressure quantization width (12 vs 16 bit, sized to what the driver delivers) is provisional until Phase 2 freezes it with the grammar; stroke ordinals come from the in-memory session count (the `getNextIds()` prediction arrives with the commit pipeline in Phase 2); nodes stay where they are emitted until Phase 2's Settle rule; dead zone and finish line are Phase 2 (STRK-05); the camera is fixed and never recorded (orbit and a movable plane are v2, CANV-05).

### Phase 2: Readable Journal

**Goal**: A painted session persists as a Tapestry `.tree` a person can read without the plugin and reopens into the same world, with the brush and material contract completed (dead zone, finish line, settling) before the sample-block grammar is frozen on real files.
**Mode:** mvp
**Depends on**: Phase 1
**Requirements**: JRNL-01, JRNL-02, JRNL-03, JRNL-04, SIM-04, STRK-05
**Success Criteria** (what must be TRUE):

  1. A saved Data Drawing `.tree` opened in a text editor shows each stroke with its brush description, its tick, and its branch, with the stroke's samples as one line of integer fields per sample; the plugin registers node types for stroke, brush version, and canvas (seed, tick rate, sim, fixed-point, and PRNG version pins as properties) through the public SDK.
  2. Painting in Tapestry commits each stroke through the kernel, and ticks enter the journal only as coalesced advance commits, one before each stroke and one on pause or close, so a session of N strokes contains at most N+1 advance commits and never one commit per tick; closing and reopening the world replays its recorded actions into the same node field that was painted.
  3. With the Data Drawing plugin disabled, Tapestry still opens the world and shows readable fallback values for every Data Drawing node.
  4. A golden Data Drawing example `.tree` lives in Tapestry's readability suite, the tests regenerate it byte for byte, and the plugin's TS codec decodes it into the same ordered action list the sim consumed to produce it.
  5. Placed nodes drift and settle by mass under a versioned, data-driven Settle rule and quiet nodes sleep so idle ticks replay cheaply; a light brush follows the pen directly through a pulled-string dead zone and every stroke completes to the pen's final position on pen-up; all three are versioned (the rule version pinned on the canvas node, dead zone and finish line as brush-version parameters) so the grammar is frozen once.

- Complete the contract before freezing: STRK-05 adds dead zone and finish line to the brush-version parameter set before `brush@1` closes, and SIM-04's Settle rule version joins the pins on `canvas@1`; do both first in this phase so the golden fixture is produced by the final rule set. Settling also gives Phase 3's timeline something alive to scrub.

### Phase 3: Timeline and Marks

**Goal**: The user moves through the world's time and revises its marks without losing history: play, pause, step, speed, scrub, and reverse; reopening proves the file reproduces the recorded state; erase and undo are recorded actions; any stroke can be inspected.
**Mode:** mvp
**Depends on**: Phase 2
**Requirements**: TIME-01, TIME-02, TIME-03, MARK-01, MARK-02, MARK-03
**Success Criteria** (what must be TRUE):

  1. The user can play, pause, single-step, and set speed in ticks per rendered frame with a tick readout, and changing speed never changes the frame rate or input handling.
  2. The user can scrub to any tick on a scrubber with stroke markers and play in reverse as a decreasing scrub target; the shown state at tick T equals from-zero replay to T, and the in-memory keyframe ring is verified against from-zero hashes and never written to disk.
  3. Reopening a saved world replays its recorded actions in the Wasm sim and verifies the resulting state hash against the hash recorded at save, reporting any divergence with the first differing tick; a settled world reopens settled.
  4. The user can erase within a radius and undo the last stroke, both as new recorded actions: erased and retracted strokes remain in the `.tree`, the hash chain stays intact, and scrubbing back before the erase or undo shows the nodes again.
  5. Selecting a stroke shows a read-only inspector with its description, tick, brush version, weight, and velocity.

Planning notes:

- Scrub is replay from zero with an in-memory keyframe ring keyed by `(branch, tick, versions)`; sleeping nodes from SIM-04 keep idle-tick replay cheap. Measure scrub latency and reverse frame rate on a recorded session of representative length.
- Speed is ticks per rendered frame on the Phase 1 `SimHost` accumulator, never frame-rate capping; pause is the same pause that triggers the advance-on-pause commit from Phase 2.
- Decide the v1 behaviour of pen-down while scrubbed off head (simplest: snap to head before recording, with ticks-per-frame reset to 1); the visible cue and block are v2 (TIME-04), and branch-at-tick undo is Tapestry Phase 3.
- Erase and retract use the action encodings reserved in Phase 2: erase is a radius on the plane at the current tick over the stable ids from Phase 1, retract references a stroke ordinal; neither truncates the log.
- The inspector reads description, tick, and brush version from the journal and weight and velocity from the sim's read-only views; selection is a hit test on the plane against emitted node positions.
